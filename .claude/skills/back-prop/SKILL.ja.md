# Back Prop

カーネルを跨いだ drift 検出の統合役。**read-only の detector を並列に fan-out** し、集約したうえで、
per-item の承認と書き込みのループを**自分で**回す。

canonical はこのディレクトリの `SKILL.md`（英語）。規約の正はそちらで、この訳は参考である。

## 使うとき

- 複数のカーネルを触った変更のあと、pull request のレビュー前。
- 定期の掃き取り —— 文書化されていない規約、規則の写しを抱えたスキル、動いたものを説明している README。
- リポジトリ全体の規約を導入するとき、**どこで既に守られていて、どこでまだ守られていないか**を見る。

**1 つのカーネルだけを見たいときも、この統合役を回してスコープの質問でそのカーネルを選ぶ。**

## Contract

| | |
| --- | --- |
| **Owns** | 宣言（README / スキル / 語彙表）と実物のずれの検出、per-item の承認、README への書き込み |
| **Never** | 実装コードの書き換え / ADR 本文・`docs/rules.md` の書き換え / 承認なしの書き込み / detector に書かせること |
| **Starts when** | 複数カーネルを触った後、あるいは定期の掃き取り |
| **Stops when** | 全 finding の承認 / 棄却が終わったとき。user はいつでも打ち切れる |

## このスキルを使わない場面

- **README ↔ ディスクの構造 drift** —— `sync-readme`。**この 2 つは重ならない**。あちらは
  「README のファイルとディレクトリの一覧が、ディスクの実物と合っているか」を問い、こちらは
  「README の**記述**が、いまコードがやっていることを説明できているか」を問う。
  **どちらも他方の部分集合ではなく**、交わるのは目録の節だけである。
- **README の portal 価値の判定** —— `readme-review`。
- **差分のレビュー** —— `impl-review` / `test-review` / `comment-sweep`。
- **実装コードの修正。**finding は提示する。直すのは user。

## 構造: 並列の detector と、統合役側の承認

検出は read-only の [`drift-detector`](../../agents/drift-detector.md) エージェントへ委譲し、
**範囲内のカーネルごとに 1 回ずつ、すべて 1 メッセージで起動して並列に走らせる。**
**エージェント定義は 1 つ、起動は複数** —— カーネルごとにエージェントのファイルを置くと、
同じロジックを 11 か所で保守することになり、**腐るのは写しのほう**である。

**detector は厳格に read-only** である。理由と選択肢を添えて finding を提示するだけで、
`AskUserQuestion` を呼ばず、書き込まない。承認と書き込みのループは**ここ**で、集約の後に
**単一スレッド**で回る —— それが、detector を**書き込みの競合ゼロで並列に**走らせられる理由である。

**検出の基準は [`prompts/detect-drift.md`](prompts/detect-drift.md) が単独で持つ。**
このスキルも、エージェント定義も、基準を書き直さない —— **どちらもそのファイルを読む。**
以下にあるのは**組み立ての手順だけ**である。

## Step 0 —— スコープと種別を確認する（`AskUserQuestion` 1 回）

差分から既定を自動判定したうえで、2 問をまとめて聞く。

1. 「back-prop のスコープを選んでください」
   - 「変更ファイルのみ（ベースとの diff。触れたカーネルだけ fan-out）」
   - 「リポジトリ全体（全カーネルを fan-out）」
   - 「特定のカーネルのみ（続けて指定）」
   - 「キャンセル」

2. 「検出する drift の種別を選んでください（複数選択、既定は全部）」
   - 「(A) README → コード」 / 「(B) コード → README の未文書化パターン」 /
     「(C) スキル ↔ README の重複」 / 「(E) 業務語彙が家を出ていないか」

**(C) と (E) はソースファイルに依存しない**ので、差分がコードに触れていなくても選ぶ値打ちがある ——
**散文だけの変更こそが、スキルの持つ規則の写しをずらし、業務語を README に住み着かせる case** である。

## Step 1 —— カーネルとファイル一覧を解決する

「変更ファイルのみ」のとき:

```sh
BASE=$(gh pr view --json baseRefName -q '.baseRefName' 2>/dev/null || make -s base-branch)
test -n "$BASE" || { echo "ベースブランチを解決できませんでした"; exit 1; }
git diff --name-only "origin/${BASE}...HEAD"
```

**既存の pull request の `baseRefName` が権威のままである** —— 報告する drift は、PR が見せている
差分の中に座っていなければならない。PR が無いときは `make base-branch` が `origin` の実状態から
最新のリリースラインを解決する。**`gh repo view --json defaultBranchRef` は代替ではない** ——
GitHub の既定ブランチは前のリリースラインを答え続ける。

**ベースが解決できないなら、続けずに止める。**空のファイル一覧は detector を 0 個 fan-out し、
drift を 0 件報告する —— **それは clean な実行と見分けが付かない。**

変更ファイルを `src/` 配下のパスでカーネルへ写す。**カーネルの一覧は
[`architecture.ts`](../../../architecture.ts) から実行時に読む。ここに一覧を持たない** ——
この本文の一覧は、カーネルが 1 つ着地した時点で偽になる。カーネルごとのファイル一覧は保持し、
**detector へ渡す**（detector が git を解決し直さないようにするため）。

(C) か (E) を選んだときは、散文のコーパスも解決する —— 層の `README.md`、`docs/adr/*.md`、
`docs/rules.md`、(C) なら `SKILL.md` の本文 —— そして「変更ファイルのみ」では差分と交差させる。
交差が空でなければ `docs` スコープの detector 起動を 1 つ足す。リポジトリ全体なら常に足す。

**ソースの変更も散文の変更も無いなら、そう述べて綺麗に終える。**

## Step 2 —— detector を並列に fan-out する

範囲内のカーネルごとに、**Agent ツール**で `drift-detector` を起動する。
**1 メッセージの中で複数のツール呼び出し**として出し、並列に走らせる。それぞれに渡すもの:

- `layer` —— カーネル名。散文だけの起動なら `docs`
- `files` —— Step 1 で解決したファイル一覧
- `categories` —— 選ばれた種別の部分集合
- `baseRef` —— ベースブランチ

**各 detector の最後のメッセージが、その finding そのものである。**カーネルのラベルと一緒に集める。

> この環境でエージェントを起動できないときは、代わりに `prompts/detect-drift.md` をその場で辿る ——
> 承認と書き込みのループは、それでも統合役が単一スレッドで回す。

## Step 3 —— 集約する（read-only の中間確認）

finding をカーネルと種別でまとめた 1 つの日本語のサマリにする。
**どんな判断より先に、user が全体の面を見られるようにする。**

```text
back-prop drift 検出結果（scope: <X>, 種別: <選択された種別>）

[<kernel>]  A <n> / B <m> / C <k> / E1 <p> / E2 <q>
  ...（各 finding: 該当・正本・理由・選択肢・確度）

総 finding: <sum>。これから 1 件ずつ承認 / 棄却を確認します。
```

全 detector が clean で返ったときは、**どのカーネルを見たかを述べる。**
**範囲を名指さない clean な報告は、何も fan-out しなかった実行と見分けが付かない。**

## Step 4 —— per-item の承認と書き込み（単一スレッド）

finding ごとに、**統合役**が判断を回す。

1. detector が提示した選択肢で `AskUserQuestion`（コード修正 / README 更新 / 規則の緩和 /
   スキルの簡略化 / 無視）。
2. **README** の変更が承認されたら: 理由を述べ、変更前 / 変更後の draft を見せ、最終確認の後に書く。
3. **スキル**の変更が承認されたら: **ここで本文を編集せず `manage-skill` へ渡す。**
   あれが `.claude/skills/**` の単一の入口であり、**canonical と対訳を 1:1 に保っているのもあれ**である ——
   ここで編集すると `SKILL.ja.md` が置き去りになる。
4. **コード修正**なら: user の作業として提示する。**このスキルは実装コードを一切書かない。**
5. 全 finding を回す。user はいつでも打ち切れる。

**書き込みの範囲はちょうど、層の `README.md` だけ。**それ以外は引き渡しか報告である。

**E2 の finding は、そもそも承認にかけない。**それらは ADR か `docs/rules.md` に座っている ——
**決定の記録と、統べる文書**である。detector を満足させるために書き換えると、**誰が決めるのかが
反転する。**報告に載せ、そこへ置いたままにする。E の finding を `docs/spec/glossary.md` の編集で
「解消」してもならない —— **語彙は `glossary` が保守するもの**であり、finding を黙らせるために
用語を消すことは、**移すのではなく定義を壊すこと**である。

書いた後は、**この実行が書いたものだけ**を整形する。

```bash
pnpm exec markdownlint-cli2 --no-globs --fix <書いたパス>
```

`--no-globs` は効力を持つ —— 付けないと設定の `globs` が引数へ**追加され**、木全体が書き換わる。
`pnpm lint:md` は hook と CI に任せる。

## Step 5 —— 完了報告（日本語）

```text
back-prop 完了（scope: <X>, 種別: <選択された種別>）

[<kernel>]  finding <N>, README 更新 <X>, manage-skill へ委譲 <Y>, コード修正委任 <Z>, 無視 <W>

総 finding: <sum>, README 書き込み: <sum>, コード修正委任: <sum>, 報告のみ（E2）: <sum>
```

**覆わなかったものを平明に述べる** —— 範囲から外したカーネル、選ばなかった種別、走らせられなかった
detector。**述べない省略は「そこは綺麗だった」と読まれる。**

## AI 変更範囲

このスキルの起動が、`AGENTS.md` の変更範囲を緩める明示の指示である。緩むのは**層の `README.md` だけ**で、
**この実行の間だけ**である。

実行中も保護されたままのもの: `AGENTS.md`、`LICENSE`、ADR 本文、`docs/rules.md`、`docs/spec/**`、
実装コード、生成物、`.claude/settings.json` の `permissions.deny` の対象。
**detector は一切書き込まない。**

## やる / やらない

- ✅ 何かを読む前に、スコープと種別を 1 回で確認する。
- ✅ ベースは `commit` / `submit-pr` と同じ解き方で解く。解けないなら止める。
- ✅ カーネルの一覧は `architecture.ts` から実行時に読む。
- ✅ detector を 1 メッセージで fan-out し、並列に走らせる。
- ✅ 解決したファイル一覧を渡し、detector に git を解決し直させない。
- ✅ どんな判断より先に集約を見せる。
- ✅ 各書き込みの前に、理由を述べ、変更前 / 変更後の draft を見せる。
- ✅ スキル本文の変更は `manage-skill` へ渡す。
- ✅ clean な実行でこそ、見たカーネルを名指す。
- ✅ 日本語で報告する。
- ❌ detector を逐次起動する。
- ❌ detector に書き込ませる / `AskUserQuestion` を呼ばせる。
- ❌ 実装コード・ADR 本文・`docs/rules.md`・`docs/spec/**` を書く。
- ❌ E2 を承認にかける / glossary を編集して E を黙らせる。
- ❌ 該当が 3 件未満の (B) パターンを提示する。
- ❌ 検出の基準をここへ書き直す（`prompts/detect-drift.md` を指す）。
- ❌ `pnpm lint:md` などのゲートを回す。
- ❌ commit / push する。

- [ ] どんな判断より先に集約サマリを出した。空の種別は空と述べた。
