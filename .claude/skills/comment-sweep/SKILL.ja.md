# Comment Sweep

蓄積したコメントを、既存のレビュアーが問えない 1 つの問いで裁く。**この内容はここに属するか。**

同じディレクトリの `SKILL.ja.md` に日本語の参考訳がある（スキルとしては読み込まれない。人間の参照用）。

## 使用する場面

- 1 行ずつは正しいのに、あるディレクトリのコメントが膨れて散文的に感じる
- doc コメントが設計論・脅威モデルの議論・棄却した代案の一覧へ育っている
- 同じ根拠が ADR とその後に続くコードの両方にある。片方は必ず腐り、腐るのは誰も読み返さない側である
- カーネル / feature / `scripts/` の定期的な整理
- リリース前や、テンプレートからリポジトリが作られる前。蓄積した記述が他人の負担になる

## このスキルを使わない場面

- **README / docs の散文の質** — `doc-reviewer`
- **README ↔ コードの構造ドリフト** — `sync-readme` / `back-prop`
- **実装やテストのレビュー** — `impl-review` / `test-review`

## このスキルが在る理由

コメントを変更のたびに 1 件ずつ裁く読み手が答えられるのは **削除**（その内容は在るべきでない）か **書換**（内容は正しいが述べ方が悪い）だけである。どちらにも当てはまらない第 3 の場合がよくある。**内容は正しく残す価値もあるが、コメントに属していない。**

その判定が **移設**であり、read-only のレビュアーには 2 つの理由で持てない。**移設先の文書を書く**必要があり、それはレビュアーがしてはならない。そして判断対象が 1 つの差分ではなく蓄積した在庫である —— ADR と 5 箇所の呼び出し地点に重複した同じ根拠は、変わったものだけを見ていては見えない。

### 2 つめの問い —— 1 件ずつでは原理的に見えないもの

管轄は 1 件のコメントに対して問うものであり、そこには同じ形の死角が残る。同じ Why が 3 つの宣言に書かれているとき、**各コピーは単独で管轄の判定を通る** —— どれも非自明で、どれも自分が前提を述べている場所に在り、どれも個別には擁護できる。1 件ずつ裁けば 3 件の 維持 になる。重複はコメント同士の関係にしか存在しないので、1 件ずつのパスではどれだけ丁寧に回しても見つからない。

そこで掃引は必ず、ファイルのコメント在庫を 1 つの塊として 2 つめの問いを立てる。

> **この内容は同じファイルの他所に既にあるか。あるなら、どの site が所有するのか。**

答えになる形は 3 つあり、どれも 1 件ずつでは到達できない。

- **重複** —— 1 つの Why が複数の宣言で言い直されている。1 つの site が概念を所有し、残りはポインタへ縮む
- **分散** —— 1 つの制約が宣言をまたいで割れ、どこにも全体が書かれておらず、読み手が組み立てる羽目になっている。直し方は 1 つの site を完全にすることであり、4 つめの断片を足すことではない
- **総量過多** —— どのコメントも個別には正しいのに、そのファイルのコメント総量が、説明している対象のコードより読むのに高くつく

これは差分スコープの罠と同じものが 1 段下で起きている姿である。各コピーを残す論拠は、単独で問われるかぎり毎回勝つので、何も統合されない。集合に対して問う。

### 例外 —— 汎用部品の公開 doc

**題材を知らない再利用部品は、集約の対象外とする。対象外にするのは集約だけである。**その部品の公開 doc コメントと、その部品自身の `README.md` は、同じことを言ってよい。

理由は読み手が違うことにある。design system の部品を使う人は、呼び出し位置で editor の hover を通してそれに出会うのであって、README を開いているとは限らない。開いていなければ prop の意味が判らない、という形にすべきでもない。一方 README は、目録を眺めている人がこの部品でよいかを決める場所である。**どちらも入口であり、他方が読まれた前提を置けない。**片方をポインタへ縮めるのは、その doc が存在する理由である読み手を犠牲にして、ファイルの見た目を整える取引になる。

したがって汎用のカーネル配下の部品（`src/components/**` と、`README.md` が feature ではなく部品を説明しているもの）については:

- **doc とその部品の README のあいだの重複は、意図された冗長であって drift ではない。**指摘しない
- **両者が食い違っていれば、それは指摘である**（`誤り/陳腐化`）。食い違った時点でどちらかが誰かに嘘をついている。コードと一致しているのはどちらかを述べる
- **削除 / 書換 / 移設 は影響を受けない。**How の語りは依然として How の語りであり、ADR の持ち物は依然として ADR の持ち物である

これは、**1 つの宣言の doc の中で**同じことを繰り返してよいという許可ではない。それは読み手が一度に見るので、コピーは誰の役にも立たない。この例外は、読み手の違う 2 つの文書についての話であって、分量についての話ではない。

## このスキルが読むもの

**実行時**に読む。方針を焼き込まない —— 基準は動くので、このファイルがその古い写しになってはいけない。

| 出所 | 何を決めるか |
| --- | --- |
| `docs/rules.md`「コメントと文書」 | **コメントの基準** —— コメントが何であり何でないか、名前の付いた誤配 |
| `docs/README.md`「2 つのテスト」 | 下の判定が当てる前提の所在テストと管轄テスト |
| `AGENTS.md` | Language Rules（コメントは日本語）と Code Style |
| `.claude/agents/comment-reviewer.md` | 基準をコメント 1 件に当てるレビュアー。本スキルのパス 1 が使うのと同じレンズ |
| `docs/adr/` | 移設先の候補と、各 ADR が既に述べていること |
| 掃引先の上位にある層 / feature の `README.md` | もう 1 つの移設先候補と、その宣言された責務 |

## 手順 0. 範囲と適用モードを決める

`AskUserQuestion` 1 回に **2 問**を載せる。引数やフラグで既に確定している問いは出さない。両方が確定しているなら呼び出し自体を行わない。

- 「comment-sweep の対象スコープを選んでください」
  - 「変更で触れたファイル」 —— 変更が触れたファイルを**丸ごと**掃く。base は `gh pr view --json baseRefName -q .baseRefName`、PR が無ければ `make -s base-branch` で解く（`gh repo view --json defaultBranchRef` は使わない）
  - 「1 カーネル / 1 feature」 —— 例: `src/adapters/`、`src/features/<name>/`
  - 「`scripts/` の 1 ツール」
  - 「パスを指定」
- 「検出結果をどう適用しますか？」
  - 「判定の束ごとに確認して書き換える」 ← 既定
  - 「そのまま書き換える（確認を取らない。文書書き込みを伴う移設は対象外）」
  - 「報告のみ（書き込まない）」

**掃くのは 1 ディレクトリずつ。** リポジトリ全体の掃引は誰も終えられない承認待ちの列を作り、半端に終わった列は無いより悪い —— 読み手が掃引済みと未掃引を区別できなくなる。

### 適用モード

| モード | 選び方 | 手順 3–4 の挙動 |
| --- | --- | --- |
| 確認して適用 | 既定の選択肢、または `mode: confirm` | 手順 3 で判定の束ごとに承認を取り、手順 4 で書き込む。全判定が到達可能 |
| 自動適用 | `--apply`、または 2 番目の選択肢 | 手順 4 が 削除 / 書換 / 確度 high の集約 を確認なしで書き込む。文書書き込みを伴う移設は報告するだけで適用しない |
| 報告のみ | `--report-only`、または `mode: report` | 手順 3 で検出結果を全文提示して終了。何も書かない |

### フラグ

- `--apply` —— 自動適用。モードが確定するのでモードの問いは出さない
- `--report-only` —— 報告のみ。検出して報告するだけで、書き込まない
- 両方の同時指定は優先順位の問題ではなく矛盾である。その旨を伝え、黙って一方を選ばずモードの問いへ戻す

## 手順 1. 基準と移設先を読む

1. コメントの基準を読む（上の表）。記憶からではなく今回の実行で読む
2. 範囲の上位の `README.md` と、そこが参照する ADR を読む
3. 範囲の全ファイルを読む。コメント**と**その下のコードの両方。管轄の判断はコメントだけでは下せない —— 前提がその呼び出し箇所に在るかは、コードについての事実である

## 手順 1.5. ファイルを跨いだ繰り返しの走査（機械）

パス 2 が問うのは 1 ファイルの在庫についてである。同じ Why が `adapters` の各クライアントへ 1 回ずつ、
各 feature の `actions.ts` へ 1 回ずつ、`scripts/` の各ツールへ 1 回ずつ書かれている形は、そこからは
見えない —— ファイル単位のパスはファイルを跨げず、しかも**各コピーは単独では管轄の検査を通っている**。
だから誰も気づかない。

範囲内の全ファイルのコメント行を集め、行頭の記号と字下げを落とし、節に満たない短い行を捨て、
**2 つ以上のファイル**の宣言に現れた文を報告する。

```sh
for f in <範囲内のファイル>; do
  grep -hE '^[[:space:]]*(//|\*|#)' "$f" \
    | sed -E 's@^[[:space:]]*(//+|\*|#)[[:space:]]?@@' \
    | awk -v f="$f" 'length($0) > 30 { print f "\t" $0 }'
done | sort -t$'\t' -k2 \
  | awk -F'\t' '{ n[$2]++; src[$2] = src[$2] "\n    " $1 }
                 END { for (k in n) if (n[k] > 1) print "[" n[k] "] " k src[k] }'
```

`grep` は効力を持つ。これが無いとコードと空行までクラスタになり、巨大で無意味な塊が 1 つ出るだけになる。
`\*` の枝は JSDoc の継続行を拾う —— このリポジトリで根拠が書かれているのはたいていそこである。

pipeline そのものより、**決定的で安価である**という性質が重要である。だから「重複を疑ったとき」ではなく
**毎回の掃き取りで回す**。長さの下限は範囲に合わせて調整する。低すぎると定型の一行が支配し、高すぎると
一行の Why が抜ける。

**走査するのは手順 0 が決めた範囲のファイルだけ。**リポジトリ全体へ広げると 1 ディレクトリの規律が壊れ、
この実行では誰も手を付けられないクラスタが出る。

各クラスタは手順 2 の判定で裁く —— まず管轄（たいていは各所で 移設 か 書換）、ファイルを跨いだ 集約 は
**1 つの宣言が本当に概念を所有しているときだけ**。**各メンバーが単独では正しくても、クラスタは finding である。**
それがこの走査の全趣旨である。

## 手順 2. 範囲の全コメントを分類する

同じファイルに対して**2 つのパスを回す**。見つかるものが違い、どちらももう一方の代わりにならない。パス 1 はコメント 1 件ごとの管轄を問い、パス 2 はファイルの在庫の所有を問う。パス 2 は追加の読み込みを行わない —— 足すのは問いだけである —— ので、パス 1 が何も見つけなかったファイルも含め全ファイルで回す。個別には全部まともなファイルこそ、重複が隠れる場所である。

判定は 5 つ。最初の 3 つは既にあり、後の 2 つがこのスキルの足すものである。

| 判定 | パス | どんなとき | 動作 |
| --- | --- | --- | --- |
| **維持** | 1 | 正しい What、または前提の所在テストを通る制約 | そのまま置く |
| **削除** | 1 | How のナレーション、言い換え、経緯、トートロジー、コードが既に満たしているマーカー | 取り除く |
| **書換** | 1 | 内容は正しいが述べ方が悪い —— 腐っている、曖昧、事実より長い | その場で書き直す |
| **移設** | 1 | 正しく残す価値もあるが、前提の所在テストを通らず、管轄テストが文書を名指す | その文書へ移し、効力のある残余と、**層 / feature README への**1 行の参照を残す |
| **集約** | 2 / 1.5 | 同じ内容が複数箇所に載っている —— 1 つのファイルの中、または手順 1.5 がクラスタにした範囲内の複数ファイル（重複 / 分散 / 総量過多）。**汎用部品の公開 doc とその部品の README のあいだでは挙げない** —— 上の例外を見よ | 1 つの site が本体を持ち、残りはポインタへ縮む |

**移設の判定基準**: その宣言を編集せずに、この記述を偽にできるか。できるなら、ここでは誰も検証できず、偽になっても何も報告しない。**どこでなら検査されるか**を問う。そこがその記述の家である。

**1 つのコメントは 1 度しか報告しない。** あるコメントが個別の 書換 の対象でも、同時に集約の集合のメンバーでもあるときは、**集約が勝ち**、短縮を吸収する。そうしないと同じ行が、部分的に矛盾する 2 つの判定でユーザーへ二度出される。

### 集約の finding が必ず含むもの

集約は対象が**集合**になる唯一の判定であり、以下はすべて、その集合を 1 つの単位として決められるようにするためのものである。どれか 1 つでも欠けた集約はレビューできない。

1. **形** —— 重複 / 分散 / 総量過多。壊れ方が違うので、形を名指すことがレビュアーに何を確かめるかを伝える
2. **全メンバー** —— それぞれの `file:line` とコメントの全文。本体に残す site だけではない: 統合は勝者だけを見て判定できない
3. **本体を持つ site と、その根拠** —— どの宣言が内容を保持するのか、そして*なぜその宣言なのか*。基準は概念の所有であって、コメントの長さでもファイル内の順序でもない。そのコメントが答える問いを持った読み手が最初に辿り着く場所である。誤った選択がここでの高くつく失敗であり、それが見えるころには他の site は既に縮んでいる
4. **集約後の文面** —— 本体側が持つ全文。縮む側が手放したものを覆っていなければならない。あるメンバー固有の事実を黙って落とす統合は、別の判定の名を借りた削除である
5. **各ポインタ** —— 他の site すべてに残す残余そのもの。「詳細は上記参照」はポインタではない。宣言名を書き、その行へ直接来た読み手が辿れるようにする。本体が別のファイルなら**ファイル名と宣言名**を書く —— `docs/rules.md` が「複数ファイルが同じ概念の値を使うなら所有モジュールを一つ決めてそこから参照する」に既に要求している形と同じである
6. **確度: high / medium / low** —— 飾りではなく効力を持つ。自動適用が集約を無人で適用するのは `high` のときだけなので、正直に付ける。`high` とは、同じ事実を述べている文と、概念を所有する宣言を指し示せる、ということである。どの site が勝つべきか迷うなら `medium` が上限である

**集約は文書を書かない** —— 1 つのファイルの中でコメント間を動かすだけである。正しい家がコードの外の散文だと判ったなら、それは**移設**であり、両者を 1 つの finding に混ぜない。

### 移設先と、拒むべき 2 つの誤配

**行き先の判定は `docs/README.md` が持つ** —— 候補を分類する 4 種、行き先を名指す順序付きの判定、境界を裁く 2 つのテスト、そして既定（どの行き先にも当てはまらない候補はコードに残る）。**拒むべき 2 つの誤配は `docs/rules.md`「コメントと文書」の「設計判断を、それを所有しない文書へ置かない」が持つ** —— ライブラリや API の固有の挙動は呼び出し地点に残し、業務知識は ADR ではなく `docs/spec/` へ行く。移設の判定が行き先を要するときは、両方を読む。

ここに写しを置かない。同じ規則が 2 か所に在ると、片方が改訂された日に、このスキルと他の還元経路が同じコメントへ違う行き先を答えはじめ、しかもどちらが権威かはどちらの写しも述べていない。

この規則の上にこのスキルが足すのは、判定と書き込みである —— 内容が他所に属するコメントは**移設**であり、移設先の文書への書き込みは読み手に委ねずここで行う。

分類は**モード非依存**である。手順 0 が何を決めていようと、全 finding を全文で生成する —— 3 モードの差はすべて手順 3–5 にある。報告するだけだからと分類を手加減した実行は、適用するために分類した実行と静かに食い違い、それを検出する手段は無い。

## 手順 3. 承認のループを回す

所見を**判定ごとに束ねて**、影響の大きい順（移設 → 削除 → 書換）に提示する。各項目に次を添える。

- `file:line` とコメントの原文
- 判定と、一文の理由
- 移設なら、移設先のファイルと、そこへ入れる文言そのもの
- コードへ残す残余（制約が残るなら、呼び出し箇所を無言にしない）

**確認して適用**では `AskUserQuestion` で束ごとに確認する:「この判定で適用しますか？」/「個別に確認したい」/「この分類は見送る」。1 回の確認で 40 箇所を編集する掃引はレビューできない。**自動適用**ではここで確認を取らない —— 手順 4 が何を書いたかを事後に述べる。

**集約は、集合全体を覆う 1 問である。**メンバーごとに問わない。分割するとユーザーが選んでいない結果が出る: 縮む側だけ承認されれば Why が消え、本体側だけ承認されれば何も統合されない。集約 /「現状のまま（維持）」/「別の site を本体にする」/「判断を保留」を提示し、全メンバーを見せる。

**報告のみではここで終了する。**そしてその場合、上の束ごとの要約だけでは足りない。`維持` 以外の finding を全件・全文で提示する —— 根拠、コメントの変更前 / 変更後、移設なら移設先へ入れる文言そのものまで。1 件ずつ明かしていく承認ループが後に続かないからである。最後に、この報告をどう実行に移すかを書く: 削除 / 書換 / 集約 だけなら `--apply` で、移設も含めるなら確認して適用で再実行する。集約は本体に残す site だけでなく全メンバーのコメントを描画する —— 統合は勝者だけを見て判定できない。

## 手順 4. 適用 —— コードと移設先を同時に

報告のみでは到達しない。残る 2 モードの間で書き込みそのものは同一であり、違うのは誰が承認するか、そして判定のどこまでが対象になるかである。

### 自動適用 —— 確認を取らない

手順 2 が分類したとおりに **削除**・**書換**・**集約** を一括で適用し、書いた内容を報告する。まず、その集合から次の 3 つを外す。

- **コードと矛盾するコメントの finding** は報告するだけで適用しない。コメントとコードのどちらが誤っているかはコメント整理の判断ではなく、コメントを消せばバグの唯一の証拠を消しかねない。下記のガードは既に「報告して止まる」と述べている。無人ではそれが、報告と、二度と誰の耳にも入らない欠陥との分かれ目になる
- **移設先が既にその内容を述べている移設**は、その文書を開いて内容が実在することを確認できたときだけ適用する。人が介在するモードではその主張は承認の時点で検証されるが、無人では、節を読み違えた実行がコードから根拠を剥ぎ取り、そう書いていない文書へ残滓を向けてしまう。確認が取れなければ適用せず報告へ回す。確認を通った移設は文書に触れない —— 実体は残余＋参照への短縮である
- **メンバーが複数ファイルに跨る 集約 は、適用せず報告する。**ファイルを跨いだ統合は、そのうちどれか 1 つを読んでいる者からは見えないファイルを編集する。しかもカーネル全体から所有する宣言を選ぶのは、最も誤りやすい判断である。着地は 確認して適用 のほう。
- **集約を適用するのは `確度: high` のときだけ。**書換 が誤るのは 1 箇所の文言だが、統合はそれに加えて*どの宣言が概念を所有するか*を選ぶ判断であり、選択の誤りが見えるころには他の site は既に縮んでいる。取り消しの難度が明らかに高いので、実行側が `medium` / `low` と付けたものは適用せず確認して適用へ回す

**文書書き込みを伴う移設は適用しない。**件数と着地形を報告し、それらが着地するのは確認して適用である旨を伝える。理由は一般論としての慎重さではない。`AGENTS.md` の *AI Modification Scope* は `docs/adr/BACKLOG.md` の編集を許すが、**ADR ファイルの新規作成には事前のユーザー指示を要求**しており、ある根拠が新規レコードになるのか既存の書き換えになるのかはまさにその判断である。「質問しない」を契約とするモードにはそれを問う手段が無い。そこだけ質問を残せば契約が壊れ、黙って答えればリポジトリ方針の判断を生成器が下したことになる。

下記のガードはすべて有効なままである。自動適用が外すのは確認であって規則ではない。

### 確認して適用 —— 承認された束のとおりに書く

承認された項目ごとに、**両側を同じ手順で**書く。

1. 移設先の文書へ、その文書の語り口と節構成に合わせて根拠を足す。コメントをそのまま貼らない —— コメントと文書では読まれ方が違う
2. コードを編集する。移した散文を取り除き、効力のある残余を残し、**層 / feature README への**
   1 行の参照を足す —— 散文が ADR へ着地した場合でも、**参照先は ADR ではなく README**である。
   `docs/rules.md` がコメントからの ADR 参照を禁じている。ADR は番号も節も決定の所在も動くが、
   README は層と一緒に動くので、README への参照は気づかれずに腐ることがない。関連する ADR を
   列挙するのは README の役目である。

片方だけを行わない。移設先が存在しないうちにコードから根拠を消すのは情報の破壊であり、両端を握っているのはこのスキルだけである。

承認にもモードにも関わらず効くガード。

- **機能ディレクティブを消さない** —— `// @ts-expect-error`、`// biome-ignore …`、`// eslint-disable*`、`/** @jsxImportSource … */`、`// Code generated … DO NOT EDIT`、shebang。（`"use client"` / `"use server"` は文字列ディレクティブでコメントではない。触らない）
- **保護されたパスを編集しない。** `AGENTS.md`、`LICENSE`、`.claude/settings.json` の `permissions.deny` にあるものは触らない。Accepted な ADR 本文は v1.0.0 未満では編集でき、通常の移設先である。v1.0.0 以降は他の ADR 編集と同じく承認を要する
- **生成ファイルに触れない** —— `**/gen/**`、生成バナーを持つもの
- **コードの振る舞いを書き換えない。** コードが誤っているせいでコメントが誤っているなら、報告して止まる

## 手順 5. 検証

書き込みが発生したときだけ実行する。報告のみには検証する対象が無い。自動適用こそ最も必要である —— 1 件ずつ人間が編集を読んでいないからである。

```sh
pnpm fix
pnpm lint:ci
pnpm md-lint
```

そのうえで、触れたファイルの差分を読み直し、コメントと文書だけが変わったことを確認する。振る舞いは不変でなければならない。`git diff` に文が変わった箇所が出たなら、それはこの実行の欠陥である。

**ファイルを跨いだ 集約 の後は、触れた全ファイルを読み、縮んだ側から各ポインタを辿って本体の宣言まで行けることを確かめる。**そこに立っている読み手から辿れない宣言を名指したポインタが、この判定が持ち込む失敗である。

**集約の後は、編集した箇所を個別に見るのではなくファイルを頭から通して読む。**finding がファイルについてのものだったので、検査もそうでなければならない。この読み方でしか出ない失敗が 2 つある: 本体の site が、縮んだ側の手放した内容を実際には持っていないこと。そして、ポインタが、そこに立っている読み手からは辿れない宣言を名指していること。

## 手順 6. 報告

ファイルごとに何を 維持 / 削除 / 書換 / 移設 / 集約 したか、移設がどこへ着地したかを述べる。手順 1.5 のファイル横断クラスタ数は別立てで報告する —— **手を付けなかったクラスタも含めて**。誰も手を付けなかったクラスタが、最も再発しやすい finding である。**集約は 1 件として数え**、メンバー数を併記する —— 承認の前に編集の大きさが見えるようにするためである。**掃かなかったもの**も平明に述べる —— 後回しにしたディレクトリ、設計判断が要るため見送った所見。述べない省略は「このディレクトリは綺麗だ」と読まれる。

**自動適用**では、適用を見送った finding とその理由も名指す —— コードと矛盾するコメント、文書書き込みを伴う移設、移設先を確認できなかった移設。述べられない見送りは、そもそも挙がらなかった finding として読まれる。

## 他のレビュースキルとの関係

このスキルは**コメント**を所管し、所管するのはこのスキルだけである。どのレビュースキルもコメントのレンズを持たず、このスキルは他のスキルの内側からではなく単体で呼ばれる。`/impl-review`（変更そのもの）と `/test-review`（テスト）は `AGENTS.md` の Review Phase Protocol における対等な相方であり、別々に問われ、別々に決められ、互いに委譲しない。

## 制約

- ✅ 基準と移設先の文書を今回の実行で読む
- ✅ 掃くのは 1 ディレクトリずつ
- ✅ 全ファイルで 2 つのパスを回す —— コメント 1 件ごとの管轄と、ファイル単位の在庫の所有
- ✅ モードに関わらず全コメントを全文で分類する —— モードが変えるのは手順 3–5 であって手順 2 ではない
- ✅ 集約は集合全体を覆う 1 つの不可分な判断として承認を取る
- ✅ 確認して適用では、承認は判定の束ごとに取る。掃引ごとではない
- ✅ 移設先の文書とコードを同じ手順で書く
- ✅ 報告のみでは `維持` 以外の finding を全文で提示し、何も書かない
- ❌ 自動適用で、移設先の文書を書く移設を適用する
- ❌ 確度 `medium` / `low` の集約を無人で適用する、または集約をコメントごとの問いに分割する
- ❌ 汎用部品の公開 doc がその部品の README と重複していることを集約として挙げる —— その冗長は意図されたもので、指摘になるのは両者の食い違いだけ
- ❌ 同じコメントを 書換 と 集約 の両方で報告する —— 集約が短縮を吸収する
- ❌ 無人のモードで、コードと矛盾するコメントの finding を適用する
- ❌ ライブラリ固有の挙動をコードから移設する
- ❌ 業務知識を ADR へ移設する
- ❌ 機能ディレクティブの削除、生成ファイルへの接触、保護されたパスの編集
- ❌ 振る舞いの変更
