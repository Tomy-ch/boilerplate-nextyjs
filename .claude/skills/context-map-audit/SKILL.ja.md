# Context Map Audit

記録された地図と木を突き合わせ、**乖離を報告し、何も変えない。**

canonical はこのディレクトリの `SKILL.md`（英語）。規約の正はそちらで、この訳は参考である。

## 使うとき

- リリース前、あるいは外向きの口を増やした / 減らした作業のあと。
- 定期の掃き取り。
- 地図がまだ実物を説明できているか、誰かが疑ったとき。

## Contract

| | |
| --- | --- |
| **Owns** | 地図と実物の突合、3 種の乖離の報告、検査できた辺と**できなかった辺**の申告 |
| **Never** | 地図の編集 / コードの編集 / 所有ラベルの決定 / 乖離のどちらが正しいかの決定 |
| **Starts when** | 外向きの口が増減した後、リリース前、あるいは定期の掃き取り |
| **Stops when** | 3 種の乖離を報告したとき。修正は `context-map` か実装側の仕事 |

## このスキルを使わない場面

- **地図の更新** —— `context-map`。**こちらは設計として read-only。**
- **差分のレビュー** —— `impl-review`。
- **その辺がそもそも存在すべきかの判断。**それは設計の問いであって、監査の所見ではない。

## なぜ編集しないのか

**乖離は 2 通りに読め、監査にはその 2 つを区別できない。**地図に行の無い辺がコードに在ることは、
**地図が古い**ことかもしれないし、**「やらない」と決めたものが足された**ことかもしれない。
**ここからは両方まったく同じに見え**、そのうち一方だけが「行を書く」ことで直る。

だから監査は報告して止まる。書くのは `context-map` で、聞いてからである。この分割は儀式ではない ——
**コードの現状を黙って記録する監査は、あらゆる drift を既成事実へ変換し、
地図は「コードが間違っている」と言えなくなる。**

## Step 0 —— スコープを確認する

`AskUserQuestion` 1 回。

- 「監査のスコープを選んでください」
  - 「変更で触れた口のみ」 —— 差分に入っている入口と外向きの呼び出し
  - 「全体」 —— 地図の全辺と、木の全接触点

## Step 1 —— 両側を列挙する

**木の側は `context-map` と同じやり方で列挙する。**そうしないと、**何を辺と数えるかで 2 つが食い違う** ——
`src/config/` / `src/adapters/` / `src/app/api/**` / metadata の面 / `src/proxy.ts`。
資源ではなく相手で数える。サンプル限定の辺を分ける。

そのうえで [`docs/design/context-map.md`](../../../docs/design/context-map.md) を読み、
その行を**記録された側**とする。

**どちらの側も、他方に対する権威ではない。**それこそが、この実行が修正ではなく**所見**を出す理由である。

## Step 2 —— 3 つの乖離

- **接触点はあるが辺が無い** —— 木がある相手に触れているのに、地図が記録していない。
  **コード上の場所を報告し、所有を提案しない** —— その問いは `context-map` のものであり、
  **ここで答えると組織的な事実を検分で決着させることになる。**
- **辺の相手が消えた** —— 地図が記録している相手へ、木のどこからも届かなくなった。
  **どのパスを探索したかを報告し、主張を反証可能にする。**
- **記録された翻案が依存表と食い違う** —— 依存表がもう翻案を強制していないのに地図が「翻案あり」と
  言っている、あるいはその逆。**これが機械的な答えを持つ唯一の軸**なので、
  それを決めている [`architecture.ts`](../../../architecture.ts) の規則を述べ、**読み手が確かめられるようにする。**

**所有は監査しない。**コードに入っていないので、**突き合わせる相手がここには無い** ——
在ると言えば、それは**比較を発明すること**である。所有が 未確定 の項は、乖離としてではなく
**開いた項目**として述べる。

## Step 3 —— 報告し、検査しなかったものを述べる

```text
context-map 監査（scope: <X>）

検査した辺: <N> / 地図の辺: <M>
検査できなかった辺: <K> — <理由。1 行ずつ>

[接触点はあるが辺が無い] <n>
  - <counterpart> — `<path>`（所有は未判定。context-map が問う）
[辺の相手が消えた] <n>
  - <counterpart> — 探索した範囲: <paths>
[記録された翻案が依存表と食い違う] <n>
  - <counterpart> — 地図: <翻案あり|なし> / 依存表: <rule>

所有が未確定のまま残っている辺: <n>

本スキルは何も変更していません。地図の更新は context-map、実装側の修正は user が行います。
```

**件数の行は飾りではない。**何辺を検査したかを言わずに「乖離なし」と報告する監査は、
**何も走査しなかった実行と見分けが付かない。**しかもこの地図の辺の数は**少なく安定している**ので、
**そっと 2 辺だけ見た実行は、綺麗な全走査とまったく同じに見える。**

**検査できなかった辺は、綺麗だったとしてではなく検査できなかったものとして報告する** ——
設定はされているがこの checkout からは到達できない相手は、**何の証拠でもない。**

## やる / やらない

- ✅ 木の側を `context-map` と同じやり方で列挙する。
- ✅ 相手で数える。サンプル限定の辺を分ける。
- ✅ 辺の無い接触点はコード上の場所を報告し、所有は `context-map` へ残す。
- ✅ 相手が消えたと主張するときは、探索したパスを述べる。
- ✅ 翻案の食い違いを報告するときは、依存の規則を引く。
- ✅ 何辺を検査し、何辺を検査できなかったかを述べる。
- ✅ 日本語で報告する。
- ❌ 地図・コード・その他を編集する。
- ❌ 乖離のどちら側が正しいかを決める。
- ❌ 所有ラベルを付ける / 監査する。
- ❌ 検査していない辺を「綺麗だった」として報告する。
- ❌ ゲートを回す。
