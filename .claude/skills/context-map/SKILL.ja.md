# Context Map

この層が外と触れる場所を列挙し、辺ごとに 2 つを記録する ——
**片方は機械が決め、もう片方は人にしか決められない。**

日本語参考訳はこのディレクトリの `SKILL.ja.md`（人間の参照用。スキルとしては読み込まれない）。

## 使うとき

- 新しい外向きの呼び出し・入ってくる口・第三者の埋め込みが現れた。
- まとまった作業のあと、地図を最新化する。
- `context-map-audit` が「コードに在るが地図に無い辺」を報告した。

## Contract

| | |
| --- | --- |
| **Owns** | 接触点の列挙、辺ごとの「境界の所有」と「翻案の有無」の記録、所有の候補提示 |
| **Never** | 所有のラベルを自分の権限で書く / 各辺の仕組みをここへ書く / 主題ごとの design 文書を書き換える |
| **Starts when** | 外部との接点が増減した、あるいは地図を最新化するとき |
| **Stops when** | 所有が人に確認され、地図が書かれたとき |

## このスキルを使わない場面

- **地図と実物の突合** —— `context-map-audit`。**こちらは書き、あちらは読むだけ。**
- **辺の仕組みの説明。**それは `docs/design/` の、それを所有する主題の文書のものである。地図は指すだけ。
- **設定値の追加** —— `new-env`。

## このスキルが決してやってはならないこと

**境界の所有を自分で決めてはならない。**

地図は辺ごとに 2 つの軸を記録する。**読み手には両方が要る**ので一緒に記録するが、
**決まり方はまったく違う。**混ぜると、**誰も擁護できないラベルを地図が抱える**ことになる。

- **翻案の有無は機械が決める。**契約から生成した型は [`architecture.ts`](../../../architecture.ts) の
  `adapters-gen` の区画に住み、そこへ届くのは `adapters` だけである —— したがって生成型は
  **出る前に必ず写される。依存表を読む。ここに判断は無い。**
- **境界の所有はコードから一切出てこない。**この相手と交渉できるのか、公開されたものに追従するしか
  ないのかは、**人と合意についての事実**である。**リポジトリをどれだけ丁寧に読んでも、どちらかは分からない。**

だから所有については、**証拠を集め、候補を提示し、人に選ばせる。**自分の権限でラベルを書くと、
**権威あるように見えて実はそうでない地図**ができ、次の読み手には**どのラベルが確立されたもので
どれが推測だったのかを見分ける手立てが無い。**

## Step 0 —— スコープを確認する

`AskUserQuestion` 1 回。

- 「地図のスコープを選んでください」
  - 「変更で触れた口のみ」 —— 差分に入っている入口と外向きの呼び出し
  - 「全体」 —— 接触点を列挙し直す
  - 「1 つの辺」 —— 相手 1 つ。追加か改訂

## Step 1 —— 接触点をコードから列挙する

**列挙する。思い出さない。地図の値打ちは列挙にしかない。**

| どこを見るか | 何が出るか |
| --- | --- |
| `src/config/` | 目的別のモジュール。**外の宛先を名乗るものはそれぞれ 1 つの辺**であり、住所が実際に住んでいるのはそのモジュールである（[0030](../../../docs/adr/0030-environment-variable-management.md)） |
| `src/adapters/` | 外向きのクライアントと transport、そして生成型が関わるかどうか |
| `src/app/api/**` | このリポジトリが所有する入ってくる口 |
| `src/app` の metadata / `robots` / `sitemap` | 呼び出し元ではなく**標準**である入りの辺 |
| `src/proxy.ts` | 上のどれよりも先に横取りされるもの |

**サンプル破棄で消える辺と、残る辺を分ける。**サンプルが在るからこそ存在する相手は、
テンプレート利用者が受け取る地図の一部ではない —— 範囲は
[`scripts/setup/remove-sample/sample-manifest.ts`](../../../scripts/setup/remove-sample/sample-manifest.ts)。

**接触点は資源ではなく相手で数える。**1 つのバックエンドに対する 10 個の endpoint は 1 つの辺である。
**地図はこの層が誰と話すかの話であって、何を頼むかの話ではない。**

## Step 2 —— 翻案を依存表から決める

辺ごとに [`architecture.ts`](../../../architecture.ts) を読み、
**外の語彙が書き換えられずに内側へ届きうるか**に答える。

- 生成された wire 型が `adapters-gen` の区画に閉じ、`adapters` からしか届かない → **翻案あり。**
  外の形がそのまま到着することが**構造上ありえない**。
- 標準がそう言うのでそのまま運ばれる外部の形式 —— 読まずに転送する封筒、組み立てて渡す URL →
  **翻案なし。**

**印象ではなく規則を引く。**この軸は依存表についての事実であり、
**読み手はあなたを信用せずに確かめられなければならない。**

## Step 3 —— 所有の証拠を集めてから、聞く

辺ごとに、**実際に知りうるもの**を揃えて提示する。

- **契約を公開しているのは誰か** —— 標準化の団体、相手、あるいはこのリポジトリ。
- **それが変わったとき、ここで何が起きるか** —— 追従するしかないのか、形はこちらのものか。
- **版や交渉が存在するか** —— 版の付いた契約か、動く的か。

そのうえで聞く。選択肢は**関係の読み方**として書く。**ラベルとして書かない。**

```text
質問: <相手> との境界は、どちらが決めますか？
選択肢:
  - 相手が決める（こちらは追従する）
  - こちらが決める（口の形をこのリポジトリが持つ）
  - 標準が決める（どちらも仕様に従う）
  - どれでもない / まだ分からない
```

**最後の選択肢を必ず入れる。**所有をまだ誰も述べられない辺は**本物の答え**であり、
**未確定と記録するほうが、欄を埋めるために選ばれたラベルより役に立つ。**

## Step 4 —— 地図を書く。地図だけを書く

[`docs/design/context-map.md`](../../../docs/design/context-map.md) を書く。辺ごとに、相手・所有・翻案・
契約の出所・そして**どの文書が仕組みを所有するか**。

**仕組みをここへ書かない。**どう繋ぐか・何を送るか・失敗をどう畳むかは、それを既に所有する主題の文書のものである。
**書き直した地図は 2 か所を同時に古くする**。そして**地図のほうが、誰も読み直さない写し**である。

**それらの主題の文書を編集しない。**仕組みが変わったのなら、それはその保守者の変更であって、
このスキルの変更ではない。

文書はサフィックス無しのパスの日本語で、**`.ja.md` の対を持たない**
（[0140](../../../docs/adr/0140-documentation-operations.md)）。書いたものだけを整形する。

```bash
pnpm exec markdownlint-cli2 --no-globs --fix docs/design/context-map.md
```

## Step 5 —— 完了報告（日本語）

足した辺・直した辺・消した辺、user が決着させた所有と**未確定のまま残した所有**、そして
**サンプル限定だったので記録しなかった辺**を述べる。スコープを名指す。

## AI 変更範囲

このスキルの起動は、`AGENTS.md` の変更範囲を `docs/design/context-map.md` **だけ**へ、
**この実行の間だけ**緩める。主題ごとの文書、ADR、`src/config/` は保護されたままである。

## やる / やらない

- ✅ 接触点をコードから列挙する。記憶からは列挙しない。
- ✅ 資源ではなく相手で数える。
- ✅ サンプル限定の辺と、残る辺を分ける。
- ✅ 翻案は依存表から決め、規則を引く。
- ✅ 所有は証拠つきの候補として提示し、人に選ばせる。
- ✅ 「どれでもない / まだ分からない」を出し、選ばれたら未確定と記録する。
- ✅ 各辺の仕組みを所有する文書を指す。
- ✅ 日本語で報告する。
- ❌ 所有のラベルを自分の権限で書く。
- ❌ 所有をコードから推測する —— そこには入っていない。
- ❌ 主題の文書が所有する仕組みを書き直す。
- ❌ 主題の文書・ADR・`src/config/` を編集する。
- ❌ このリポジトリが採用していないモデリング手法の関係語彙を使う。
- ❌ `.ja.md` を作る / ゲートを回す。
