# Design System Export

This skill takes the design system out of the repository and puts it in front of a design tool, so
that design work happens with the real tokens and the real component inventory rather than a
guess at them.

The reason it exists as a skill rather than a script is the split the plan draws: **the artifact is
tool-agnostic, the delivery is not.** `scripts/design-bundle` knows nothing about any SaaS, and
must stay that way — naming a specific vendor in the repository's permanent documents conflicts with
ADR [0010](../../../docs/adr/0010-standards-and-non-lockin.md) (standards conformance and
non-lock-in). Everything vendor-shaped therefore lives here, in one place that can be replaced
without touching the repository.

A Japanese reference translation is available at `SKILL.ja.md` in the same directory (not loaded as
a skill; for human reference only).

## When to Use

- The user wants the design system visible in an external tool — to review it, redesign parts of it,
  or design new screens on top of it.
- The user asks to reflect the current components or tokens into Figma.
- The user wants an AI to critique the design system as a whole, and needs something to hand it.

## Do NOT use this skill for

- **Changing components.** Edits happen under `src/components/`, governed by
  [`components/README.md`](../../../src/components/README.md). This skill only reads.
- **Writing stories or component docs.** That is ordinary component work.
- **Pulling anything back into the repository.** The dependency direction is fixed at repo → design —
  see §The one-way rule.

## The one-way rule

The plan fixes the dependency direction and this skill must not bend it. **Nothing generated by the
design tool is written into the repository by this skill.** Not tokens, not component source, not
screenshots. If the user wants a design proposal implemented, that is a separate, ordinary
implementation task where a human decides what to take.

The reason is that a design tool's output is a *proposal about how things should look*, while the
repository is *what actually ships*. Letting the proposal flow back automatically means the code
starts tracking a tool nobody validates, and the tool becomes an upstream that every repository created from this template inherits.

## Step 1. Confirm the destination and the scope

Call `AskUserQuestion` before producing anything:

1. **Destination** — which external tool receives the bundle. Do not infer it from the conversation;
   the destination determines everything downstream.
2. **Scope** — the whole design system, or a subset (a layer such as `design-system`, or named
   components). The bundle is cheap to produce whole, so prefer whole unless the user is aiming at a
   specific part.

If the user has not decided on a destination, produce the bundle anyway and stop after Step 2. The
bundle is useful on its own — it is the thing that gets attached, pasted, or read.

## Step 2. Produce the bundle

```bash
pnpm build-storybook   # design:bundle reads storybook-static/index.json for the story list
pnpm design:bundle
```

`tmp/design-bundle/` then contains three things, and knowing what each is for decides how you use it:

| Path | What it is | What it is good for |
| --- | --- | --- |
| `r/*.json` | shadcn registry items — every component's source, inlined, with title and purpose | A tool that can consume a shadcn registry ingests this directly. Everything else can still read the source |
| `catalog.md` | The inventory: layer, heading, purpose, what each component does **not** own, and its story names | The first thing to hand any assistant. It is the whole design system in one readable file |
| `tokens.css` | The generated semantic tokens | Colours and spacing. A design tool that builds its own variables needs this, not the component source |

`tmp/` is gitignored. **Never commit the bundle** — it is derived, and committing it creates a
second copy of the design system that will drift from the components.

If `pnpm design:bundle` reports a missing `storybook-static/index.json`, the Storybook build was
skipped or failed; run it first rather than working around the error.

## Step 3. Deliver to the destination

### Destination A — assistants that read files

Claude, v0, Lovable and similar tools have no design-system import API; they take files a person or
an agent gives them. The delivery is therefore the same for all of them and the differences are only
in what each can read.

1. Lead with `catalog.md`. It is the map, and an assistant that reads it first asks better questions
   about everything else.
2. Add `tokens.css` when the task touches colour, spacing, or typography.
3. Add the specific `r/<component>.json` files the task concerns. Do not attach all 100+ — the
   inventory is in `catalog.md`, and a wall of source crowds out the actual question.
4. State the constraint explicitly to the receiving tool: **the output is a proposal, and the
   repository is not going to be edited from it.** Tools default to emitting code to paste back;
   saying this up front keeps the answer focused on design.

### Destination B — Figma

Figma cannot be reached by handing over files. Its REST API does not create design content; frames,
components, and variables are created by the Plugin API, which runs inside the Figma editor. The
route is therefore an agent with Figma access, not a script.

Delegate rather than reimplementing: the `figma-generate-library` plugin skill exists for exactly
this job — building a design system in Figma from a codebase, including variables, component
variants, and token binding — and `figma-use` covers the mechanics of the underlying tool. Load
those and give them the bundle as the source of truth:

- `tokens.css` is the input for Figma variables. Semantic tokens map to variable collections;
  primitives are the underlying values.
- `catalog.md` decides what to build and in what order — layer by layer, `design-system` first,
  since the other layers compose it.
- `r/*.json` carries the actual props and variants for each component.

Confirm with the user before writing into a Figma file. Creating or restructuring a library is an
outward-facing, hard-to-reverse action in a document other people may share.

## Step 4. Report

Report in Japanese, as with everything this repository emits:

- Where the bundle is and how many components it covers.
- What was actually delivered to the destination, and what was deliberately left out.
- For Figma, which file was written to and what was created there.
- Anything the bundle cannot carry. It has no rendered HTML and no screenshots — stories are drawn
  by JavaScript, so producing either needs a headless browser, which this repository does not
  install. When the destination needs to *see* the components rather than read them, say so plainly
  instead of implying the bundle covered it.

## Verification

- `pnpm design:bundle` exits zero and `tmp/design-bundle/` contains `r/`, `catalog.md`, and
  `tokens.css`.
- `git status` shows nothing from `tmp/` staged.
- Nothing under `src/` changed. This skill reads the repository; it does not edit it.
