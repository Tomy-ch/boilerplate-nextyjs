# How To

「ここではこれをどうやるのが正規か」に、実際に実行できる手順で答える。

canonical はこのディレクトリの `SKILL.md`（英語）。規約の正はそちらで、この訳は参考である。

## 使うとき

- 実行したい操作があり、祝福された経路を知らない。
- 打とうとしているコマンドがあり、それが正規のものかを知りたい。
- コマンドは知っているが、前提・成功の判定・切り戻しを知らない。

## Contract

| | |
| --- | --- |
| **Owns** | 目標 → 正規手順（前提 / 成功判定 / 復旧 / 警告つき）、および所有スキルへの routing |
| **Never** | コマンドの発明 / 所有スキルの手順の再記述 / 破壊的操作の無断実行 / ツールの独断インストール / ゲートの実行 |
| **Starts when** | 実行したい操作があり、正規経路が不明なとき |
| **Stops when** | 索引を通読しても手順が無い（UNDEFINED）、候補が複数で決着しない（AMBIGUOUS）、権限超過（BLOCKED） |

## このスキルを使わない場面

- 症状、または落ちたゲート —— `repo-ops`。
- どうやるかではなく、どう動くかの説明 —— `repo-truth`。
- まだ誰も選んでいない選択肢の比較 —— `research`。
- コードの変更そのもの。

## このスキルが在る理由と、`repo-ops` でない理由

2 つは別の扉であり、統合すると両方が壊れる。

`repo-ops` は**症状駆動**である。予期しない振る舞いを、実際に誰かが踏んだ落とし穴の索引に照合し、
節が対処になる。**値打ちは「そこに在るものは全部、誰かが実際に踏んだ」こと**である。
**`repo-ops` は「手順が存在しない」と結論できない。**結論できるようにすると、その沈黙が答えと
区別できなくなる。

このスキルは**目標駆動**である。達成したいことは分かっていて、ここでのやり方が分からない。
その問いの一部を覆う逆引きは在る —— `docs/playbook.md`、`AGENTS.md` § Recommended Commands、
`.makefiles/README.md`。だがどれも自分の担当範囲しか覆わず、**手順が必要とする封筒**（何が先に
成り立っていなければならないか、成功をどう見分けるか、何が元に戻すか）を持っていない。

このスキルが形を与えられている失敗は具体的である —— **もっともらしいコマンドは、文書化された
コマンドと見分けが付かない。**`make test-unit` はまさに「在るべき」種類のターゲットで、 <!-- skill-lint-ignore -->
書かれてしまえば権威あるものとして読まれ、聞いた人はそれを実行する。そして存在しない。
**この文をこのリポジトリ自身の lint に通すために、意図的な非参照として印を付ける必要があったこと**が
まさに要点である。**正規のコマンドを出すか、何も出さないか**の 2 つしか許される結末は無い。

## 引数と門番

| 引数 | 効果 |
| --- | --- |
| `--mode=lookup`（既定） | 手順を出す。何も実行しない |
| `--mode=run` | 操作を実行する。破壊的な段は 1 つずつ個別に確認する |
| `--dry-run` | `DRY_RUN=1` の形を持つ段では、そちらを優先する |

`--mode` は利便性ではなく**安全のために在る**。無ければ「実行してほしいのか説明してほしいのか」を
言い回しから推測することになり、**「やって」と「見せて」は助詞ひとつしか違わない**。読み取りなら
その推測でよいが、`make baseline-push` では許されない。フラグが無ければ `lookup` と見なす ——
実行してほしかった人にコマンドを見せる費用は 1 ターンで、逆は誰も承認していない基準画像を送る。

**`--mode=run` はゲートを決して回さない。**`pnpm lint` / `pnpm lint:ci` / `pnpm test` / `pnpm build` /
`pnpm typecheck` と、それらを包む make ターゲットは、フラグが何であれこのスキルが実行するものから
外す —— hook と CI が所有し、判定は CI が正である（`AGENTS.md`）。コマンドは見せる。実行に 2 回
費用を払わない。

**次に、自分が正しい扉かを確かめる。**隣の扉は同じ名詞を取り、**相談の内容だけが違う**。

| 相談の内容 | 扉 |
| --- | --- |
| 壊れたもの、落ちたゲート | `repo-ops` |
| どう動くか / 規則は何か / そもそも在るか | `repo-truth` |
| まだ誰も決めていない選択 | `research` |
| 実行したい操作 | ここ |

**症状がここへ来た場合が、捕まえる値打ちのある case である。**既に壊れている系に対して手順を
組み立てると、前提が成り立たない段が出来上がる。そう言って `repo-ops` を指し、進めない。

## Step 1 —— まず所有スキルへ振る

組み立てる前に、その手順を既に所有するスキルが無いかを見る。多くは在る。

```bash
ls .claude/skills/                                  # 何が在るか
grep -l "<goal keywords>" .claude/skills/*/SKILL.md # 誰が名乗っているか
```

**目録は実行時に読む。ここに書かれた一覧を信用しない。**この本文の一覧はスキルが 1 本増えた時点で
偽になり、そもそもこの段の目的は「所有者を見つけること」であって手順を導出し直すことではない。

所有者が在るなら、**そう言って止まる。**2 か所に在る手順は乖離し、**腐るのは写しのほう**である。
目録そのものが問いなら `/tool-map` を回す。

## Step 2 —— レジストリから、関心で組み立てる

どのスキルも所有していないなら、手順は次のどれかに在る。キーワード検索ではなく**索引**を読む ——
ターゲットは「何をするか」で名付けられており、「目標がどう言い表されたか」では名付けられていない。

| レジストリ | 何を持つか | 索引 |
| --- | --- | --- |
| make ターゲット | ツール・セキュリティ走査・リリースとブランチ操作・基準画像 | [`.makefiles/README.md`](../../../.makefiles/README.md)、`make help` |
| `package.json` の scripts | アプリ側のコマンド —— dev / build / lint / typecheck / 生成 | `package.json` |
| git hook | commit / push 時に走るもの | `.lefthook.yaml` |
| CI | PR で走るものと、その環境 | [`.github/workflows/README.md`](../../../.github/workflows/README.md) |
| 初回のセットアップ | 新しい clone / 新しいリポジトリに要るもの | [`docs/get-started/setup-repository.md`](../../../docs/get-started/setup-repository.md) |
| 逆引き | 「X をやりたい」→ 置き場 | [`docs/playbook.md`](../../../docs/playbook.md) |

**アプリ側のコマンドは make ターゲットではなく `pnpm` の script である** —— `make help` には出て来ず、
「ビルドを回したい」という目標は `package.json` で解ける。**2 つのうち片方しか見ないことが、
ここで偽の UNDEFINED に至る最もよくある経路**である。

`repo-ops` の各節は、目標の問いに対しても走査する値打ちがある —— 手順に付随する既知の落とし穴は
注意 に入る。

キーワード検索は最後。索引が取りこぼしたものを拾う網である。`graphify` が索引化するのはコードと
文書であって make のグラフではないので、このスキルにとっては上のレジストリの**補完**であって
置き換えではない。

## Step 3 —— 運用の封筒を立てる

**コマンドだけでは手順ではない。**次のそれぞれが別の問いであり、それぞれに出典がある。

- **前提条件。**ツールチェーンの導入が要るか（`make install-tools`）。build 済みのアプリ、生成物、
  特定のブランチ、`gh` の認証が要るか。**ターゲットの名前ではなくレシピを読む。**
- **期待される結果。**呼び出した側は何をもって成功と分かるか —— 終了状態、変わるファイル、緑になる
  検査。**成功を見分けられない手順は、成功したことにされる。**
- **復旧。**何が元に戻すか。そもそも戻せるのか。**戻せないなら平明にそう言う。**
- **注意。**破壊的か、環境に依存するか、遅いか、共有面に触るか。

このリポジトリの性質のうち 3 つは封筒を非自明にするので、毎回確かめる値打ちがある。

- **共有面はこの checkout の外へ届く。**基準画像の置き場はリモートを持つ submodule なので、
  `make baseline-push` と `*-retake` は他のブランチが読む状態を進める。`make setup-repo` は
  リポジトリ全体の GitHub 設定を書く。**どちらもローカルではない。**聞いた人はたいてい自分の木の
  ことだけを考えている。
- **他の worktree がホストを共有している。**ポートと重い実行は checkout を跨いで衝突する。
  ここで立てたサーバは、別の窓が既に握っているポートで応答するかもしれない。
- **dry-run の慣習が在る。**いくつかのターゲットは `DRY_RUN=1` を尊重する
  （[`.makefiles/README.md`](../../../.makefiles/README.md)）。真とみなす値は `1` だけである。
  持つターゲットなら手順に入れる —— **取り消せない段を、覗ける段に変える。**

## Step 4 —— この契約で答える

常にこの形、日本語で。本当に当てはまらない欄だけ省き、**黙って落とさずそう述べる。**

````markdown
## 状態
FOUND | AMBIGUOUS | UNDEFINED | BLOCKED

## 手順
<何をする手順か、1 行>

## 出典
- `<path>` の `<target / script / 節 / job 名>`

## 前提条件
- <満たしていなければならないこと、必要な権限>

## コマンド
```bash
<正規に定義されたコマンド。存在するものだけ>
```
<UNDEFINED のときは「なし」と書き、なぜ近そうなコマンドを出さないのかを 1 行添える>

## 近いもの
- `<target / 手順>` — <ただし〜の点で目的が異なる>   ← FOUND 以外のときに書く

## 成功の判定
<どうなれば成功か>

## 復旧 / 切り戻し
<既存資料に定義されたもの。無いなら「定義なし」と書く>

## 注意
- <破壊性 / 環境差 / 共有面への影響 / 未検証の点>

## 探索範囲
<通読したレジストリ / 確認した所有スキル / 検索した glob / 回さなかった掃引とその理由>
← UNDEFINED / AMBIGUOUS のときは必須

## エスカレーション
<未定義・矛盾・権限超過のとき、誰が何を決めれば進むか>
````

4 つの状態は交換可能ではない。

| 状態 | 意味 |
| --- | --- |
| `FOUND` | 正規手順が存在し、上に再現されている |
| `AMBIGUOUS` | 候補が複数あり、どれが統べるかを出典が決めない —— 全部出す。選ばない |
| `UNDEFINED` | 所有レジストリを通読し、正規手順が存在しなかった |
| `BLOCKED` | 手順は在るが、要求された操作がここで許された範囲を超える |

`UNDEFINED` は `repo-truth` と同じ基準を負う —— 所有レジストリを**通読**すること（make ターゲットと
`pnpm` の script の**両方**）、そして前線を添えて出すこと。それに満たないなら状態は `AMBIGUOUS` か、
答えは 確認できず で、**どの索引を読み残したかを名指す**。落とす費用はゼロで、誤った `UNDEFINED` は
リポジトリについての事実として読まれる。

`UNDEFINED` のとき `コマンド` 欄は **なし** と書き、なぜ明らかに近そうなコマンドを出さないのかを
1 行添える。空欄にすると、次の読み手が自分でコマンドを補うよう促すことになり、**それはこのスキルが
防ぐために在る失敗そのもの**である（1 段ずれた形で）。代わりに入るのは**惜しかったもの** ——
`近いもの` に、**目的がどの点で違うか**とともに名指す。「手順は無い」とだけ言われた読み手は探しに行き、
最初に見つけるのは、このスキルが既に検討して却下したものである。

## Step 5 —— 実行する

`--mode=lookup` ではこの段は起きない —— **手順そのものが成果物**である。`--mode=run` では実行する。
ただしフラグが認可したのは**手順**であって、その中の破壊的な各段ではない。それらは 1 つずつ確認する。
**ゲートはフラグが何であれここでは回さない。**

破壊的なことの前に、**何を壊すかを言って待つ。**基準画像の置き場を進める、GitHub の設定を書き換える、
サンプル面を取り除く —— どれもこの checkout の外へ届き、聞いた人はたいてい自分の木のことだけを
考えている。

**自分の判断で何かをインストールしない。**ツールの不在は報告すべき所見である。このリポジトリは
たいていその能力を `make` ターゲットの後ろに既に持っており、ツールチェーンそのものは `mise` が持つ
（`make install-tools`）。

## 単独で完結する設計

このスキルは手順を渡して止まる。次に何をするかは名指す —— 手順が既知の落とし穴で失敗したなら
`repo-ops`、目標が実は知識の問いだったなら `repo-truth`、その欠落を追う値打ちがあるなら
`new-issue` —— **決めるのは user である。**

振り先のスキルを吸収もしない。**所有者へ振ることが答えの全部**であり、その所有者の手順をここへ
書き直せば、このスキルが防ぐために在る 2 つめの写しが生まれる。

## やる / やらない

- ✅ `--mode` が無ければ `lookup` と見なす。言い回しから実行の認可を推測しない。
- ✅ まず所有スキルを、実行時に読んだ目録から確かめる。在るならそこで止まる。
- ✅ 不在を結論する前に、**両方**のレジストリを読む —— make ターゲットと `pnpm` の script。
- ✅ 前提・成功の判定・復旧・注意を、それぞれ別の問いとして立てる。
- ✅ 各段がどのファイルのどのターゲット / script / 節から来たかを引く。
- ✅ 共有面への影響と `DRY_RUN=1` の有無を毎回見る。
- ✅ `UNDEFINED` は前線とともに報告する。届かないなら `AMBIGUOUS` / 確認できず へ落とす。
- ✅ `UNDEFINED` のとき `コマンド` に なし と理由を書き、`近いもの` に惜しかったものを ——
  目的がどの点で違うかとともに —— 名指す。
- ✅ 意図的に**回さなかった**掃引を、その理由とともに記録する。
- ✅ 破壊的なことの前に警告して待つ。
- ✅ 日本語で答える。
- ❌ レジストリで読んでいないコマンド・フラグ・ターゲットを発明する。
- ❌ 手順を所有するスキルの各段を書き直す。
- ❌ 実行時に読む代わりに、スキルの目録をこの本文へ列挙する。
- ❌ キーワード検索から、あるいは 2 つあるレジストリの片方だけから `UNDEFINED` を報告する。
- ❌ 食い違う出典のどちらかを選ぶ —— 両方出してエスカレーションする。
- ❌ `--mode` が何であれゲートを回す。
- ❌ 何を壊すかを言わずに破壊的なコマンドを打つ。見せるだけと言われたコマンドを実行する。
- ❌ 無いからといってツールをインストールする。

- [ ] 契約を日本語で全部出した。状態を明示した。
