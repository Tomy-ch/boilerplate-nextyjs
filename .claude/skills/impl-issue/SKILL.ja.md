# Impl Issue

issue から PR まで通す半自動のパイプライン。進行・記帳・検出を機械が持ち、判断はすべて人が持つ。
長い自動実行が黒箱にならないのは、承認済みの計画からの逸脱が、終わりにまとめてではなく**起きた
その場で表に出る**からである。

コマンドはこのファイルだけで実行を再現できるように置く。自走する詳細はポインタに留める ——
[`.makefiles/README.md`](../../../.makefiles/README.md)（ターゲットの目録）、
[`docs/playbook.md`](../../../docs/playbook.md)（置き場と画面の順序）、
[`docs/rules.md`](../../../docs/rules.md)（実装規約）、そして `AGENTS.md` の *Where You May Stop*。

## いつ使うか

- issue の URL / 番号を渡され、merge 済みの PR まで持っていってほしいとき。
- 判断点で止まった実行の再開を頼まれたとき。

## 本スキルを使わない場面

- **issue が背後に無い変更** —— `commit` のあと `submit-pr` を直接使う。
- **既にある差分のレビュー** —— `impl-review` / `test-review` / `comment-sweep`。3 本は `AGENTS.md` の
  Review Phase Protocol の下で対等であり、それぞれ独立に依頼される。
- **スキルの作成・改訂** —— `manage-skill`。
- **issue を立てること自体** —— `new-issue`。本スキルは既に在る issue から始まる。

## Contract

| | |
| --- | --- |
| **持つもの** | issue → merged PR の進行、承認済み計画と実物の突き合わせ、人間判断が要る瞬間の機械的検出 |
| **しないこと** | 未決の設計を独自に補完する / 実装判断そのもの（委譲先が持つ） |
| **始まる契機** | 採択済みの issue が提示されたとき |
| **止まる場所** | 下表の 5 箇所だけ。それ以外では停止せず、判断は run record と PR へ記録する |

## 停止 —— 完全な一覧

このパイプラインがどこで止まるかは仕様であって判断ではない。ここで止まり、他では止まらない。

| # | どこ | 何が決まるか |
| --- | --- | --- |
| 1 | Step 0 | 6 つのモード。他の何よりも先に、連続する 2 回の呼び出しで |
| 2 | Step 3 | 書かれた計画の承認 |
| 3 | Step 4 | 行が halt と書いてある trip-wire |
| 4 | Step 7 | レビュー 3 本のどれを回すか。各々に見積もりを添えて |
| 5 | Step 8 | ランタイム検証が落ちたとき、および merge そのもの |

`AGENTS.md` の *Where You May Stop* はこの一覧の上位に在り続ける —— あちらの停止点と trip wire は
ここで上書きされない。上の行は、**このパイプラインが追加で**待つ場所である。

停止点に見えて停止点ではない瞬間が 3 つある。いずれも、一覧に無い停止が忍び込む場所である。

- **段の切れ目。** Step 3 の承認は Step 4〜9 を覆う。計画が実行の全体を数え上げており、承認されたのは
  それだからである。段が終わることは出来事ではない —— 継ぎ目も同じ。
- **サブエージェントの完了通知。** レビューや監査は展開する。報告が届くのは作業が**再開する**場所で
  あって、止まる場所ではない。
- **Step 0 で決めたモード。** それは使用済みの権限である。レビューモードが既に許可した修正を確認し
  直すのは、同じことを 2 度承認させることである。

1 つずつ問えば、停止はいつでも安く見え、その費用は散らばったままになる。だから上の一覧は助言では
なく閉じている。

## 本スキルがしないこと

実装判断を一切持たない。どの設計を採るか、レビュアーが正しいか、所見が issue に値するかを決めない。
それらは人へ回し、答えを記録する。

| 作業 | 所有者 |
| --- | --- |
| コミットの分割と実行 | `commit` |
| push と PR の作成・更新 | `submit-pr` |
| base の取り込みと衝突 | `resolve-merge` |
| 新しい画面・feature スライス | `new-feature` —— 実装の段を丸ごと渡す |
| 変更そのもののレビュー | `impl-review` |
| テストのレビュー | `test-review` |
| コメント在庫のレビュー | `comment-sweep` |
| 実装そのもの | 承認された計画に従うあなた |

## AI Modification Scope

`AGENTS.md` は既定で AI の編集を `src/` / `public/` / `docs/adr/BACKLOG.md` に閉じる。v1.0.0 未満では
*Temporary Operating Rules* が保護パスの一覧を既に外しており、残るのは「CI・道具・文書についての
issue は、既定の範囲が名指していない面へ届く」という点である。**本スキルの起動が、その残りを緩める
明示の指示である。**本スキルは issue 非依存であり、面を決めるのは issue だからである。

緩和には境界があり、その境界は計画である。

- Step 3 の計画の **Files to touch** が許可された面である。`src/` の外のパスは、編集より**先に**
  そこへ、glob で含意するのではなく明示的に名指して現れなければならない。
- 計画を提示するときにそう言う。利用者が差分で発見するのではなく、承知のうえで承認できるように。
- 計画に無いパスへ届いた時点で、flow モードに関わらず halt する（trip-wire 1′、Step 4）。

本スキルの実行中も硬く保護されるもの（issue が何を求めても触らない）:

- `AGENTS.md` / `CLAUDE.md` / `LICENSE`
- `.claude/settings.json` の `permissions.deny` に載るもの
- 生成物 —— `**/gen/**` と生成バナーを持つもの。生成器を通して作り直すのはよく、手で編集するのは
  不可（`AGENTS.md` の trip wire 3）
- `baseline/images` —— gitlink が動くのは撮り直しの経路だけである（`docs/design/vrt.md`）

## Step 0 —— 6 つのモードを決める（`AskUserQuestion` を 2 回連続）

他の何よりも先に、2 回続けて問う ——**どこまで行き、所見をどう扱うか**、それから**自分で何を決めて
よく、計画にいくら掛けるか**。1 回ではなく 2 回なのは、1 回の呼び出しが 4 問で頭打ちだからである。
7 つめのモードが要るときも、落とすのではなくもう一度割る。**これで停止点は 1 つである。**利用者は
2 つに続けて答え、その間に実行は何もしない。

既定には印を付ける。利用者の選択が常に勝つ。

### 1 回目 —— どこまで行き、所見をどう扱うか

**scope モード** —— この実行がどこまで行くか。**最初に問う。**下のすべてのモードを境界づけており、
PR で終わる実行は、他のモードが統べる段へそもそも届かない。

| モード | 終わる場所 | 届かないもの |
| --- | --- | --- |
| `merge` *(既定)* | Step 9 —— merge し、申し送り、issue を閉じる | —— |
| `pr` | Step 8 の PR まで。CI は回したまま | 回収・ランタイム検証・merge・close |
| `commit` | Step 5 まで。作業は手元にコミット済み | push から先すべて |

**トリガ語がこれを決めることがあり、「pr作って」は `pr` である。**利用者が渡した言葉が既に終点を
名指しているなら、**それが答え**であり、選択肢は開いて問うのではなく確認して通す。

**それぞれの終わり方が何を残したかを、締めの報告で述べる。** `pr` で止まった実行は、リクエストの
経路を確かめておらず、回収も何もしていない。どちらも PR からは見えない。`pr` のときは
**回収を未了として PR 本文に名指す** —— Step 8 が回収を CI 緑後に置いているのは、そこが最後の
機会だからであり、そこより手前で終わる scope は負債を消すのではなく、merge する人へ移している。

**レビューモード** —— レビューの所見をどう扱うか。

| モード | 確定した所見 | それ以外 |
| --- | --- | --- |
| `all` | 変更が大きくても適用する | —— |
| `harmful` *(既定)* | 変更の範囲内で明らかに有害なものだけ適用する | issue モードへ回す |
| `issues` | 何も適用しない | issue モードへ回す |

**issue モード** —— 変更の外にある所見をどうするか。

| モード | 振る舞い |
| --- | --- |
| `fix-here` *(既定)* | この実行の中で直す。`docs/rules.md`「作業とエージェント」がこれをリポジトリの既定にしている —— 範囲外であることは起票の理由にならない |
| `search` | 先に既存 issue を探し、重複ならそちらへコメントする |
| `file` | 探さずに起票する |

**`fix-here` が既定なのは、逆が複利で効くからである。**所見を 3 件起票した 1 回の実行は、未完了の
作業を 3 つ生む。そして拾う人は、再現をゼロから組み直すところから始める。起票が正しいのは、
**別の判断か別の合意が要るもの**だけである —— ADR の新設、機構の採否、他リポジトリ側の作業。
`issues` × `file` はどの組み合わせよりも多くの issue を生むので、実行の前に件数を見せて確認する。

**flow モード** —— trip-wire が何をするか。

| モード | 振る舞い |
| --- | --- |
| `record-on-tripwire` *(既定)* | 判断を記録して続行し、記録した全部を最後に 1 つの PR コメントで表に出す |
| `halt-on-tripwire` | その trip-wire で止まって問う |

**どちらのモードも、Step 4 で halt と書かれた行には届かない。**それらは `AGENTS.md` が無条件で人の
関所に置いている判断である。

### 2 回目 —— 何を自分で決めてよく、計画にいくら掛けるか

**derive モード** —— 計画が決めなかった設計の問いをどうするか。

| モード | 振る舞い |
| --- | --- |
| `ask` *(既定)* | 表に出して待つ。その問いで実行が止まる |
| `derive` | まず ADR・`docs/rules.md`・層の README を読み、それらが開いたままにしている分は、デファクトスタンダード（RFC / 仕様 / プラットフォーム自身の定義）から決めて、導出を記録する |

**`derive` は好みを許可しない。** [0010](../../../docs/adr/0010-standards-and-non-lockin.md) が権威をちょうど 2 つ —— デファクト
スタンダードと、このリポジトリのアーキテクチャが導出する形 —— と名指しており、このモードが委譲する
のはその 2 つだけである。どちらでも答えられない問いは導出できないので、モードに関わらず人へ戻る。
導出はすべて、依拠した一節とともに run record へ書く。読み手が作業を繰り返さずに反対できるように。

このモードが在るのは、`docs/rules.md` が既に逆の失敗を禁じているからである ——
**導出で決まる判断を、保留として issue へ逃がさない。** `ask` が安全な既定で、`derive` は利用者が
その場に居られないときに選ぶものである。

**計画モード** —— 計画の段にいくら掛けるか。Step 3 は 3 つの stage を持ち、これがどれを回すかを決める。
**どのモードも Step 3 の不変条件（計画が、実装者のものではないモデルに見られる）を満たす。**

| モード | stage | 費用 |
| --- | --- | --- |
| `full` *(既定)* | 3a + 3b + 3c | 3 パス —— 起草者の分に加え、上位帯で 2 回 |
| `draft-review` | 3b + 3c | 2 パス。枠組みの段を省く |
| `single` | 3b のみ。実装者のものではないモデルが起草する | 1 パス |

**問うときは、何をするかだけでなく、いくら掛かるかを言う。**これは issue の大きさに関わらず毎回
支払われる唯一のモードなので、値段を言わない既定は事故で支払われる既定である。1 行の文書修正と層を
またぐ機能は、同じ計画の予算に値しない。層をまたぐ・契約を変える・設計判断を名指す issue なら `full`、
形が既に決まっていて細部だけなら `draft-review`、計画が形式に過ぎないなら `single` を勧め、
**どれを勧めているかとその理由**を言う。

## run record —— 「判断を記録する」の書き込み先

このパイプラインは記録するよう言われている —— 通り過ぎた trip-wire、回さなかったゲート、退けた所見、
下した導出。Step 9 はそれら全部を最後の PR コメントへ負っている。

**それらはファイルへ、起きたその場で追記される** —— 計画の隣、追跡外の `tmp/` の下、issue の名前で。
会話の中ではない。

長い実行は自分の文脈より長生きする。覚えているだけのものは途中のどこかで要約されて消え、その失敗は
両方向に無言である —— Step 9 は変わらず自信のある PR コメントを書き、そこには項目が消えたとは書かれ
ない。ファイルは実行を再開可能にするものでもある。

| 書く時点 | 項目 |
| --- | --- |
| Step 0 | 決まった 6 つのモード |
| Step 3 | 計画ファイルのパスと、3a / 3c が回ったか |
| Step 4 | 発火した trip-wire すべて —— 番号・引き金・取った判断 |
| Step 4 | `derive` の下で下した導出すべてと、依拠した一節 |
| Step 6 | 回らなかったゲートすべてと、その理由 |
| Step 7 | 退けた所見、提案と違う直し方をした所見と、その理由 |
| Step 8 | ランタイム検証が覆った範囲と、覆わなかった範囲 |

出来事が起きたときに書く。最後にまとめて書かない —— まとめは、まさに compaction が食うものである。

## 継ぎ目 —— compaction が安い場所

2 つの地点は、ほとんど何も先へ運ばない。重要なものが既にディスクに在るからである。

| 継ぎ目 | 下流が要るもの全部 | それが既に在る場所 |
| --- | --- | --- |
| Step 5 の後（実装を突き合わせた後） | 承認済みの計画・差分・ここまでの判断 | 計画ファイル・`git diff`・run record |
| PR を開いた後（Step 8、CI が回っている間） | PR・ブランチ・ここまでの判断 | GitHub・`git`・run record |

どちらでも: **先に run record を書き、compaction を勧め、続ける。** PR の継ぎ目では問う ——
その先に残るのは、この実行で最も重い読み物だからである。例外は、常設の全権委任の下で利用者が
その場に居ない実行で、そこでは告げて続ける。答える人が居ない問いは、自分で終わらせろと言われた
その瞬間に実行を止める。

**どちらの継ぎ目も停止点ではなく、一覧は 5 つのままである。** compaction は作業について何も決めない。

## Step 1 —— 立ち上げ

```bash
printf '\033]0;%s\007' "<issue-number>-<slug>"   # 並行する実行を見分けられるように窓へ名前を付ける
gh issue view <n> --json number,title,body,labels,state,comments
```

**何かを書く前に、issue を実際の base と突き合わせる。** issue の本文は、誰かが書いた時点のリポジトリの
スナップショットである。行番号・「X はまだ無い」・「Y に呼び出し側が無い」は古くなる。事実の主張を
1 つずつ、これから枝を切る base に当てて確かめる —— これは `docs/rules.md` の
「『まだ直っていない』『未着手』『存在しない』と言う直前に、測り直す」を、最も安い瞬間に適用したもの
である。

そのうえで、ブランチ名・base のコミット・そして何より**上で見つけた食い違いすべて**を記録する
立ち上げコメントを投げる。

```bash
gh issue comment <n> --body-file <file>
```

## Step 2 —— 作業環境を確保する

コードに触れる前に行う。共有の checkout に何も落ちないようにするためである。

**利用者が言っていなければ、worktree の置き場を問う。**このリポジトリは置き場を宣言しておらず、
答えはリポジトリではなくマシンの性質である。だから既存の worktree（`git worktree list`）から導き、
勝手に決めない。指示に「wt 上で」や明示のパスが既に含まれていれば、**それが答え**であり、この問いは
省く。

### 初期構築 —— worktree がまだ無い

```bash
# 1. 動いているリリースラインを origin の実状態から解決する。
BASE=$(make -s base-branch)
test -n "$BASE" || { echo "ベースブランチを解決できませんでした"; exit 1; }

# 2. 古いローカル参照ではなく、いまの origin から枝を切る。
git fetch origin "$BASE"
git worktree add -b feature/<n>-<slug> <worktree-path> "origin/$BASE"

# 3. node_modules は worktree 間で共有されない。
cd <worktree-path> && pnpm install --frozen-lockfile
```

`make base-branch` は `origin` の実状態を読む。他を使わないこと —— ローカルの
`refs/remotes/origin/HEAD` は clone 時に固定され `git fetch` では更新されず、GitHub の既定ブランチは
前のリリースラインを指したままで、ハーネス自身の "Main branch" 行も同じ古い symref を報告する。
3 つとも警告なしに答えるので、1 世代古い base から切った枝は、皆が在ると思っているファイルが無いと
判るまで正しく見える。

利用者の指示が解決結果と違うリリース版を名指していたら、枝を切る前に問う —— 意図的な backport 先は、
解決器が知りようのない唯一の場合である。

ブランチの作成は `git switch -c` / `git worktree add -b` で行い、`git checkout` はブランチ操作に使わない
（`docs/rules.md`「作業とエージェント」）。

### 既存の worktree へ再開する

構築は既に済んでいる。観測して見つけたものを報告し、どれも回し直さない。

**何よりも先に run record を読む。** worktree を見て分かるのは作業がどこまで進んだかであって、それに
ついて何が決まったかではない —— 決まったモード・発火した trip-wire・回さなかったゲートはあのファイル
にしか無い。

```bash
git rev-parse --show-toplevel
test -d node_modules && echo 'node_modules: present' || echo 'node_modules: absent'
git status --short
```

`node_modules` が無いことは報告すべき事実である。`pnpm install --frozen-lockfile` は、build か
サーバが実際に迫ったときに回す。再開の儀式として回さない。

## Step 3 —— 計画し、待つ

**不変条件: 計画は、実装者のものではないモデルに見られる。**下の 3 stage はそれを満たす既定の 1 つ
であって規則そのものではない —— 規則はここに書かれたモデル名ではなく、セッション自身のモデルから
読む。

後段のどのゲートも計画を開き直さない。`impl-review` / `test-review` / `comment-sweep` はどれも完成した
変更を主題にするので、**その計画がそもそも issue を解くのか**はここで確かめるか、どこでも確かめられ
ないかのどちらかである。

| stage | 走らせる先 | 産物 | 回るモード |
| --- | --- | --- | --- |
| 3a 枠組み | 上位に近い帯で、実装者のものではない系統 | 計画が答えるべき問い。それだけ | `full` |
| 3b 調査と起草 | 使える最も強い帯。サブエージェントとして | 計画ファイル | 全モード |
| 3c 計画レビュー | 3a と同じモデル。`single` では不変条件を 3b が担う | 所見。計画ファイルへ独立した節として追記 | `full`・`draft-review` |

**各 stage のモデルは実行時に解決する。このファイルから読まない。**スキルへ書いたモデル名は、変わり
続ける名簿のスナップショットである。**軽い調査のために選んだモデルで起草しない** ——
`docs/rules.md` は「その出力がリポジトリに入るか」で線を引いており、計画は入る。

### 3a —— 枠組み

issue の本文・Step 1 の食い違い・既に読んだパスを渡す。

**返すのは答えではなく開いた問いである。**この時点でリポジトリをほとんど読んでいないので、断言する
ものは何であれ一般論であり、一般論を強い起草者へ渡すと視野は広がらずに固定される。計画案・推奨・
方向のどれかを返してきたら、突き返す。

### 3b —— 調査と起草

サブエージェントとして走らせる。統括側が溜め込んだ枠組みを一切持たない窓で調査が起きるようにする
ためである。issue・Step 1 の訂正・既に読んだパス・3a の問いを渡す。あなたの要約を信じずに確かめろと
言う。

**現在の挙動を辿っていないコードに issue が触るなら、先に `code-explorer` を出す** —— 公式
`feature-dev` プラグインの read-only エージェントで、入口から出力まで呼び出しの鎖を辿り、読む価値の
あるファイルを返す。観点を変えて 2〜3 本を 1 メッセージで並列に出し、名指されたものを読んでから
3b の入力にする。これが答えるのは「いまどう動いているか」であって、3b の仕事ではない ——
3b は何を変えるかを決める。**このプラグインから他は何も使わない** ——
ADR [0155](../../../docs/adr/0155-claude-skills-development.md) を見よ。

**答えを所有する文書を指す**のであって、内容を書き写さない —— 置き場は `docs/playbook.md` の逆引き、
層が何を import してよいかは ADR [0021](../../../docs/adr/0021-frontend-responsibility.md) の依存
マトリクス、その層ごとの実体は層 `README.md` の frontmatter、変更が満たすべき規約は `docs/rules.md`。
3a の問い**すべて**に答える義務がある。

計画は会話のメッセージではなく書かれた成果物である。Step 5 が機械的に突き合わせるからである。追跡外の
`tmp/` の下へ書く。次を含むこと:

| 節 | なぜ必須か |
| --- | --- |
| Files to touch | Step 5 が `git diff --name-only` と突き合わせる。許可された面でもある |
| 段ごとの成果物 | 途中まで進んだ実行を再開・引き継ぎできるようにする |
| 採った案**と、退けた案とその理由** | 退けた案が後から採られたとき trip-wire 2 が鳴る |
| ゲート表 | ランタイム検証が要るかを計画の時点で固定し、黙って落とせないようにする |

**issue が新しい画面なら、計画にそう書き、Step 4〜7 を `new-feature` へ渡す。**あちらが画面の順序
（ディレクション → story → レビュー → 分離 → 仕様書 → テスト）を持ち、`docs/playbook.md` から実行時に
読む。その順序をここで導き直さない。

### 3c —— 計画レビュー

要否は導出であって仮定ではない。3b が実装者自身のモデルで回ったなら、計画はまだ他のどのモデルにも
見られていないので **3c は必須**である。3b が既に別の系統で回ったなら不変条件はその時点で満たされ、
3c は任意である。

所見は計画ファイルへ独立した節として追記し、**計画の中へ畳まず、計画の隣に並べて提示する** ——
黙って計画を書き換えるレビュアーは、利用者が承認を求められるまさにその瞬間に、食い違いを隠す。

### そして待つ

計画を提示し、**承認を待つ。その前に実装しない。**この承認が Step 4〜9 を覆う。

## Step 4 —— 5 つの trip-wire を見ながら実装する

承認された計画に従う。引き金は意図して機械的である —— 判断が重大だったと**気づく**ことをあなたに
頼るのが、まさに逸脱が報告されない仕組みだからである。

| # | trip-wire | 既定 | なぜ |
| --- | --- | --- | --- |
| 1 | 計画に無いファイルに触る。`src/` の**内側** | 記録 | 範囲は広がったが、既定の変更範囲が既に許している面の中である |
| 1′ | 同じことを、その**外側**で（`.github/` / `scripts/` / `.makefiles/` / `docs/` / ルートの設定） | **halt** | 計画が許可された面であり、広げるのは利用者の判断である |
| 2 | 計画が退けた案、または第 3 の案を採る | **halt** | 退けたことには理由があり、黙って覆すとその理由ごと捨てる |
| 3 | アーキテクチャ規則に根がある失敗（`eslint-plugin-boundaries` / `pnpm check:architecture` / 層 README の `imports-allowed`） | **halt** | これは書式ではない —— 満たすことは設計を変えることである |
| 4 | レビュアーの所見を退ける、または提案と違う直し方をする | **halt** | 所見が正しくても提案された直し方が有害なことはあり、その判断はあなた 1 人のものではない |
| 5 | ゲートを飛ばす | 記録 | Step 6 が既に PR へ書くことを求めている |

**halt の行は flow モードに関わらず halt する。**発火したら、状況と自分の推奨を添えて提示する。
`halt-on-tripwire` は記録の行にも同じ扱いを広げる。

`docs/rules.md` の 2 つがこの段の全体を縛る。これらは逸脱についてのものではないので trip-wire では
ない。

- **利用者に見えている要素を減らす判断は、人のものである。**描画の木はあなたのものだが、列・操作・
  状態表示・説明文を落とすことは違う。これは `AGENTS.md` にも停止点として載っている。
- **見つけたものは、その場で直す** —— issue モード `fix-here` の下では、触れた部品に見つけた不具合は、
  再発を捕まえる検査とともにこの実行の中で直す。起票しない。

## Step 5 —— 計画を実物と突き合わせる

ゲートより先に回す。突き合わせるもの:

- `git diff --name-only` と計画のファイル一覧 —— 増えたものと、触られなかった項目を報告する。
- 実際に採った案と、計画の採用 / 棄却の一覧。
- ゲート表の項目と、実際に回したもの。

差を提示する。長い実行は正当な理由で逸れる。問題なのは、利用者が見なかった逸脱である。何も逸れて
いなければ 1 行でそう言って先へ進む。

## Step 6 —— ゲートは hook と CI のものである

**ゲートを先回りして回さない。** `docs/playbook.md` が権威を hook と CI に置いている。
同じ検査を手で回しても結果はより正しくならず、混んだ機械では二重実行そのものが、変更と無関係な失敗の
源になる。commit し、push し、判定を読む。

この段が負うのは実行ではなく**申告**である —— **どのゲートを CI へ委ねたかを PR に書く。**沈黙は
「検証済み」と読まれる。いまどのゲートが手元で走るかは `make load-status` が出す。その判断を
`--no-verify` で先取りしない。

いま書き換えた 1 ファイルを回すのは構わない。全量を掃くのは違う。

ランタイム検証は意図的にここに無い。PR が在る後（Step 8）に属する。そうすれば CI がその後ろではなく
並行して回る。

## Step 7 —— レビュー

完成した変更は 3 つの主題を持ち、それぞれを 1 つのスキルが所有する —— `impl-review`（変更）・
`test-review`（テスト）・`comment-sweep`（触れたファイルのコメント在庫）。3 本は対等であり、どれも
他を呼ばないので、この段が黙って 1 本を選んではならない。

`AGENTS.md` の Review Phase Protocol に従う ——
**この実行が既に持っている文脈から、各スキルの見返りを見積もる**（どの層に触れたか、テストや
コメントがそもそも動いたか）。そのうえで**スキルごとに**、見積もりとその理由を述べて可否を問い、
承認された分を回す。「三つとも回しますか」は問いではない。費用を値付けせずに突き返している。

この段は見積もりが最も安い場所である。計画・差分・Step 5 の突き合わせが既に手元に在る。

所見は Step 0 のレビューモードに従って扱う。自動適用は機械で確かめられるものに限る。
**設計を変える修正は、どのモードでも常に判断点である** —— `all` が許可するのは大きな書き換えであって、
レビューされていない書き換えではない。

**反映の回は新しい範囲である。** `AGENTS.md` の *The response to a review is itself unreviewed* が
所見を反映した後を統べる —— 範囲を `<レビューの最後のコミット>...HEAD` として宣言し、反映が実際に
触れた主題のスキルだけを回し直す。

## Step 8 —— PR、回収、ランタイム検証、そして merge

**この段のどこまでを回すかは scope モードが決める。** `commit` ではこの段そのものを回さない ——
Step 7 で止め、手元にコミット済みで push していないことを述べて報告する。`pr` では PR を開いた
ところで止まる。最後まで届くのは `merge` だけである。

先に `submit-pr` で PR を開く。この段の残りを回している間に CI が始まるようにするためである。

### 回収 —— merge の前、CI が緑になった後

**直したものの一般形を、サンプル破棄後も残る文書へ集める**（`docs/rules.md`・層の README・その領域を
所有する ADR・`docs/testing-conventions.md`）。直した事実は破棄されうるコードにしか無く、破棄すると
結論ごと消える。

時点は動かせない —— **CI 緑後・merge 前。**修正は 3 つの瞬間から来る（実装中・レビュー・CI）ので、
PR を出す前に回収すると 3 つめを取り逃がす。列挙は `git log --oneline <base>..HEAD` から機械的に取り、
記憶から作らない。

文書が膨らまないようにする 2 つのフィルタは `docs/rules.md`「作業とエージェント」が持ち、落としたものを
黙って捨てずに述べることを求めている。

### ランタイム検証 —— リクエスト時の seam が動いたときの merge の関所

**関所は `impl-review` Step 4-2 と同じもの**である —— Route Handler（`src/app/**/route.ts`）・
Server Action・`src/proxy.ts`・応答ヘッダの設定・レイアウトの外枠 / Provider の組み立てのいずれかに
触れたか。どれも動いていなければそう述べて段を飛ばす。**する理由の無かった検査を、したことにしない**
（ADR [0157](../../../docs/adr/0157-inspection-declaration-discipline.md)）。

関所が開いているとき、これは `pnpm build` と `pnpm start` の実行であり、lint でもテストでもないが
同じ機械を食う。**始める前にそう言い**、並行する worktree が握っていないポートを選ぶ。

```bash
APP_ENV=local pnpm build
APP_ENV=local pnpm start --port <3000+N>
curl -i http://localhost:<port>/<path>
```

`APP_ENV` は明示が要る —— 未設定は `local` として扱われないので、同梱の開発用の秘密値が弾かれて
サーバが起動時に落ちる。正常系・上流の生の status が漏れないこと・変更が出すべきセキュリティ
ヘッダ・そして変更が守るパスについては、資格情報を付けない要求が実際に拒まれることを確かめる。

**このリポジトリにバックエンドは無い。**それ無しには到達できないもの（本物の成功応答、主体をまたぐ
認可）は**到達不能として述べる**。模擬せず、通ったことにしない。

**緑の CI は代わりにならない** —— モックしたテストが届かない seam については。ランタイム検証が
そもそも回せないときの誠実な選択肢は 2 つで、3 つめは無い。まだ merge しないか、同じ経路を駆動する
結合テストを足してそれで merge するか。どちらを取ったかを明言する。

### merge

前景の sleep ループでセッションを焼かずに CI を待つ:

```bash
until [ "$(gh pr checks <n> --json bucket --jq '[.[]|select(.bucket=="pending")]|length')" = "0" ]; do sleep 30; done
gh pr checks <n>
```

**base が動いていたら、merge の前に取り込むかを決める。**可否は `docs/rules.md` が持つ判断である ——
「base の変更が自分の変更を意味的に壊せるか」であって、ファイルが重なるかではない。merge そのものと
衝突したパスは `resolve-merge` が所有する。

そして merge する。

```sh
gh pr merge <n> --merge
```

## Step 9 —— 締める

**届くのは scope モード `merge` のときだけである。** `pr` / `commit` では、代わりに報告で締める ——
何を作り、どこで止まり、その終わり方が何を残したか。とくに上の回収と、ランタイム検証である。

issue は**手で閉じる** —— 自動で閉じるキーワードは、PR の宛先が既定ブランチではなくリリース
ブランチのときは発火しない。

```bash
gh issue comment <n> --body-file <handover> && gh issue close <n>
```

申し送りコメントは、完了条件に沿って **どの条件をどう満たしたか / 指示と違えた判断とその理由 /
別 issue が妥当な積み残し** を覆う。

**世界の状態について何かを主張する直前に、もう一度 fetch する。**ここではリリースラインが分単位で
動くので、セッションの頭のスナップショットから書いた申し送りは、既に真でなくなったことを主張する。

**片付けるのは worktree であって、ブランチではない。** `git worktree remove` はローカルブランチを
残し、それが正しい終わりの状態である。リモート側は merge 時に GitHub が消す。`git branch -d` を
打たない。

最後に、コミットメッセージにも PR 本文にも現れていない判断を PR コメントへ記録する。
**run record を読んで順に降りる** —— halt せずに記録した trip-wire すべてと、`derive` の下で下した
導出すべてがここへ着地し、それらが全部そろって残っている場所はあのファイルだけである。

## 二重に問わない委譲

サブスキルは自分の問いを持つ。本スキルが既に利用者と決めているので、答えを payload として渡し、
サブスキル側の関所を飛ばさせる。

| サブスキル | 渡すもの | 抑止されるもの |
| --- | --- | --- |
| `commit` | 既に提示したグルーピング | グルーピング承認の問い |
| `submit-pr` | レビューが既に回ったこと・push の判断 | レビューの促しと push の確認 |
| `new-feature` | 承認済みの計画と主題 | Step 0 の主題確認 |
| `impl-review` | 範囲・レビュアーのモデル | Step 0 |
| `test-review` | 範囲・レビュアーのモデル | 範囲の問い |
| `comment-sweep` | 範囲**と適用モード** | 範囲と適用モードの問い |
| `resolve-merge` | base | base の解決 |

**どの行も必須である。**1 つ欠けると、本スキルが既に決めた関所が復活する。項目ごとに確認するのが
既定のサブスキル —— `comment-sweep` が要注意 —— は、適用モードが届かなければまさにそれをする。

## する / しない

- ✅ scope モードを最初に問い、それに従う。早く終わった実行が何を残したかを、覆ったかのように書かず報告する。
- ✅ コードに触れる前に worktree を確保し、置き場を利用者が言っていなければ問う。
- ✅ issue の主張を実際の base に当てて確かめ、食い違いを立ち上げコメントへ入れる。
- ✅ 実装の前に計画の承認を取り、Step 5 が突き合わせられるようにファイルとして残す。
- ✅ 計画を実装者のものではないモデルへ通し、その所見を計画へ畳まず隣に並べて提示する。
- ✅ 5 つの trip-wire を、気づくべきものではなく機械的な引き金として扱う。
- ✅ 一覧に在る 5 箇所でだけ止まり、他の判断は起きたその場で run record へ追記する。
- ✅ CI が緑になった後・merge の前に、一般形を残る文書へ回収する。
- ✅ どのゲートを CI へ委ねたか、ランタイム検証がどの経路へ届かなかったかを明言する。
- ✅ 見つけたものは直し、別の判断が要るものだけを起票する。
- ✅ サブスキルには決まった答えを渡す。適用モードを含めて。
- ❌ 自分の緑を作るためにゲートを先回りして回さない。
- ❌ リクエスト時の seam が動いたまま、一度も踏まずに merge しない。緑の CI を踏んだことにしない。
- ❌ 設計を変える修正を、どのモードでも自動適用しない。
- ❌ 利用者に見えている要素を、先に問わずに減らさない。
- ❌ `derive` の下で設計の問いを好みから決めない —— 標準かアーキテクチャだけである。
- ❌ 段の切れ目で承認を求めない。サブエージェントの完了を切れ目として扱わない。
- ❌ どのレビュースキルを回すかを自分で選ばない。1 本が他を連鎖させる前提で回さない。
- ❌ 片付けでローカルブランチを消さない。
- ❌ 実行の判断を文脈だけで持ち運ばない。Step 9 のコメントを記憶から組み立てない。
