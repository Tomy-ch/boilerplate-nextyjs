# New Issue

変更の可能性についての問いを、**後から信用できる** issue へ変える —— あるいは「issue にする必要は無い」
という結論へ。

**下書きを書くのは易しいほう。**このスキルが在るのはその前の段のためである ——
**これから断定しようとしていることが、いまのコードについて本当に真か**を確かめ、
**穴をもっともらしい推測で埋めることを拒む。**issue は数か月後に、それに基づいて動く人が読む。
**一度も確かめられていない自信のある一文は、issue が無いより高くつく。**

canonical はこのディレクトリの `SKILL.md`（英語）。規約の正はそちらで、この訳は参考である。

## 使うとき

- できるかどうかを user が思案している、あるいは通りすがりに変更を提案した。
- user が「これは誤りだと思う」振る舞いを報告した。
- user が issue を作ってほしいと明示した。

## Contract

| | |
| --- | --- |
| **Owns** | 前提の裏取り、falsifiable な本文の作成、「これは issue か」の関門、起票 |
| **Never** | 実行していない振る舞いを断定する / 測っていないコストを比較に出す / 未決の選択を決着として書く / 素の外部リンクを自分の判断で貼る |
| **Starts when** | 変更の可能性についての問いがあり、追跡する値打ちがありそうなとき |
| **Stops when** | 前提が反証された、既存 issue で足りる、その場で直せる大きさだった |

## このスキルを使わない場面

- 差分のレビュー —— `impl-review` / `test-review` / `comment-sweep`。
- まだ誰も選んでいない選択肢の比較 —— まず `research`。その推奨は決定ではない。
- ADR を書くこと。

## このスキルが在る理由

issue の事実の主張が誤っているのは、たいてい 1 つの理由による ——
**書いた人が、自分が考えていた層の外を見ていない。**ステータスコード、値が実際に越える境界、
ある案のコスト —— どれも静的に確かめられ、**どれも書いた人が一度も開かなかった場所で決まっている。**
**「関係する層を読む」ことは、経路を辿ることと同じではない。**

## Step 0 —— 2 つを確認する（`AskUserQuestion` 1 回）

**裏取りの深さ** —— 振る舞いの主張を、起票前にどこまで証明するか。

| モード | 振る舞い |
| --- | --- |
| `static`（既定） | コードを読むだけ。振る舞いの主張はすべて本文で未確認と印を付ける |
| `observed` | アプリを立てて振る舞いを観測してから起票する。**先に聞く** —— ここではアプリを立てること自体が別の判断であり、このスキルが独断で踏む段ではない |

**出力** —— この実行が起票で終わるか、下書きの引き渡しで終わるか。

| モード | 振る舞い |
| --- | --- |
| `file`（既定） | 本文を提示し、承認後に起票する |
| `draft` | 本文と分析を作る。起票しない |

**既存 issue の検索はモードではない。**常に行う —— 安く、飛ばすことが重複起票の経路そのものである。

## Step 1 —— 問いを捉える

user が実際に聞いていることを 1〜2 文で言い直し、確認する。通りすがりの問い（「これ直せる？」）は
たいてい**問題が*どこに*あるかについての、言われていない前提**を抱えている。
**その前提を早く名指すことが、Step 2 がそれを反証できるようにする。**

何がこれを引き起こしたかを記録する —— user が踏んだ症状、レビューの所見、コードの読解。
**出所が、どこまでが既に証拠でどこからが推測かを決める。**

## Step 2 —— 経路を端から端まで辿る

**このスキルが在る理由そのものの段である。問いが指している層だけを読まない。**

振る舞いについての問いなら、入口から外側へ要求を追う。

```txt
proxy → route segment / route handler / Server Action → features → adapters → バックエンドの契約
```

**`src/proxy.ts` は最も飛ばされやすく、最もしばしば決定的な区間である。**議論している層が走るより前に
要求を拒んだり書き換えたりでき、しかもその `matcher` が**そもそもどの経路を見るか**を決めている。

この層に固有の境界が 2 つあり、見た目より多くの主張を決めている。

- **描画の境界。**問題のコードがサーバで走るのかブラウザへ届くのかで、触れるものも、それについての
  主張の意味も変わる。**`"use client"` は束の境界であって「クライアントで描かれる」という指示ではない** ——
  [`docs/design/rendering.md`](../../../docs/design/rendering.md) が正であり、ここを取り違えた主張は
  **もっともらしく読める形で**誤っている。
- **import の行列。**あるカーネルが何へ届いてよいかは [`architecture.ts`](../../../architecture.ts) が
  決めており、**たまたま今日通ることではない。**例から規則を推測せず、そのファイルを読む。

構造についての問いなら、代わりに依存の向きを辿り、`docs/rules.md` と所有する層の `README.md` を
**記憶からではなく実行時に**読む。

そのうえで、断定しようとしている一つひとつについて次を立てる。

- **それは最新か。**そのファイルは今週マージされたブランチで変わったかもしれない。
  関係するパスの履歴を見る（`git log --oneline -15 -- <paths>`）。
- **範囲は網羅されているか。**主張が「ここだけが〜」なら、呼び出し地点を推測せずグラフを逆引きする
  （`graphify affected <symbol>`）—— 各地点を関係ラベルと `file:line` 付きで返し、それが不在の主張が
  必要とする証拠である。**範囲の主張は不在についての主張**であり、不在は網羅探索のためにある。
  グラフの鮮度を述べ、遅れているなら網羅探索へ落とす。
- **コストの比較は何かの上に立っているか。**「hot path に 1 回読みが増える」は確かめられる。
  **測っていないコストはトレードオフではなく推測である。**

## Step 3 —— 5 つの blocker

**どれか 1 つでも真である間、下書きは Step 4 へ進まない。**意図的に機械的にしてある ——
**「自分は確信が無い」と*気づく*ことを求められた書き手は、たいてい気づかない。**

| # | blocker | 解消 |
| --- | --- | --- |
| 1 | 観測していない実行時の振る舞いを断定している | 観測する（Step 5）、あるいは未確認と印を付けて本文でそう言う |
| 2 | 引用した実装の鮮度を確かめていない | そのパスの履歴を見る |
| 3 | 案の比較に測った根拠が無い | 測る、あるいは比較を落としてコストの主張なしに選択肢を出す |
| 4 | 影響範囲の主張が部分的な探索の上に立っている | グラフを逆引きする、網羅探索する、あるいは覆った範囲まで主張を狭める |
| 5 | 既存 issue を検索していない | 検索する |

**情報が足りないなら聞く。見積もらない。**もっともらしい推測が issue の自信のある調子で書かれると、
**以後それを読む全員にとって事実になる。**足りない情報には、実際に望まれている振る舞いはどれか、
考えられる複数の原因のうち user がどれを念頭に置いているか、コードが含意している制約が意図的か、
が含まれる。**それらは聞く。推論で解決しない。**

## Step 4 —— 本文を書く

**欄の集合はこのリポジトリのものであって、このスキルのものではない。**`.github/ISSUE_TEMPLATE/` を
**実行時に読み**、合うテンプレートを選び、必須と印の付いた欄を埋める。**欄の一覧をこの本文に持たない** ——
テンプレートは変わり、ここの一覧が**腐るほうの写し**になる。

それを「整頓」ではなく**必須**にしている理由が 2 つある。

- **`scripts/issue-field-lint` は必須の見出しを完全一致で見る。**しかも `###` で。`##` で起票した
  本文は、いま作ったばかりの issue の上で検査に落ちる。
- **テンプレートが縛るのは Web フォームだけ。**`--body-file` の起票はそれを丸ごと素通りする ——
  そして**それがエージェントの起票する経路**である。lint が在るのはその穴のためで、
  **欄を自分で書くことがその穴を塞ぐ。**

テンプレートの欄に加えて、3 つの節を足す。**後から検査できる issue にしているのはこの 3 つである。**

```markdown
### 前提            ← 事実の主張ごとに、どこで裏取りしたか
### 論点            ← 選択肢と、理由付きの推奨（決着ではなく論点として）
### やらないこと
```

**前提 の節が要点である。**各前提を、**それ単独で反証できる文**として、裏付けとともに書く。

```markdown
### 前提

- 保護対象の経路に無資格の要求が届く — **確認済み**: `matcher` がその接頭辞を選んでいない
  （`src/proxy.ts`、`<commit>` 時点）
- この値は表示側まで生の形で届かない — **未確認**: 静的な読みのみ。実際の応答は観測していない
```

issue を拾う人はこの節を読み、**主張ごとに、どれがまだ成り立つかを言える。**
**前提を散文に埋め込むとその検査ができない** —— そしてそれが、誤った主張が実装まで生き残る経路である。

issue を腐らせないための書き方の規則が 3 つ。

- **シンボルとパスで引く。行番号は書かない。**行番号は次のリファクタで陳腐化し、それを辿って違う場所に
  着いた読み手は、そこに在るものを信じる。
- **推奨は根拠と一緒に記録する。****誤っていた推奨は普通のこと**である。**理由が見えない推奨は、
  証拠で覆せない。**
- **security の所見は伏せてから書く。**このリポジトリは公開されており、**issue は取り消せない。**
  形を述べ、`path` とシンボルで引き、**秘密らしき値を再現しない。**伏せると要点が消える所見は、
  起票せず私的に上げるもの。

**他リポジトリの issue / PR へのリンクは `redirect.github.com` を使う。**素の `github.com` リンクは
**そのスレッドに公開の相互参照を残し**、本文を後から編集しても取り消せない。その信号を意図して送るかは
**例外なく人の判断である** —— **毎回聞く。包括的な委任があっても自分で決めない。**`AGENTS.md` が統べる。

本文は日本語で書く。提示して承認を待つ。

## Step 5 —— 振る舞いを観測する（`--verify=observed` のときだけ）

`--verify=static` ではこの段は起きず、**前提 の振る舞いの主張はすべて未確認と印を付ける。**
**未確認の主張を確認済みと同じ調子で提示することは、認めた欠落より悪い。**

`--verify=observed` では、動いているアプリに対して主張を確認する ——
**先に聞いてから。ここではアプリを立てること自体が別の判断である。**`APP_ENV` は明示が要る ——
loader は既定へ落ちず、開発用の session の口は環境が自分を名乗ることを要求する
（認証の側は [`docs/design/auth.md`](../../../docs/design/auth.md) が正）。

**何かを「検証」するためにゲートを回さない。**ゲートは hook と CI のもので、判定は CI が正である。
この段が観測するのは**振る舞い**であって、緑の検査ではない。

どの主張を観測し、どれを読んだだけかを報告する。

## Step 6 —— そもそも issue にすべきかを決める

**起票の前にこの関門を通す。**issue を速く書ける AI は、**人よりも多く作る。**
そして issue の数それ自体がコストである —— **重複は元の issue を埋め、読めないバックログは誰も使わない。**

| 状況 | 起票の代わりにやること |
| --- | --- |
| 既存の issue が覆っている | そこへ新しい所見をコメントする |
| その場で直せる大きさ | 今直すことを申し出る |
| Step 2 が前提を反証した | それを報告する。起票しない |
| タスクではなく決定である | ADR を提案する、あるいは `docs/adr/BACKLOG.md` に撤回条件つきの枠を提案する |
| 欠陥ではなく画面の約束である | `docs/spec/` の更新を提案する |
| 意図して持たないものである | まず `docs/project/out-of-scope.md` を見る —— 既に答えが在り、それを変える条件も書かれているかもしれない |

新しいと結論する前に検索する。

```bash
gh issue list --state open --limit 100 --search "<keywords> in:title"
gh issue list --state all --limit 50 --search "<keywords>"
```

**closed も含める。**過去に却下された提案は重要な文脈であり、**却下を認めずに再提出することは
読み手の時間を浪費する。**

**表のどの枝が当たったかを述べる。沈黙は「明らかに issue だった」と読まれる。**

## Step 7 —— 起票する

```bash
gh issue create --title "<title>" --label <label> --body-file <file>
```

ラベルは `.github/settings/labels.json` から取る。名前を推測しない。URL を報告し、
**どの前提を観測し、どれを読んだだけかを述べる。**

user が `--output=draft` を選んでいれば、ここへ来る前に止めて本文を渡す。

## この段が座っている場所

上流には `research` が座り、未決の選択肢を比較して `決めるべきこと` で止まる。
**その推奨は決定ではない** —— **人の承認がそれを決定に変える**のであり、このスキルは
**承認されたその結果が追跡可能になる場所**である。誰もまだ承認していない推奨を抱えた問いが来たら、
**それは塞ぐ穴ではなく名指す穴**である。**決着した計画としてではなく、論点として書く。**

下流は issue を拾う人である。**その読み手に向けて書く** ——
**前提は、最も滑らかに読める場所ではなく、検査できる場所に置く。**

## やる / やらない

- ✅ `src/proxy.ts` を含めて経路全体を辿ってから断定する。
- ✅ 描画の境界と import の行列は、推測せず読む。
- ✅ 情報が足りないなら聞く。推論で穴を埋めない。
- ✅ `.github/ISSUE_TEMPLATE/` を実行時に読み、必須の欄を `###` で埋める。
- ✅ 各前提を、裏付け付きの、単独で反証できる主張として書く。
- ✅ closed を含めて既存 issue を検索してから、新しいと結論する。
- ✅ どの主張が未確認かを明示する。
- ✅ シンボルとパスで引く。推奨の根拠を並べて記録する。
- ✅ security の所見は、公開の issue へ届く前に伏せる。
- ✅ Step 6 の表のどの枝が当たったかを述べる。
- ✅ 日本語で書く。
- ❌ 観測していない実行時の振る舞いを、未確認と印を付けずに断定する。
- ❌ テンプレートの欄の一覧を、読む代わりにこの本文へ持つ。
- ❌ 測っていないコストをトレードオフとして出す。
- ❌ 部分的な探索から影響範囲を主張する。
- ❌ 既存 issue へのコメントで足りるとき、あるいは修正が issue より小さいときに起票する。
- ❌ 他リポジトリの issue を素の `github.com` URL で貼る。相互参照が妥当かを自分で決める。
- ❌ 本文に行番号を書く。
- ❌ 振る舞いの観測の代わりにゲートを回す。
