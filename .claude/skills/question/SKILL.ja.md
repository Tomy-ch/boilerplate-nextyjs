# Question

問う側が実際に何を意味したのかを解き、それを確認し、答えを所有する相手へ問いを渡す。

日本語参考訳はこのディレクトリの `SKILL.ja.md`（人間の参照用。スキルとしては読み込まれない）。

## 使うとき

- 問いが 2 通り以上に無理なく読める。
- どのスキルが何を担当するか分からない、あるいは「この問いはどこへ行くのか」と聞かれた。
- 前の実行が違う読みに答えてしまい、振り直しが要る。

## Contract

| | |
| --- | --- |
| **Owns** | 問いの読みの解決（世界 / 意図 / 対象の 3 軸）、人への確認、所有スキルへの引き渡し |
| **Never** | 自分で答える / 手順を組む / 比較する / レビューする / 軸が割れているのに黙って片方を選ぶ |
| **Starts when** | 問いの読み方が一意でないとき、どのスキルが担当か分からないとき |
| **Stops when** | 引き渡し先が決まったとき、または該当するスキルが無いと分かったとき |

## このスキルを使わない場面

- 読みが既に一意な問い —— 所有者へ直接行く。
- 自分で答え・手順・比較・レビューを出すこと。

## このスキルが在る理由

ここの扉はどれも、誤発火した問いを振り直す門番を持っている。それが捕まえるのは易しいほうの case ——
**中から見て、違う扉が見えている**場合である。このスキルが在るのはそれが捕まえない case のためで、
**2 つの異なる読みのどちらでも問いとして成立し**、どちらの行き先も有能で自信のある、しかし範囲の違う
答えを出し、**出力のどこにも「もう 1 つの読みが在った」ことが現れない**場合である。

最もよくある形は素の「今」である。**外の業界のこと**にも、**いまのこのリポジトリのこと**にも、
**この窓の差分のこと**にも読める。読みごとに所有者が違い、どの所有者も有能に答え、文のどこにも
選ぶ材料が無い。片方を選んだスキルは**完全に見える答え**を出す —— まさにそれが、選ぶのが誤りで
問うのが正しい理由である。

**曖昧さは問う側に在るので、問う側が解く。**これは弱い経験則の代わりに置いた逃げ道ではない ——
情報が実際に在る場所がそこだからである。

## 3 つの軸

問いをこの 3 つで解く。ほとんどの問いは 3 軸とも一意で、ここへ来るものが 1 つ、たまに 2 つ割れる。

| 軸 | 分かれ方 | 割れている合図 |
| --- | --- | --- |
| **世界** | 外の世界 / このリポジトリ全体 / この窓の差分 | 素の「今」「最近」「普通」、あるいは基準を言わない比較 |
| **意図** | 症状 / 目標 / 知識 / 未決の選択 | 動作にも失敗にも名前を付けない「どう」「大丈夫」「どうなってる」 |
| **対象** | 実装 / テスト / コメント / 文書 / 語彙 / 運用 | 全部をいっぺんに指す名詞（「品質」「これ」「この画面」） |

軸は互いに独立なので、**スキル名へ飛ばずに軸ごとの読みを別々に述べる。**読み手が
「差分ではなくリポジトリ全体の話」を訂正するのは、「`impl-review` ではなく `repo-truth`」を訂正するより
ずっと易しい —— **前者は自分の問いについての話で、後者は知らないかもしれない道具についての話**だからである。

## Step 1 —— 問いを読み、解けるものを解く

問いを 1 行で言い直し、**軸ごとの読み**を添える。文が実際に決めている軸はすべて解く —— たいていは解ける。

これは**文とその文脈から**やる。**コードベースを読んでやらない。**曖昧さを解くために調査するのは
行き先の仕事であり、たいてい徒労でもある —— **どの「今」を指しているかは、どのファイルにも書いていない。**

軸を正当に決める文脈の事実が 2 つある。使ったなら、どちらも述べること。

- **開いている差分。**未マージのコミットがあれば「この窓」の読みが生きており、clean なツリーなら
  ほぼありえない。確かめて、何が分かったかを言う。ベースは `commit` / `submit-pr` と同じ解き方で ——
  `gh pr view --json baseRefName -q .baseRefName`、無ければ `make -s base-branch`。
- **直前の会話。**実装の直後の問いは、たいていその変更についてである。**文脈から推測したと述べる** ——
  訂正できるようにするため。

## Step 2 —— 実際に割れている軸だけを聞く

すべての軸が解けたら Step 3 へ飛び、読みを 1 行で述べる。**一意な問いにモーダルを作らない** ——
その摩擦は、稀な case のために**よくある case のほう**に掛かる。

軸が本当に割れているときは `AskUserQuestion` を呼ぶ。割れた軸ごとに 1 問、多くて 2 問。
選択肢は**その人の問いの読み方**として書く。**スキル名では書かない。**

```text
質問: 「今」はどの範囲を指していますか？
選択肢:
  - 外の世界と比べて — 一般的なやり方として今も妥当か
  - このリポジトリ全体 — コードベース全体が筋の通った状態か
  - この窓の変更 — いま書いた差分がどうか
  - どれでもない — 別の意味だった
```

**「どれでもない」を必ず入れる。**自分の 3 つの読みしか出さないルータは、そのどれかが正しかったかに
関わらず、そのどれかを収穫する。

## Step 3 —— 行き先を実行時に解決する

**ルーティング表をハードコードしない。**スキルは足され、改名され、退役する。この本文に書かれた表は
黙って古くなる —— もう無いスキルへ振る、あるいはいま所有しているスキルを取りこぼす。
**代わりに、導入されている集合を読む。**

```bash
ls .claude/skills/
head -20 .claude/skills/*/SKILL.md      # frontmatter: name + description + argument-hint
```

各スキルの `description` は何を所有するかを述べ、末尾で**明示的に何を所有しないか**を述べる ——
その `Do NOT use it for…` の節が **frontmatter で最も信用できるルーティング信号**である。境界を所有する
本人が書いたものだからである。隣に扉を持つスキルは `## Contract` 表（Owns / Never / Starts when /
Stops when）も持つので、description で判断が際どいときはそちらを読む。

解決した読みを問いと一緒に渡す。**読みが行き先の引数まで決めるなら、それも渡す** ——
そもそも存在するかを知りたいなら `repo-truth --depth=full`、その問いがまだ開いているかを聞いて
いるなら `research --stage=dissolve`、操作ではなく手順が欲しかったなら `how-to --mode=lookup`。

導入されているスキルのどれも所有していないなら、平明にそう言って止まる。**それは所見である** ——
スキル集合の穴であって、ここで答える理由ではない。

### 差分の読みには行き先が 1 つあり、それはスキルではない

**世界の軸が「この窓の差分」に解けたときは、`AGENTS.md` の Review Phase Protocol へ渡す ——
レビュー 3 本のどれかへ直接渡さない。**

あの protocol はレビュー依頼に 3 つの主題（変更そのもの / テスト / コメントの在庫）を名指し、
**各スキルの見込みリターンの見積もりを要求し、スキルごとに user へ諾否を問う**。どれか 1 本へ直接
振ることは、**その protocol が user に問うために在る問いを黙って答えてしまう** —— そしてここを
通ったフローから残り 2 本を落とす。**それこそが protocol が防ぐために書かれた drift** である。

したがってこの読みの引き渡しは「読みが差分であることを述べ、protocol に従う」である。
protocol は**実行時に読む**。あれは `AGENTS.md` のものであってこのスキルのものではなく、判定基準を
ここへ書き直せば 2 つめの写しが生まれる。

## Step 4 —— 引き渡す

**行き先とその理由を 1 行**述べ、起動する。user は既に読みを承認している ——
スキルの選択を再確認するのは、いま下したばかりの判断への 2 つめの関所である。

```text
「このリポジトリ全体」の読みで受け取りました。現状の事実は repo-truth が所有します。
```

**引き渡しがこのスキルの唯一の出力である。**行き先が何を見つけるかを要約しない。一部を先に答えない。
両方の読みを覆うために 2 つの行き先を回さない —— それは丁寧さではなく、**読みの問いを未解決のまま
残したこと**である。

## 引数

| 引数 | 効果 |
| --- | --- |
| `--to=<skill>` | 呼ぶ側が行き先を既に知っている。Step 1〜3 を飛ばして引き渡す |
| `--explain` | 軸の解決と行き先を示して、起動せずに止まる |

`--explain` は「これはどこへ行く問い？」のためのモードである —— リポジトリについてではなく、
スキル集合についての問い。腑に落ちなかったルーティング判断を検分する口でもある。

## 連鎖ではない

**ルーティングは連鎖の反対**であり、違いは**判断がどこに座るか**である。別のスキルへ連鎖するスキルは
user の代わりに決める。このスキルはその判断を user の前に置き、そのうえで実行するために在る。
軸が割れたときの確認が任意でないのは、そして行き先を 2 度起動しないのは、そのためである。

同時にそれは、**行き先が独立に起動可能なまま**であることも意味する。**ここは `question` を必須の
入口にしない** —— 範囲のはっきりした問いは所有者へ直接行くべきで、このスキルはそうでないもののために在る。

## やる / やらない

- ✅ 文が決めている軸はすべて解く。本当に割れている軸だけを聞く。
- ✅ 選択肢は問いの読み方として書く。スキル名では書かない。
- ✅ 常に「どれでもない」を出す。
- ✅ 行き先の解決に、導入されているスキルの frontmatter を実行時に読む。
- ✅ 解決した読みと、行き先の引数を問いと一緒に渡す。
- ✅ 開いている差分や直前の文脈が軸を決めたなら、そう述べる。
- ✅ 差分の読みは Review Phase Protocol へ渡す。レビュー 1 本へ渡さない。
- ✅ 「どのスキルも所有していない」を所見として報告して止まる。
- ✅ 日本語で答える。
- ❌ 問いに答える、手順を組む、選択肢を比較する、何かをレビューする。
- ❌ 軸が割れているのに読みを選ぶ。
- ❌ ルーティング表をハードコードする。導入を確かめずにスキルへ振る。
- ❌ 曖昧さを解くためにコードベースを読む —— 曖昧さはファイルではなく問う側に在る。
- ❌ 一意な問いにモーダルを出す。
- ❌ 両方の読みを覆うために 2 つの行き先を起動する。
