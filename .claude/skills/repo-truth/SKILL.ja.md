# Repo Truth

このリポジトリが**いま**どうなっているかを、リポジトリ自身の一次資料から、推論の道筋を見える形で答える。

canonical はこのディレクトリの `SKILL.md`（英語）。規約の正はそちらで、この訳は参考である。

## 使うとき

- どこで実装されているか、あるいはその経路が実際どう振る舞うかを聞かれた。
- ここでの規約は何か、正本はどの文書かを聞かれた。
- なぜこの設計なのかを聞かれた。
- その規則・手順・語がそもそも存在するのかを聞かれた。

## Contract

| | |
| --- | --- |
| **Owns** | このリポジトリの現状の事実回答、根拠と推論の分離、**未定義 / 確認できず** の判定 |
| **Never** | リポジトリ外の一般論を主根拠にした将来設計 / 未決の採択 / 変更 / 見つけた drift の修復 |
| **Starts when** | 現状・規約・根拠・語義・存在有無を問われたとき |
| **Stops when** | 同格の権威が食い違ったとき（両方を出して停止）、索引を通読しないまま断定を求められたとき |

## このスキルを使わない場面

- リポジトリ固有の答えを持たない、一般の Next.js / React の問い。
- 既知の運用上の症状と、その対処 —— `repo-ops`。
- 実行したい操作 —— `how-to`。
- 選択肢の比較が要る未決の設計の問い —— `research`。
- 差分のレビュー —— `impl-review` / `test-review` / `comment-sweep`。
- 見つけたものの起票 —— `new-issue`。

## このスキルが在る理由

このリポジトリについての誤答は、ほとんど 2 つの失敗から出る。どちらも「もっと丁寧に読む」では直らない。

**1 つめは記憶から答えること。**層の規則、make ターゲットの挙動、ステータスコード —— どれも思い出せる
気がして、どれもその後に変わったファイルが決めている。断定の調子で述べられた答えは実行に移される。
**確かめていないと言うより、だいたい合っているほうが悪い。**

**2 つめは正本の場所を取り違えること。**`AGENTS.md` がそのまま書いている —— **文書はそれが所有する
関心で名付けられる**。だから索引を機能の語で検索しても足りない。問いを統べているファイルは、
たいていその問いの語を 1 つも含まない。**正本を特定することは、それを読むこととは別の段**であり、
答えが正しいかを決めるのはそちらである。

出力が 根拠 と 推論 を分けているのはそのためである。不確かさに対する礼儀の話ではない ——
**読み手が覆せるのは、拠り所が見えている主張だけ**だからである。

## 引数と門番

このスキルは何も聞かずに始める。範囲を確認するモーダルは、たいていの答えの値打ちより高くつく。
変わる部分は引数で表し、連鎖して呼ぶ側が推測させるのではなく述べる。

| 引数 | 効果 |
| --- | --- |
| `--depth=quick`（既定） | 所有する索引を拾い読みする。**未定義 は名乗れない** —— 不在は 確認できず としてしか報告できない |
| `--depth=full` | 所有する索引を通読する。これが **未定義** を名乗る資格になる |
| `--kind=<kind>` | Step 1 の分類を飛ばす。呼ぶ側がどのコーパスが統べるかを既に知っている場合 |

`--depth` は意図的に**権威ある不在の値段**にしてある。ADR の索引を端から読み、README 連鎖を辿るのは
実費が掛かり、ポインタで足りる問いにその費用を払う理由は無い。**答えが「無いこと」に懸かっていると
判ったら自分で `full` へ上げてよい** —— 上げたことを述べること。

**次に、自分が正しい扉かを確かめる。**隣り合う扉が 4 つあり、**区別する信号は語彙ではなく意図**である
（同じ名詞がどの扉の説明にも出てくる）。

| 相談の内容 | 扉 |
| --- | --- |
| 壊れたもの、落ちたゲート | `repo-ops` |
| 実行したい操作 | `how-to` |
| まだ誰も決めていない選択 | `research` |
| どう動くか / 規則は何か / そもそも在るか | ここ |
| 上の複数に読めるもの | `question` —— 問う側のルータ |

扉が違うなら 1 行でそう言って、正しい扉を名指す。**それでも答えるほうが、誤発火より悪い** ——
手順が要る人に、知識の形をした答えが返る。

一番効くのは最後の行である。素の「今どうなってる」は、外の業界のことにも、いまのこのリポジトリのことにも、
この窓の差分のことにも読める。**曖昧さは問う側に在るので、コードをいくら読んでも決まらない。**
読みを選ばず `question` へ渡す —— 選ぶと、誰も聞いていない問いへの自信のある答えが出る。

## Step 1 —— 何を問われているかを分類する

分類が「何をもって答えとするか」を決める。そして何より、**不在が何を意味するか**を決める。
検索の前にやること。

| 種別 | 何が答えになるか | 不在は何を意味するか |
| --- | --- | --- |
| Fact —— どう振る舞うか | その経路の実装 | 経路が存在しない。もっともらしい経路を描写せず、そう言う |
| Rule —— ここでは何をすべきか | それを統べる文書 | **規則が未定義かもしれない**。それ自体が所見だが、Step 2 が所有索引を尽くした後にだけ言える |
| Rationale —— なぜこうなっているか | `docs/adr/` / `docs/design/` | 暗黙に決まり、記録されなかった |
| Procedure —— ここではどうやるか | `.makefiles/**` / `package.json` の scripts / `.lefthook.yaml` / `.github/workflows/` / `docs/get-started/` | **正規手順が無いかもしれない**。同じ基準。穴を埋めるためにコマンドを発明しない |
| Vocabulary —— この語は何を指すか | [`docs/spec/glossary.md`](../../../docs/spec/glossary.md) / `docs/spec/README.md` / 層 README | その語にまだ家が無いか、正がバックエンドの契約にある業務語彙である |
| History —— いつ・なぜ変わったか | `git log` / merge された PR | —— |

問いは、どの種別かについての言われていない前提を抱えていることが多い。「この検証はどのコマンド？」は
Procedure、「なぜこの検証は CI 側なのか」は Rationale で、解けるコーパスが違う。

## Step 2 —— 探索の前線を張り、正本を特定する

このスキルが在る理由そのものの段であり、答えが信用できるかを決める段である。

**開いていないファイルからは何も結論できない。**何を読もうと、コーパスの大半は読まれないまま残る。
つまり**当たりが無いことは、答えが無いことではない。**相手にしている量は、ここに書かれた数字ではなく
**索引を読んで数える** —— ここに数字を書けば、書いた翌週には偽になる。

### 索引を、関心で先に読む

索引を読み、**その文書が何の関心を所有しているか**でエントリを選ぶ。キーワードの一致で選ばない。

| 索引 | 何を覆うか |
| --- | --- |
| [`docs/README.md`](../../../docs/README.md) | **どの文書がその判断を所有するか** —— 4 分類と行き先の判定。どのコーパスが統べるか分からないときは、まずここ |
| [`docs/adr/README.md`](../../../docs/adr/README.md) | なぜその決定になったか。どれが意図的な除外か |
| [`docs/design/README.md`](../../../docs/design/README.md) | 層を跨ぐ 1 つの主題がどう動くか |
| [`docs/rules.md`](../../../docs/rules.md) | 日々強制される制約。各項が Rationale のリンクを持つ |
| [`.makefiles/README.md`](../../../.makefiles/README.md) | 全 make ターゲット、領域別 |
| [`docs/playbook.md`](../../../docs/playbook.md) | 逆引き —— 「X をやりたい」→ 置き場 |
| 対象パスから `src/<kernel>/README.md` まで辿る README 連鎖 | 責務・禁止・frontmatter の `imports-allowed` / `test-requirement` |
| [`architecture.ts`](../../../architecture.ts) | 依存表そのもの。何が何を import してよいかの唯一の権威 |

キーワード検索は**最後**。索引が取りこぼしたものを拾う網であって、最初の一手ではない。

### 権威に見えて権威でないもの 2 つ

ここのコーパスは小さく、おおむね正直である。だからこそ例外の 2 つを見落としやすい。

- **`SKILL.ja.md` は翻訳であって出典ではない。**当たったこと自体は**在り処の手がかり**として有用だが
  （その主題が文書化されている証拠になる）、引くのは隣の正典 `SKILL.md` のほう。v1.0.0 未満では
  これがリポジトリ内で唯一の `*.ja.md` である（[0140](../../../docs/adr/0140-documentation-operations.md)）。
- **生成ビューは権威ではない。**`docs/portal/` はそれが列挙する出典から組み立てられ、`graphify-out/` は
  派生した索引である。引くのは、それらが組み立てられた元のほう。

### 結論の前に前線を記録する

実際に覆った範囲を控える —— どの索引を通読したか、どの README 連鎖を辿ったか、どの glob を検索したか。
**そして、回さないと決めた掃引とその理由も。**覆った側だけを並べた前線は、残りを除外したのか忘れたのかを
区別できず、**そのうち一方だけがリポジトリについての所見**である。これが不在を反証可能にするものであり、
このスキルが決してぼかしてはならない線を引く。

| 判定 | 要件 |
| --- | --- |
| **未定義** —— 規則 / 手順が存在しない | 所有索引を**通読**し、README 連鎖を辿った |
| **確認できず** —— 確かめられなかった | それ未満のすべて |

確認できず へ落とすことは常に可能で、費用も掛からない。**部分的な掃引から 未定義 を報告するのは、
答えが無いことより悪い** —— 決着した事実として読まれ、次の人がその上に積む。

### 構造がテキストに勝つところではグラフを使う

キーワード検索が外すのは、まさにこの節が挙げた問いである —— 関心で名付けられた統べる文書、
呼び先と語彙を共有しない呼び元。`graphify` は**構造**を索引化するので、テキスト検索が届かない
ところへ届く（何であるか・どう導入するかは [`.claude/README.md`](../../README.md)）。
**警戒するだけでなく、手を伸ばすこと。**

- **`graphify affected <symbol>` が払うコマンドであり、範囲の主張が要求するものである。**
  逆引きが各呼び出し地点を関係ラベルと `file:line` 付きで返す —— 「ここだけが〜」が必要とする
  網羅探索の証拠そのもので、**`grep` では供給できない**（呼び元が呼び先と語彙を共有している必要が
  無いため）。これを使わずに述べた範囲の主張は、実際に覆った範囲まで狭める。
- **`god-nodes` は使わない。**エッジ数で順位づけるので、このリポジトリの 1:1 テスト写像規約のせいで
  テスト足場が production の上に来る —— 誰も聞いていない問いに答える。
- **ノードやエッジは決して根拠ではない。**それはファイルへの到達手段であり、そのファイルを開いて引く。
  ソースで確認していないグラフの答えは 推論 に留まる。
- **鮮度を述べる。**グラフはあるコミットから作られる。どのコミットかを言うこと。**未コミットの作業には
  盲目**である —— 作業ツリーについての問いなら作り直すか `grep` を使う。小さい差分なら後者が安い。
- **グラフが無いなら、構造の掃引は行われていない。**索引読み・検索・直接読解へ落とし、
  **そのことを前線に記録する** —— 構造の掃引なしに報告する不在は 未定義 ではなく 確認できず である。

## Step 3 —— 一次資料を読み、継ぎ目に印を付ける

引くものは開く。**読んでいないパスは根拠ではない。**

読みながら、2 つの山を分けたまま保つ。1 つの段落に書いた瞬間に混ざるからである。

- **根拠** —— 出典が実際に含んでいる文、またはコードが実際に表している振る舞い。
- **推論** —— 出典を組み合わせて、不在から、あるいは兄弟との類推で導いたこと。推論は正当であり、
  しばしば答えの値打ちそのものである。**根拠と同じ調子で提示することが正当でない。**

最もよくある漏れは**範囲**の主張である。「ここだけがこれをやっている」は不在についての主張であり、
不在は網羅探索によってしか立たない。グラフを逆引きするか、網羅探索を回す。どちらも回していないなら、
**実際に覆った範囲まで主張を狭める。**

## Step 4 —— 鮮度と矛盾を見る

- **鮮度。**統べるファイルは今週動いたかもしれない。答えが最新であることに懸かっているなら、
  引くパスの履歴を見る（`git log --oneline -10 -- <paths>`）。
- **矛盾。**ここでの食い違いの多くは既に決着している —— `AGENTS.md` § Instruction Priority が権威の順を
  決め、[0140](../../../docs/adr/0140-documentation-operations.md) が `rules.md` / `docs/design/` と
  食い違えば ADR を上に置く。**リポジトリが既に決めている矛盾を報告せず、その順位を当てる。**
  止まるのは**同格どうし**の食い違い —— ADR 同士、層 README 同士、規則とその Rationale 先 ——
  順位を付けるものが無い場合である。両方を鮮度付きで出して止まる。
- **drift は所見であって作業ではない。**コードと統べる文書が食い違うなら、文書が統べる側でコードが
  drift である。そう述べて止まる。直すのは `back-prop` の仕事である。

## Step 5 —— この契約で答える

常にこの形、日本語で。回答 は最初に読める長さに保つ。

```markdown
## 回答
<結論を 1〜3 文で>

## 根拠
- <主張> — `<path>` の `<symbol / target / 節>`
- <主張> — `<path>` の `<symbol / target / 節>`

## 推論
- <根拠から導いたこと。断定と区別できる書き方で>

## 矛盾 / 欠落
- <食い違う出典と、それぞれの鮮度> / <未定義 または 確認できず> / <古い可能性のある記述>
- 探索範囲: <通読した索引 / 辿った README 連鎖 / 検索した glob / 回さなかった掃引とその理由>
  ← 欠落を報告するときは必須

## 確度
High | Medium | Low — <そう判断した理由>

## 次にできること
<追加確認 / research / new-issue / back-prop / repo-ops など。実行はしない>
```

引くのは**シンボルとパスで、行番号は書かない** —— 行番号は次のリファクタで陳腐化し、それを辿って
違う場所に着いた読み手は、そこに在るものを信じる。

確度は「どれくらい自信があるか」ではなく、出典で判定する。

| 段階 | どういうとき |
| --- | --- |
| High | 現行の一次資料が複数一致し、それらが問われた問いを統べている |
| Medium | 一次資料が 1 つ、暗黙のもの、または鮮度が未確認のもの |
| Low | ほぼ推論、出典が食い違う、決め手の出典に到達できなかった |

問いの一部にしか答えられなかったときは、確かめた部分を返し、残りを欠落として名指す。
**完全に見える答えより、正確な部分解のほうがよい。**

## 欠落は答えである

「正規の手順は無い」はこのスキルが所有する所見であり、代わりのほうが悪いから存在する ——
発明されたがもっともらしいコマンドは、文書化されたものと見分けが付かず、次の人がそれを実行する。

**結果として述べ、前線を添えて、不在を反証可能にする。**

> 正規手順は**未定義**。`.makefiles/README.md`（全 target）と `package.json` の scripts を通読し、
> `.lefthook.yaml` / `.github/workflows/` を確認したが該当なし。近いのは `<target>`（ただし〜の点で
> 目的が異なる）。

索引を通読していないなら判定は **確認できず** であり、どの索引を読み残したかを述べる。
2 つは交換可能ではない —— 一方はリポジトリについての所見、他方はこの実行がどこまで進んだかの所見である。

`repo-ops` はどちらの判定も意図的に持たない —— 既知の症状のルックアップ表であり、「未定義」を
結論できるようにすると汎用の検索スキルになってしまう。症状が索引に無いとき、問いはここへ来る。

## 単独で完結する設計

このスキルはそれ自身として起動され、何にも連鎖しない。次にできること が何かは報告する ——
未決の設計の問いなら `research`、見つけたものの起票なら `new-issue`、drift なら `back-prop`、
既知の症状なら `repo-ops` —— **実行するかは user が決める。**

レビュー 3 本が `AGENTS.md` の Review Phase Protocol の下で対等な相方であるのと同じ理由である。
次を代わりに実行するスキルは、その判断を user から取り上げる。そしてこのスキルの判断が drift したとき、
そこを通った全フローが黙って別の場所へ流される。

## やる / やらない

- ✅ 扉が違うならそう言って正しい扉を名指す。それでも答える、をしない。
- ✅ 索引を関心で先に読む。キーワード検索は最後の網であって最初の一手ではない。
- ✅ 前線を記録する —— 通読した索引、辿った README 連鎖、検索した glob。
- ✅ 所有索引を尽くしていないなら 確認できず と言う。未定義 は尽くしたときだけ。
- ✅ 引く出典はすべて開く。シンボルとパスで引く。
- ✅ 根拠 と 推論 を別の節に保つ。
- ✅ 順位の付く食い違いには `AGENTS.md` § Instruction Priority を当てる。止まるのは同格の矛盾だけ。
- ✅ 不在を答えとして報告し、何を探したかを添える。
- ✅ 構造がテキストに勝つところではグラフへ手を伸ばし、指した先をソースで確認し、鮮度を述べる ——
  あるいは回さなかったことを前線に記録する。
- ✅ 意図的に**回さなかった**掃引を、その理由とともに記録する。
- ✅ 日本語で答える。
- ❌ リポジトリが決めていることについて記憶から答える。
- ❌ `SKILL.ja.md` や生成ビューを権威として引く。
- ❌ スキル本文を統べる文書より上に置く。コードの事実を統べる文書より上に置く。
- ❌ 同格の権威どうしの矛盾を自分で解く。
- ❌ キーワード検索から、あるいは通読していない索引から 未定義 を報告する。
- ❌ 穴を埋めるためにコマンド・規則・根拠を発明する。
- ❌ 何かを編集する、ゲートを回す、見つけた drift を直す。
- ❌ 部分的な探索から範囲（「ここだけが〜」）を主張する。
- ❌ 答えに行番号を書く。
