# Research

開いた問いを、人が実際に決められる判断へ変える —— あるいは「そもそも開いていなかった」という所見へ。

canonical はこのディレクトリの `SKILL.md`（英語）。規約の正はそちらで、この訳は参考である。

## 使うとき

- 設計・ライブラリ・運用の選択が開いていて、まだ誰も決めていない。
- 選択肢を出してほしい、あるいは「普通はどうするのか」と聞かれた。
- 決定を見直すことになり、トレードオフを並べ直す必要がある。

## Contract

| | |
| --- | --- |
| **Owns** | 未決の比較、評価軸の確定、推奨とその反転条件、決めるべきことの提示 |
| **Never** | 採択 / ADR の執筆 / 実装 / 案数合わせの選択肢の捏造 / 出典・数値の捏造 |
| **Starts when** | 選択が開いていて、まだ誰も決めていないとき |
| **Stops when** | 現状が不明（`repo-truth` へ）、既に決着している、外部情報を確認できない |

## このスキルを使わない場面

- いまリポジトリがどうなっているかを確かめること —— まず `repo-truth`。
- 操作の正規手順を探すこと —— `how-to`。
- 結果の起票 —— `new-issue`。
- 差分のレビュー —— `impl-review` / `test-review` / `comment-sweep`。

## このスキルが在る理由

比較を「比較しないより悪い」ものにする失敗が 3 つあり、**3 つとも入念さに見える。**

**軸が答えから逆算される。**好ましい案が先に在ると、それを有利にする基準のほうが書き留められる。
**軸を先に固定することだけが防御**であり、それは**どの案を挙げるより前**に起きなければならない。

**コストが答えを選ぶ。**「30 ファイル触ることになる」が、いつのまにか決め手の論拠になる。
[0010](../../../docs/adr/0010-standards-and-non-lockin.md) は、**品質と一貫性がそこへ到達するコストに優る**こと、
そしてコストは「人が方向を保ったまま範囲を断れるように」述べるものだと明言している。
**コストを述べることは必須で、コストに選ばせることは違う。**

**証拠が捏造される。**ベンチマークの数値、版、「一般に推奨される」 —— どれも作るのは易しく、
作られたものだと気づくのは難しい。**確認していない主張が、比較の自信のある調子の中に置かれると、
誰も遡れない判断の根拠になる。**

このスキルが防ぐために在るものがもう 1 つあり、そちらはより見えにくい ——
**そもそも開いていなかった問いに答えること**である。Step 0 と Step 1 を見よ。

## 引数

| 引数 | 効果 |
| --- | --- |
| `--stage=full`（既定） | 推奨まで通す |
| `--stage=dissolve` | Step 0〜1 だけ回して止まる —— 既に決まっていないか、同型の前例が無いか |
| `--sources=repo` | リポジトリの証拠だけ。未確認の主張を出すくらいなら外部の主張をしない |
| `--sources=external`（既定） | 外部調査を許す。Sources 節に従って引用する |
| `--axes=<csv>` | 呼ぶ側が評価軸を固定する。Step 2 は選ばずそれを採る |

`--stage=dissolve` は安いモードで、しばしばそれが答えの全部である —— ここへ来る問いの多くは、
**既に決着しているか、このリポジトリが解いた何かと構造的に同一**である。「これはそもそも未決なのか？」
という依頼のときはこれへ手を伸ばす。そして**溶解を結果として報告する。比較の失敗としてではなく。**

`--sources=repo` は調査ができないときの**正直なモード**である。劣化した実行ではなく、
**推測を断る実行**であり、**そのせいで立てられなかった主張はどれかを述べなければならない。**

## Step 0 —— 問いが本当に開いていることを確かめる

**現状についての誤った前提の上に立てた比較は、比較しないより悪い** —— 決められるように見えるからである。

何よりも先に現状を確かめる。不明または争いがあるなら、**止めてそう言う** —— user はまず
`repo-truth` を回すべきである。自分で起動しない。仮定で穴を埋めない ——
**その仮定が以後すべての選択肢を黙って形づくる。**

**ここで問いを決着させる場所は 1 つではなく 3 つある。**どれかを見落とすと、このスキルが出しうる
**最も高くつく出力** —— 既に決まっていることの再審理 —— になる。

| どこ | 何を決着させるか |
| --- | --- |
| [`docs/adr/`](../../../docs/adr/README.md) | 現行の決定。意図的な除外も含む |
| [`docs/adr/BACKLOG.md`](../../../docs/adr/BACKLOG.md) | 枠の **撤回条件** —— 何を保留したか、何が真になれば見直すか |
| [`docs/project/out-of-scope.md`](../../../docs/project/out-of-scope.md) | このリポジトリが意図して持たないもの。どの条件なら持つか |

**後ろの 2 つが「やらない」を不在ではなく決定にしている。**開いて見える問いは、たいてい
**撤回条件がまだ満たされていないだけ**であり、答えは比較ではなく**その条件**である。

**決めている記録は、キーワードではなく関心で探す。**`AGENTS.md` は「索引を機能の語で検索しても
足りない。文書はそれが所有する関心で名付けられるから」と明言している。`docs/adr/README.md` と
`docs/design/README.md` の項を読み、**それぞれが何を統べるか**で選ぶ。

既にこれを決めているものが在るなら、**それが答えである。**報告し、その理由付けがまだ成り立つかを
述べて、止まる。**決着した決定を開き直すのは人の判断である** —— 前例は権限ではない。

## Step 1 —— まず同型の機構を探す

これを設計の問いとして扱う前に、**構造的に同一の問題をこのリポジトリが既に別の場所で解いていないか**を
見る。解いているなら、配置・構築・呼び出し位置はその前例で確定しており、選択肢を採点することは
**存在しない分岐を発明すること**になる。

**これが最も安い段であり、最も飛ばされる段である。**カーネルを
[`architecture.ts`](../../../architecture.ts) から**列挙する** —— 何が存在し、何が何を import して
よいかの権威はそのファイルである。そのうえで所有する `README.md` と
[`docs/design/placement.md`](../../../docs/design/placement.md) を実行時に読む。
**問題の形から推論しない。**

**同型の機構はその形で見つかる。つまりキーワード検索では見つからない。**それは**違う問題を同じ構造で**
解いており、問いと語彙を共有しない —— 再試行の窓の前例はページングのカーソルであって、
「窓」で検索してもそこには届かない。

**そのためにグラフが在る。**`graphify` はテキストではなく**構造**を索引化するので、問いと語を
共有しない前例へ届く —— **検索が確実に失敗し、走査が失敗しない唯一の case** である。

```bash
graphify query "<structural question>" --budget 8000   # 既定の budget は大きなリポジトリで切り詰められる
graphify affected <symbol>                             # その前例に何が依存しているか＝どれだけ効いているか
```

**候補は同型と呼ぶ前にソースで確認する** —— グラフの辺は関係を示すのであって、
2 つが同じ形の問題を解いていることを示さない。グラフが作業ツリーより遅れているならそう言う ——
**回せなかった構造の掃引は、「前例なし」を弱い主張にする要素**である。

この非対称が立証責任を決める。**「見つけた」は検分で確かめられる**ので前線は要らない。
**「無い」は開いていないカーネル全部についての主張**なので、**どのカーネルを列挙したかを述べる。**
掃引が部分的だったなら、分岐が本物だと断定せず**その確認待ちの暫定として**選択肢を出す。

当てはまるなら平明に言う。

> 設計分岐なし。`<X>` は既存の `<Y>` と同型で、配置・構築・呼び出し位置はそちらの前例で確定する。

**採点の軸は、この段が何も見つけなかったときに手を伸ばすもの**である —— そして**何も見つけなかった
ことは、勝ち取らなければならない主張**である。

## Step 2 —— 評価軸を固定し、以後は触らない

**この問いのための**軸を選び、**どの案も挙げる前に**書き留める。

**出発点の軸は実行時に読む。下の一覧を固定の採点表として扱わない。**これらはこのリポジトリの判断が
実際に住んでいる場所であり、**どれも変わりうる文書が所有している。**

| 軸 | 所有者 |
| --- | --- |
| デファクトへの適合 / 非ロックイン | [0010](../../../docs/adr/0010-standards-and-non-lockin.md) |
| 採用アーキテクチャからの導出 | [0020](../../../docs/adr/0020-adopted-architecture.md) / [0021](../../../docs/adr/0021-frontend-responsibility.md) / `architecture.ts` |
| いまの状態としての純粋さ | [0010](../../../docs/adr/0010-standards-and-non-lockin.md) §3 |
| 依存を足す問いなら、選定基準 | [0004](../../../docs/adr/0004-library-management.md) と [`.github/pull_request_template.md`](../../../.github/pull_request_template.md) の依存欄 |

CI のゲートについての問いはアーキテクチャの軸で決まらない。ライブラリを足す問いはほとんど最後の行で
決まる。**その問いが実際に何で決まるか**を選び、**なぜその軸なのか**を述べる。

**立てなかった軸も書き留める。**軸が無いのは、問いがそれで決まらないからかもしれないし、
この実行がその出典を得られなかったからかもしれない —— `--sources=repo` は業界慣行の軸を丸ごと外し、
4 つの軸を見せられた読み手には**そのどちらが起きたのかを知る手立てが無い**。
**比較の形そのものが「何が効いたか」についての主張である。**

3 行目は最も忘れられやすく、最もしばしば決定的である —— **このリポジトリの製品は、テンプレートから
作られた時点でそのプロジェクトが受け取る状態**であって、そこへ至った履歴ではない。
**このリポジトリを見たことがなく、git log を決して読まない人**を想定して各案を測る。

## Step 3 —— 選択肢を挙げる —— 数は本質ではない

**その問いが実際に持っている選択肢**を挙げる。3 はよくある数であって要件ではない ——
やる / やらない の問いは 2 つであり、形を埋めるために 3 つめを発明すると、
**実際より熟慮されて見えるだけの藁人形**が出来る。本当に異なる 5 つの方針があるなら 5 つ挙げる。
圧縮するのは**ほぼ重複するもの同士を畳むことによって**であって、**違うものを落とすことによってではない。**

案ごとに、Step 2 で固定した軸に対して:

| 欄 | 何が入らなければならないか |
| --- | --- |
| 案 | それが何であるかを言う名前。「案 A」ではない |
| 利点 / 欠点 | 形容詞ではなく帰結 |
| リスク | 失敗の仕方、移行、運用の負担、セキュリティ、ロックイン |
| 既存構造との整合 | どのカーネルが所有するか、`docs/rules.md` のどの規則に触れるか、他に何を強いるか |
| コスト | 触るファイル、誰にとって何が壊れるか、何を作り直すか —— **述べる。判定に重みとして入れない** |

**測っていないコストはトレードオフではなく推測である。**影響範囲も同じで、「30 ファイルくらい触る」は
**グラフが見積もるのではなく算出する数**である。各案が変えるシンボルから逆引きし
（`graphify affected <symbol>`）、**返ってきたものを報告する。**

本当に測れなかったコストは `未確認` へ、**測れば何が変わるか**とともに入れる ——
**限定詞を付けてコスト欄へ入れない。**限定詞の付いた数字も数字として読まれ、
**読み手が判断へ持って行くのはその数字**である。

## Step 4 —— 推奨し、何がそれを覆すかを述べる

**推奨を出す。**推奨無しで渡された比較は、聞いた人へ仕事を返している。ここでの期待は
**推奨が選択肢と一緒に届くこと**であって、求められてから出ることではない。

そして**反転条件**を書く —— それが違えば答えが変わる事実。これが推奨を**議論ではなく証拠で覆せる**
ものにし、同時に**何に自信が無かったかの正直な記録**になる。

> この推奨は、`<前提>` が成り立つ限り。`<条件>` なら B が優位に転じる。

## Step 5 —— この契約で答える

常にこの形、日本語で。**推奨を先頭に。**比較はその裏付けである。

```markdown
## 問題
<何を決めようとしているか、1〜2 文>

## 前提
- <置いた仮定と、それが崩れたときの影響>

## 評価軸
- <軸> — <なぜこの問いでこの軸なのか>
- 立てなかった軸: <軸> — <なぜこの問いでは立てられない / 関係しないのか>

## 選択肢
### <案の名前>
- 利点 / 欠点 / リスク / 既存構造との整合 / コスト

## 推奨
<どれを、なぜ>

## 推奨が変わる条件
- <この事実が違えば結論が変わる>

## 未確認
- <測れなかったコスト / 確認できなかった主張> — <なぜ測れなかったか、測れば何が変わるか>

## 決めるべきこと
- <人が決める事項> — 記録先: ADR / BACKLOG の枠 / issue / spec / 層 README のどれか
```

問いの一部しか調べられなかったときは、その部分を返し、残りを**未調査として名指す**。
**完全に見える比較より、正確な部分比較のほうがよい。**

## 出典

**外部の主張はすべて、発行主体・題名・URL・参照日を持つ。**一次資料と公式資料 ——
そのプロジェクト自身の文書、仕様、リリースノート —— を、二次的な要約より優先する。

調査ができない、あるいは主張を確認できないときは、**未確認だと述べ、それに載っているものの確度を
下げる。**読んでいないベンチマークの数値・版・非推奨化の日付・引用を**決して作らない。**
捏造した出典はここでは小さな誤りではない —— **判断が下される瞬間に本物と見分けが付かず、
そのまま ADR まで生き残る。**

リポジトリ内の主張は、**パスとシンボル**で引く。**行番号では引かない。**

## 単独で完結する設計

このスキルは `決めるべきこと` を出して止まる。案を採択しない、ADR を書かない、issue を立てない、
実装を始めない。**`new-issue` を代わりに起動もしない。**

**推奨と決定の間の隙間が、この段の全部である。**そのまま実装へ流れ込んだ推奨は、誰にもレビュー
されていない。`AGENTS.md` が `docs/adr/BACKLOG.md` の空白領域を人の関所の後ろに置いているのは、
まさに**コードまで生き残る案が、誰かが選んだものであるため**である。先の経路は
**人の承認 → `new-issue`** である。

## やる / やらない

- ✅ まず現状を確かめる。不明なら止めて `repo-truth` を勧める。
- ✅ 決着させる 3 か所を全部見る —— ADR、BACKLOG の撤回条件、out-of-scope。
- ✅ 索引は関心で探す。機能の語では探さない。
- ✅ 設計の分岐として扱う前に同型の機構を探す —— 形で、カーネルを列挙して。概念を grep しない。
- ✅ 構造的な前例と影響範囲のためにグラフを走査し、ソースで確認する。
- ✅ 「前例なし」と断定する前に、列挙したカーネルを述べる。掃引が部分的なら選択肢を暫定と印を付ける。
- ✅ どの案を挙げるより前に評価軸を固定し、所有者を実行時に読み、各軸の理由を述べる ——
  立てなかった軸とその理由も含めて。
- ✅ 測れなかったコストは `未確認` へ、測れば何が変わるかとともに入れる。
- ✅ テンプレートを受け取る読み手を想定して測る。このリポジトリの履歴のためではなく。
- ✅ コストを情報として平明に、推奨と並べて述べる。
- ✅ 根拠付きの推奨と、それを覆す条件を出す。
- ✅ 外部の主張には発行主体・題名・URL・参照日を付ける。
- ✅ 日本語で答える。
- ❌ 目標の数に達するために案を捏造する。本当に違う案を落とす。
- ❌ 好ましい案が分かった後で軸を選ぶ。
- ❌ コストに推奨を決めさせる。
- ❌ ベンチマーク・版・日付・引用を発明する。未確認の主張を確認済みとして出す。
- ❌ 案を採択する、ADR を書く、issue を立てる、何かを実装する。
- ❌ キーワード検索から、あるいは列挙していないカーネルから「前例なし」と断定する。
- ❌ 決着した決定を自分の判断で開き直す。
- ❌ `repo-truth` や `new-issue` へ連鎖する。

- [ ] 決着させる 3 か所を関心で当たった。現行の決定か、満たされていない撤回条件が在るなら
      それを答えとして報告した。
- [ ] 同型の機構の確認を、列挙したカーネルに対して形で行った。当てはまるなら「設計分岐なし」を

- [ ] どの案を挙げるより前に評価軸を固定し理由を付けた。所有者は実行時に読んだ。

- [ ] 確かめられなかったコストと主張は `未確認` に在る。行内で限定詞を付けていない。

- [ ] 各案が帰結・リスク・構造との整合・述べられたコストを持つ。
