# Resolve Merge

衝突した各パスを、そのクラスが既に持っている解決へ振り分けてマージを着地させ、残りを人へ返す。

日本語参考訳はこのディレクトリの `SKILL.ja.md`（人間の参照用。スキルとしては読み込まれない）。

## 使うとき

- マージが衝突を報告した。
- マージが衝突を**報告しなかった** —— 派生した成果物は依然として再生成が要る。
- 手でマージを解決した後、誰も編集していないファイルで検査が落ちている。

## Contract

| | |
| --- | --- |
| **Owns** | 衝突パスのクラス分けと、クラスごとの機械的解決（再生成 / resolver 再実行 / 和集合 / 撮り直し） |
| **Never** | 実装の意味的衝突を解く / 生成物の片側を選ぶ / rebase・squash・force-push / レジストリの鍵衝突をどちらか採用する |
| **Starts when** | ベースを取り込んだ直後（衝突の有無を問わず） |
| **Stops when** | 機械的に解けないものが 1 つでも残ったとき —— その場でマーカーを残して打ち切り、コミットしない |

## このスキルを使わない場面

- 実装コードの意味的な衝突 —— それは人の読みである。
- rebase / squash / force-push。
- 両側で衝突したレジストリの鍵の、どちらを採るかの決定。
- 誰も頼んでいないブランチの同期。

## このスキルが在る理由

**このリポジトリで衝突マーカーが着地する先の大半は、誰も編集すべきでないファイルである。**
契約から生成した API の型と、同じ契約から作られたモックのハンドラ、束ねられた契約そのもの、
`pnpm-lock.yaml`、pin の lockfile、マーカーの基準、デザイントークンの生成物 ——
どれも生成器か resolver を持っており、**どれにも「正しい側」が無い。**

そこで片側を選ぶと、**得られる中で最悪の結果**になる —— マーカーの無いファイル、レビューを通る
ファイル、そして**もう出典から再現しないファイル**。それを捕まえる検査が走るのは後で、
**他人の pull request の上で、その人が一度も触っていないコードの失敗として**である。

2 つめの理由はより静かである。**きれいなマージは、終わったマージではない。**派生した成果物が古く
なるのは**もう一方の側の変更**によってであって、それとのテキストの衝突によってではない ——
2 つのブランチがそれぞれ endpoint を足し、何も衝突せず、**モックのハンドラは再生成可能なまま
再生成されていない**状態が残る。衝突で名付けられたスキルは**まさにその case で飛ばされる**。
だからこのスキルはマージで名付けられている。

## 引数

| 引数 | 効果 |
| --- | --- |
| `--base=<ref>` | ベースを解決せずこれを使う。hotfix ラインが絡むときは必須 |
| `--class=<csv>` | 挙げたクラスに限る。残りは報告して触らない |
| `--dry-run` | 分類して計画を報告する。何も変えない |

## Step 1 —— ベースを取り込む

`make base-merge` がこれを所有する。ベースを解決し（`--base` → PR の `baseRefName` → `origin` の
最新のリリースライン）、保護ブランチの上と汚れたツリーでは実行を拒み、rebase せずマージし、
**未解決のパスを stdout に出しつつツリーを MERGING のまま残す。**

```bash
make base-merge            # 衝突が残れば exit 1 で未解決のパスを 1 行 1 件
```

ここで正しさを決める規則が 2 つあり、**どちらもこのスキルの外に在る。**

- **PR の `baseRefName` が勝つ。**それがそのブランチがいま実際にマージしていく先である。
  今日いちばん新しいものを取り込むのは、追いつかせるのではなく**行き先の付け替え**になる。
- **マージする。rebase しない。**`AGENTS.md` の Git Rules であることに加えて、rebase は追記専用の
  ファイルに実害を出す —— 同じ内容が別のハッシュで両側に再着地し、**2 つの独立した追加として読める。**

**hotfix ラインが絡むときは、解決せず聞く。**リリースラインの解決は `release/*` しか見ないので
hotfix を名指さない。ブランチ名からベースを推測するのは、**推測が最も高くつく瞬間に推測すること**である。
`--base=<ref>` を人から受け取る。

## Step 2 —— 衝突した全パスを分類する

```bash
git diff --name-only --diff-filter=U
```

| クラス | パス | 解決 |
| --- | --- | --- |
| 生成物 —— 契約 | `openapi/api.gen.yaml`, `src/adapters/gen/**`, `mocks/api/**` | 両側を捨てる。`openapi/sources.yaml` が衝突していれば先に解決し、`make gen-api` <!-- skill-lint-ignore --> |
| 生成物 —— デザイントークン | `tokens/` 配下のビルド出力 | `tokens/primitives.json` とテーマの入力を先に解決し、`pnpm gen:tokens` |
| 依存の lockfile | `pnpm-lock.yaml` | 行を選ばない。`package.json` を先に解決してから `pnpm install` |
| pin の lockfile | `.github/actions-pin.toml`, `docker/images-pin.toml` | 行を選ばない。`make actions-pin-resolve` + `make actions-pin-apply`、`make images-pin-resolve` + `make images-pin-apply` |
| 版の刻印 | `package.json` の `version` | ブランチ名が出典。そこで決めてから `make version-stamp-check` |
| 基準画像 | `baseline/images` の gitlink | submodule のポインタの片側を選ばない。撮り直して baseline のターゲットで送る |
| マーカーの基準 | `scripts/marker-baseline/baseline.json` | 数を merge しない。マーカーを持つファイルを先に解決してから `pnpm exec tsx scripts/marker-baseline --write` <!-- boilerplate-only:line --> |
| 追記専用のレジストリ | `docs/adr/README.md` の表、`docs/spec/glossary.md`、`.github/settings/labels.json` | 両側の項目の和集合 —— **同じ鍵が両側に在る場合を除く**。それは Step 5 が人へ返す |
| 対訳ペア | `**/SKILL.ja.md` | canonical の `SKILL.md` を先に解決し、その後で対訳を見出し 1:1 へ戻す。**対訳を直接解決しない** |
| 実装 | それ以外すべて | **機械的でない。**マーカーを残して人へ返す |

**何かを解決する前に分類する。どの行にも当たらないパスは既定で実装である** —— 安全な向きだからである。
機械的な case を人へ返す費用はメッセージ 1 通、意味的な case を機械的に「解決」する費用は
**黙って間違ったマージ**である。

## Step 3 —— クラスごとに当てる

**依存の順に解決する。**いくつかのクラスは互いに供給し合う —— 契約の出典が `gen-api` より先、
`package.json` が `pnpm install` より先、マーカーを持つファイルがマーカーの基準より先、
トークンの入力がトークンのビルドより先。

生成物のクラスでは打ち手はどれも同じで、平明に述べる値打ちがある ——
**ファイルを merge するのではなく、衝突を消して作り直す。**出典を両側から取り（契約の出典、
`package.json`、トークンの入力）、**それが衝突していたなら*そちらを*解決し**、生成器を回して
成果物を作らせる。

pin の lockfile では、項目を突き合わせるのではなく **resolver を回す**。lockfile は tag → SHA の
キャッシュであり、手で merge すると**その tag に一度も対応したことのない SHA** を持つ項目が残りうる。
以後の検査はすべてそれを権威として扱う。

**staging はパスを明示して行う。**`git add -A` はどこでも禁じられている理由でここでも禁じられ、
マージの最中はなおさらである —— **自分が決めていない submodule のポインタを staging する。**

## Step 4 —— 衝突しなかったものを再生成する

Step 2 が何を見つけたかに関わらず回し、**回したことを述べる。**

```bash
make gen-api                                       # 契約から生成したもの
pnpm gen:tokens                                    # デザイントークンの生成物
pnpm exec tsx scripts/marker-baseline              # 差分が出たら --write で数え直す
```

派生した成果物が古くなるのは**もう一方の側の変更**によってであって、それとのテキストの衝突によって
ではない。**この段の不在が、手元では緑のマージと、次の無関係な PR での赤い CI を生む。**

## Step 5 —— resolver 自身が持つ検査を回す

```bash
make actions-pin-check
make images-pin-check
make version-stamp-check
```

**ここでゲートを回さない。**`pnpm lint:ci` / `pnpm md-lint` / テスト一式は hook と CI のもので、
判定は CI が正である（`AGENTS.md`）。上に挙げたものはそれより狭く、**種類が違う** ——
どれも **resolver 自身の整合検査**であり、**このスキルの機械的解決が実際に再現したかを言える
唯一のもの**である。**どれを回したかを述べる。**

## Step 6 —— 終わり方は 2 つ

実行は**ちょうど 2 つの状態のどちらか**で終わる。どちらになるかは**機械的に解けないものが残ったか**で
決まり、**どれだけ解決したかでは決まらない。**

### 残った → そこで止まる

残っているものを、**衝突マーカーを残したまま**報告し、実行を終える。

| 人へ返すもの | なぜ |
| --- | --- |
| 実装の衝突 | どちらの振る舞いが正しいかは読みであって、マージではない |
| 同じ鍵が両側で足された —— ADR 番号、語彙表の項、ラベル | 和集合は機械的だが、**どちらの定義が生き残るかを決めるのは違う** |
| ADR の採番のし直し | 採番の規約は `docs/adr/README.md` のもの。実行時に読み、食い違いは選ばずに提起する |
| 1 つの ref に解決できなかったベース | ベースを推測することが、ブランチが黙って別のラインをマージする経路そのものである |

> 機械的に解けるところまで統合しました。残りはここからお願いします: `<path>`（実装の意味的衝突）…

**この状態でコミットしない。申し出もしない。**衝突マーカーを抱えたマージコミットは履歴の中の
壊れた木であり、**解決済みに読める形で壊れている** —— このスキルが防ぐために在る失敗そのものが、
1 段上で起きる。人があなたが止めたところから続けられるよう作業ツリーをそのまま残し、
残りを解決してもらった後に「仕上げ」に再実行しない。**それはその人のコミットである。**

`git merge --abort` がここで deny されているのも同じ理由である —— **残していく木そのものが、
人への入力**だからである。

### 残らなかった → 聞いてから、コミットして push

**すべての衝突が解決し、Step 5 の resolver の検査が緑のときだけ。**

```text
質問: ベースとの統合が完了しました。コミットしてプッシュしますか？
選択肢:
  - コミットしてプッシュ
  - コミットのみ（プッシュしない）
  - 何もしない（作業ツリーのまま）
```

**毎回聞く。マージが成功したことを理由に push しない。**ブランチはリリースラインを取り込めても、
そのマージが機械の外へ出る準備ができているとは限らない。**このスキルにはその 2 つが区別できない** ——
結果がリモートへ届くべきかはブランチの状態についての話で、それは**著者の知識**であってマージの知識ではない。

push の側については、ブランチに既に pull request があるとき `AGENTS.md` がこの確認とその文言を要求する。

> 変更はローカルにコミット済みです。これらの変更をプルリクエストにプッシュしますか？

push は `--no-verify`。**コミットそのものは `commit` へ委ねる** —— このリポジトリの規約で分割し、
言葉を選ぶのはそちらである。

## やる / やらない

- ✅ ベースは `make base-merge` で取り込む。hotfix ラインが絡むなら `--base` を要求する。
- ✅ 何かを解決する前に、衝突した全パスを分類する。
- ✅ 生成物は片側を選ばず、出典から作り直す。
- ✅ pin の lockfile は resolver を回す。依存の lockfile より先に `package.json` を決める。
- ✅ 何も衝突していなくても派生物を再生成し、そうしたと述べる。
- ✅ どの行にも当たらないパスは実装として扱う。
- ✅ staging はパスを明示する。
- ✅ resolver 自身の検査を回し、どれを回したかを述べる。
- ✅ ちょうど 2 つの状態のどちらかで終わる。きれいなほうならコミット前に聞く。
- ✅ 日本語で報告する。
- ❌ 生成物・lockfile・submodule のポインタ・`SKILL.ja.md` を手で編集する / 片側を選ぶ。
- ❌ rebase / squash / force-push する。ブランチ自身のベース以外を取り込む。
- ❌ ゲートを回す —— それは hook と CI のものである。
- ❌ `git add -A` や `git merge --abort` を使う。
- ❌ 両側で衝突したレジストリの鍵の、どちらを採るかを決める。
- ❌ 実装コードの意味的な衝突を解く。
- ❌ 衝突マーカーが残っている状態でコミットする / 申し出る。
- ❌ マージが成功したから push する —— ブランチの準備は著者の知識である。
