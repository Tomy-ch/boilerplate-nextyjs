# Scaffold Integration Test

契約から生成された mock を通して 1 つの HTTP 継ぎ目を動かすテストを書き、そこで止まる。

同じディレクトリの `SKILL.ja.md` に日本語の参考訳がある（スキルとしては読み込まれない。人間の参照用）。

## 使用する場面

- `src/adapters/server/**` に新しい API クライアント関数が着地した（ADR 0024 の分割が実体化すればクライアント側も同様）
- `src/app/` 配下に Route Handler（`route.ts`）を足した
- `make api-gen` で契約を再生成して wire 型が変わり、その drift を捕まえられるテストが継ぎ目に要る
- 既存の継ぎ目が `fetch` を手書き stub する unit テストだけでカバーされており、境界そのものは生成ハンドラで一度も動かされていない

## このスキルを使わない場面

- **HTTP 境界を持たない純粋ロジック** — `scaffold-test`。retry ポリシーやペイロード整形は、`adapters` に居ても unit である
- **既にあるテストの評価** — `test-review`
- **MSW ハンドラの追加・編集** — ハンドラは契約から生成され、`mocks/handlers.ts` はそれを配線するだけ（`stableHandlers`）。手書きすると mock と契約が別々に動き始め、それこそが生成物で防いでいる failure である。ハンドラが無いなら、再生成すべきは契約の側
- **ブラウザの end-to-end** — Playwright であり、ADR 0090 の表の別の行

書き出すのは 1 ファイルだけで、sibling の命名規約（確立した形として `<subject>.contract.test.ts`）に従う。対象は **read-only**。

## 手順 0. 継ぎ目を解決し、それが継ぎ目であることを確かめる

引数から対象を採るか、`AskUserQuestion` で、契約テストをまだ持たないクライアントと Route Handler を選択肢として尋ねる。レイアウトが揃っている前提を置かず、実在するものを検出する —— ADR [0024](../../../docs/adr/0024-adapters-server-client-split.md) のクライアント側は決定が実体化した時点で作られ、Route Handler はそれを必要とする feature とともに現れる。

次に、それが本当に HTTP の継ぎ目かを確かめる。対象を読み、共有 fetch wrapper 経由でリクエストを出しているかを見る。**`adapters` 配下でもリクエストを出さないモジュールは integration の対象ではない** —— ペイロード整形、resilience ポリシー、circuit breaker は unit であり、`scaffold-test` の担当である。境界に何も無い結合テストを書くのではなく、そう言って止まる。

最近傍の `test-requirement` が `integration` であることを確かめる。そうでないのに対象が本当に継ぎ目なら、それはドキュメントの欠落である。報告したうえで続ける。

## 手順 1. 入力を読む

1. ADR 0090 と ADR 0091
2. `mocks/handlers.ts` / `mocks/node.ts` / `vitest.setup.msw.ts` —— 生成一式が何をカバーするかと、interception を起動しているのが **`vitest.setup.msw.ts`**（テストファイルが import する側）であることを把握する。`onUnhandledRequest: "error"` で走るので、生成一式が覆っていない宛先への要求は網へ出ずにテストが落ちる
3. 対象のソースを最後まで —— どのエンドポイントを呼び、何を検証し、何を正規化するか
4. 対象が `src/adapters/gen/**` から import している生成型
5. 構造テンプレートとしての sibling `*.contract.test.ts`

## 手順 2. 契約からケースを導出する

ケースは対象が呼ぶエンドポイントについて**契約**が宣言する応答ごとに 1 つ。対象の分岐ごとではない（そちらは `scaffold-test` の軸である）。

- **成功**: 呼び出し側が受け取る形。正規化後にアダプタが約束する型と構造をアサートし、生の wire 形ではない —— 継ぎ目の要点は wire 型が漏れないことである
- **宣言された各エラーステータス**: アダプタがそれを `errors` カーネルの定める正規化済みエラー種別へ写すこと。ステータスコードを内側へ露出させないこと
- **スキーマ不一致**: 生成 zod スキーマに合わない応答が境界で弾かれ、内側へ流れないこと。そもそも検証する理由がこのケースである
- **アダプタが行う正規化**: クエリの直列化、ページネーションのカーソル、ペイロードの整形 —— 生成一式がケース単位のハンドラ差し替えを許すなら、ハンドラが受け取ったものを通してアサートする

**形と型をアサートし、業務的な値はアサートしない。** 3 番目の商品の価格が 1200 かどうかは、写像関数の unit テストに属する。ここに属するのは、呼び出し側が約束された型を満たす整った page を受け取ること、そして壊れた応答が通り抜けないことである。

## 手順 3. 計画して確認を取る

書く前に書き出し先とケース一覧を見せ、`AskUserQuestion` で確認する:「この構成で結合テストを書きますか？」/「ケースを追加・修正したい」/「キャンセル」。

## 手順 4. ファイルを書く

手順 1 で読んだものを適用する。現時点の規約では次を指す。

- **最外の `describe` は対象 export の名前**。観点は `// ----- 正常系 -----` / `// ----- 異常系 -----` で区切る。`it` 文字列は日本語
- **MSW サーバを起動しない。** `vitest.setup.msw.ts` を import した時点で起動し、テストごとにハンドラを reset する。1 ケースだけ応答を割り当てるなら、受け取った要求も返す `serveJson(url, body)` を使い、後始末はテストごとの reset に任せる
- **既定は生成ハンドラの応答に任せる。** 応答を割り当てるのは、写しの分岐そのものを見るケースだけにする —— 生成の抽選に頼ると、モックの値域を変えるたびにテストが動く
- **mock するのはネットワークではなく設定。** 継ぎ目には固定のベース URL が要るので、sibling の契約テストと同じく `vi.hoisted` + `vi.mock` で `@/config/environment` を mock し、hoisting の順序が保たれるよう対象は mock の**後**で import する
- **`fetch` の手書き stub を作らない。** 生成ハンドラがそのエンドポイントを覆っていないなら、欠けているのは契約である
- **ログや span をアサートしない。** 継ぎ目の契約がテレメトリ自体である場合を除く

## 手順 5. 検証

```sh
pnpm fix
pnpm exec vitest run <書いたテストファイル>
pnpm exec vitest run --config vitest.scripts.config.ts scripts/one-to-one.gate.test.ts
```

ゲートの実行はここでも効く。最上位 `describe` がどの export も指していない契約テストは、対象ファイルが export を持つとき `unknown-describe` 違反になる。

何が走り何が走らなかったかを正直に報告する。とくに、そのエンドポイントの宣言された全エラーステータスにケースが付いたのか、それとも今の生成ハンドラ一式で作れるものだけなのかを述べる。

## 手順 6. 引き継ぐ

何を書き、継ぎ目が今どこに固定されたのかを述べる。そのうえで新しいファイルへの `test-review` を提案する。このスキルは契約からケースを導くが、`test-review` はアサーションが情報を持つか、層の責務が実際に確かめられているかを問う。

## 制約

- ✅ ADR 0090 / 0091、`mocks/**`、生成型、sibling の契約テストを実行時に読む
- ✅ 境界は生成ハンドラだけで動かす
- ✅ 継ぎ目では形と型をアサートし、値の正しさは unit テストへ残す
- ✅ 書く前にケース計画の確認を取る
- ❌ 対象・生成ハンドラ・`src/adapters/gen/**` の編集
- ❌ setup ファイルが既に起動している MSW サーバの再起動
- ❌ `fetch` stub やハンドラの手書き
- ❌ HTTP 境界を持たないモジュールへの結合テスト
