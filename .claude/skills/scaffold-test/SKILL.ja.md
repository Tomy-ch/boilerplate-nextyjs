# Scaffold Test

テストを持たない対象について、このリポジトリのゲートが既に強制している形でテストファイルを書く。

**作業の単位は集合である。** 画面は 20 余りの未テストモジュールを一度に伴って着地し、それを生んだ
手順は「テストを一斉に配置する」ことを求める。1 つの対象を解決するのは、要素数 1 の集合を通る同じ
経路にすぎない。

## いつ使うか

- 1:1 ゲートが callable な export について `missing-test-file` / `missing-describe` を報告している。
- 新しい関数 / component / hook / Server Action が着地し、そのテストがまだ書かれていない。
- `make test-full` がカバレッジ閾値で落ち、覆えていない分岐にケースが要る。
- ある対象のテストは既にあるが、同じファイルへ後から足した export にだけテストが無い。本スキルは
  既にある `describe` に触れず、欠けている `describe` を足す。
- 画面を実装し終え、リファクタリングと仕様書の後に、そのテストを 1 つの段として配置する。

## 本スキルを使わない場面

- **既にあるテストの良し悪しを判定する** — `test-review` の担当で、5 つの敵対的な観点を持つ。
- **HTTP 境界の結合テスト** — `adapters` のクライアントや Route Handler を MSW 経由で見るのは
  `scaffold-integration-test` の対象。本スキルは単体 / component テストを書く。
- **スイートを走らせる** — `make test-full` / `make scripts-test`。
- **対象の変更で壊れたテストを直す** — それを壊した変更の側の仕事であり、テストと振る舞いのどちらが
  誤っているかはその作者が知っている。

## 本スキルが読むもの・書くもの

以下はすべて**実行時に**読む。本ファイルの後ろにある一覧は規約の当て方を述べるものであって規約
そのものではなく、出所と食い違えば出所が勝つ —— ゲートが従うのは本スキルではなく出所の側である。

| 出所 | そこが決めること |
| --- | --- |
| [ADR 0090](../../../docs/adr/0090-testing-strategy.md) | `describe` = export 名、コメント区切りがどの軸を使うか、ケースの命名、skip / todo の規律、層ごとの責務、mock の境界 |
| [ADR 0091](../../../docs/adr/0091-test-verification-methods.md) | 非同期 RSC のテストの置き場、a11y 自動検査の組み込み方 |
| 最も近い祖先の `README.md` frontmatter（`test-requirement`） | 対象がどの層の責務に照らされるか |
| 1:1 ゲート自身 | 意図的に対象外としているもの（`RUNTIME_ONLY_MODULES` の glob が `src/app/**/page.tsx` を外している分を含む） |
| 同じディレクトリの兄弟テスト | その場に定着している形（fixture の書き方、ヘルパの signature、MSW の配線） |
| 対象のソース | ケースを導く分岐の集合 |
| `AGENTS.md` | `describe` / `it` の文字列は日本語 |

集合の各対象の隣へ `<subject>.test.ts`（または `.test.tsx`）を 1 つずつ書き出す。それ以外は書かない
—— fixture モジュールも、ディレクトリを跨いで共有するヘルパも、対象への編集も。

**対象は読み取り専用である。** シンボルをテスト可能にするために編集・改名・分割したり、余分な export
を足したりしない。書かれたままでは検証できないシンボルがあれば、そう言って止まる —— 手順 5 を見よ。

## 手順 0. 対象の集合を解決する

作業の単位は**集合**であって単一のシンボルではない。画面は 20 余りの未テストモジュールを一度に伴って
着地し、それを生んだ手順はテストを一斉に配置することを求める。対象 1 つは、要素数 1 の集合にすぎない。

除外の宣言を自分で読むのではなく、ゲートに何が欠けているかを尋ねる。

```sh
pnpm exec vitest run --config vitest.scripts.config.ts scripts/one-to-one.gate.test.ts
```

失敗の出力が `missing-test-file` / `missing-describe` の対象を `file:line` つきで列挙する。
**何にテストが要るかの権威はゲートである。** ゲートが報告しない対象は既に除外されている ——
`scripts/lib/untested-modules.ts` の明示的なパスによるか、同じファイルの glob 定数によるかのどちらか
（`RUNTIME_ONLY_MODULES` が `src/app/**/page.tsx` を外している。単体実行では描画できないため）。
除外を一覧から読み直すのは、実際に走るゲートと食い違う余地を招く。

### いま手にしている変更へ絞る

ゲートはリポジトリ全体を報告する。並行 worktree を持つ木では、他のセッションが作業中の対象もそこに
含まれ、それにテストを書くと相手の作業と衝突する。ゲートの出力を、このブランチが実際に触ったファイル
と突き合わせる。

```sh
git diff --name-only $(git merge-base HEAD origin/<base>)...HEAD
```

その交わりを提示する。ゲートがその外の対象を報告したら、**そう述べたうえで手を触れない** —— それは
他人のものであり、今回の対象から外れていること自体が利用者の欲しい情報である。

### 定数にも契約がある

ゲートが表に出すのは **callable** な export だけである。定数しか export しないモジュールは `describe`
を要求されず、テストが無くても現れない。利用者がそうした対象を名指ししたら受ける —— 定数の正確な
members と並び順は、ゲートが黙っていても押さえる価値がある。

### 各ファイルの置き場

- 対象 `src/foo/bar.ts` → `src/foo/bar.test.ts`
- JSX を描く対象 → `.test.tsx`
- テストは対象の**隣**に置く。`__tests__/` ディレクトリは ADR 0090 の違反である。

### 確認のために集合を群へ分ける

対象を、**それが従う `test-requirement` を宣言しているディレクトリ**ごとにまとめる —— 手順 1 が読むのと
同じ、最も近い祖先の宣言である。同じ群の対象は責務を共有するので、ケースの導き方も共有し、1 つの合意が
群の全体を運ぶ。

群が手順 3 の確認と手順 6 の検証の単位になる。22 の対象は、読めない 1 つの一覧でも 22 回の割り込みでも
なく、3〜4 回の判断になる。

**各群をどの runner が支配するかを控える。** 手順 6 のコマンドが変わるためである。`src/`（および既定の
`include` が挙げる他のルート）の下の対象は既定の config、`scripts/` の下の対象は
`vitest.scripts.config.ts` で走る。両方に跨る集合は、1 回ではなく 2 回の検証になる。

## 手順 1. 層の文脈を読む

1. 対象から遡り、frontmatter に `test-requirement` を持つ最も近い祖先の `README.md` を見つけ、
   frontmatter と本文の両方を読む。
2. ADR 0090 と ADR 0091 を読む。
3. 対象のソースを全部読む。
4. 同じディレクトリの兄弟テストを読む。

`test-requirement` がテストの負う責務を選ぶ。

| 値 | 責務 |
| --- | --- |
| `unit` | 純粋なロジック。返る値と投げるエラーの分類を検証する |
| `component` | Testing Library を通した描画と振る舞い。**加えて ADR 0091 が要求する `axe` の検証** |
| `integration` | HTTP 境界だけ —— 内側は mock し、形と型を検証する |
| `route` / `feature` | ADR 0090 の表のとおり —— 推測せず読むこと |

### 責務はディレクトリではなくシンボルに従う

`test-requirement` は frontmatter の一語であり、ディレクトリが抱えるシンボルはすべてが同じでは
ない。**その宣言が実際にどのシンボルへ掛かるのかを述べているのは README の本文である** ——
`src/adapters` は `integration` を宣言した上で、本文でそれを外部との往復を持つモジュールへ狭め、
純粋な変換は `unit` へ送っている。frontmatter だけでなく本文を読む。手順 1 が両方を求めているのは、
本文がそのためにあるからである。

これで決まるのはシンボルが負う**責務**である。シンボルを他のスキルへ渡すことではない。

### `integration` の責務は引き渡しではない

`scaffold-integration-test` はこのファイルの片割れではない。**別の問いを立てる、2 本目の別ファイル**を
書く。両方が既にあるディレクトリを `ls src/adapters/**/*.contract.test.ts` で探し、その `.test.ts`
の隣を読んで、思い込みではなく実物として確かめること。

| ファイル | 問い | 担当 |
| --- | --- | --- |
| `<subject>.test.ts` | 各 export が書かれたとおりに振る舞うか | **本スキル —— 境界を跨ぐものも含め、callable な export のすべて** |
| `<subject>.contract.test.ts` | 境界が生成された契約と合っているか | `scaffold-integration-test` |

**1:1 ゲートが解決するのは `<subject>.test.ts` だけである** —— 頼る前に `resolveTestFile`
(`scripts/lib/one-to-one.ts`) で確認すること。したがって contract 側にしか無い `describe` はゲートを
決して満たさず、境界を跨ぐシンボルを「もう一方のスキルへ」と残せばゲートは恒久的に赤いまま残る。
ここで書く —— HTTP はその層自身の境界で mock する —— そして契約テストも要るかどうかを締めの報告で
述べる。

**祖先が `test-requirement` をまったく宣言していない場合**は、兄弟テストと ADR 0090 から責務を導き、
宣言の欠落を報告する。責務を黙って発明しない —— 欠落そのものが所見である。

## 手順 2. 対象からケースの集合を導く

ケースの一覧は雛形からではなく、**対象自身の分岐**から組む。範囲内の export ごとに次を見る。

- すべての条件分岐、すべての早期 return、投げるエラーの分類すべて。
- 境界の対 —— 両側を取り、違う結果が出ることをケースが押さえるようにする。
- `null` / `undefined` / 空入力に対する防御すべて。
- component の場合: `components/README.md` の状態表に照らして、その component が**所有する** variant /
  状態それぞれ。loading / empty / error / success を所有しない component に、それらの状態を発明しない。
- hook の場合: 遷移する状態を、内部へ手を伸ばすのではなく描画結果を通して検証する。

**固有の検証を持たない分岐は覆えていない。** リポジトリはカバレッジを 100 % でゲートしているので、
「その行が走った」ことは何の情報も運ばない。情報を運ぶのは、**その**分岐を隣の分岐から区別する結果を
ケースが検証していること —— どのエラーか、どの描画状態か、どの値か。

**分岐を持たないシンボルにもテストは要る。** props を素通しするだけの component にも契約がある ——
どこへ渡すのか、既定は何か。

**ケースを束ねる軸は対象が何を返すかで変わり、それを決めるのは ADR 0090 である** —— 決まった 1 組へ
手を伸ばす前に、その「軸の選び方」を読むこと。現状では、**値**を返す対象は `正常系` / `異常系` で
分け、**描画**を返す対象はその軸で分けてはならない。描画する対象にとって上流の失敗は出す状態の 1 つ
なので、軸は状態になる（`// ----- 空のとき -----` とその仲間）。component のケースを `正常系` /
`異常系` に束ねることは ADR の ❌ に載っている。

`正常系` / `異常系` の軸が効く場合、割り当ては**ハッピーパスの内側か外側か**で行い、対象が失敗を
どう表現するかでは行わない —— throw も、エラー状態の返却も、値を黙って捨てることも同じ側に属する、
と ADR が明示している。

## 手順 3. 群ごとに計画し、確認を取る

確認は**群ごと**に取る。ファイル単位でも、集合の全体でもない。群に含まれる対象すべてについて、
書き出し先とケース一覧を示し、1 回の合意がその全部を覆うようにする。

```txt
群: <feature>/（test-requirement: feature）

書き出し先: <feature>/<期間を解く純関数>.test.ts
  describe("toPeriodRequest")
    ----- 正常系 -----
    - 日付の要らない区分はそのまま求められる形になる
    ----- 異常系 -----
    - range で日付が欠けていれば求めない
    - range で終了日が開始日より前なら求めない
  describe("toPeriodHref")
    ----- 正常系 -----
    - 日付を持ち越さない

書き出し先: <feature>/ui/<表の部品>/<表の部品>.test.tsx
  describe("RankingTable")
    ----- 空のとき -----
    - 行が無ければ、無いと判る文言を出す
    ----- 揃っているとき -----
    - 契約の並び順のまま順位を出す
    - 表として読み上げられる（axe）
```

上の 2 つの対象は同じ群にありながら**区切りが異なる**。軸は手順 2 のとおり、それぞれの対象が何を
返すかに従う。群は確認の単位であって、統一の単位ではない。

`AskUserQuestion` で確認する:「この構成で書きますか？」/「ケースを追加・修正したい」/
「この群は飛ばす」/「ここで止める」。計画は安く変えられるが、書いたファイルはそうではない。

**次の群を計画する前に、その群を書いて検証する。** 全群の計画を先にまとめると、この一括作業を成立
させているものを手放すことになる —— 最初の群がその場の形（fixture の書き方、兄弟がどう mock するか）
について教えることは、2 つ目の群の計画へ届くべきである。

**利用者が集合の途中で止めたら、どの群を書き、どの群を書いていないかを述べる。** 1:1 ゲートが赤の
まま途中で止まるのは正当な区切りだが、残りが名指しされている場合に限る。

## 手順 4. ファイルを書く

手順 1 で読んだものを適用する。現時点の規約では次を意味する。

- **最も外側の `describe` は export されたシンボル自身の名前**で、対象ごとに 1 つ。1 ファイルに複数の
  export があれば、ソースの順に複数のトップレベル `describe` を置く。
- **観点は手順 2 で定まった軸のコメント区切りで分け**、`it` は対象の
  `describe` の直下に置く。入れ子の `describe` は共有 setup の文脈にだけ使い、その文脈の名前を付ける。
- **`it` の文字列は日本語**で、振る舞い**と**分岐の条件を述べる。
- **1 つの `it` に 1 ケース。** `it.each` / `it.for` は、各ケースを識別する名前テンプレートを伴うなら
  よい。素の `it` を手書きの `for` / `forEach` で囲むのは不可。
- **層が所有する境界で mock する**: HTTP は MSW（`mocks/` の共有ハンドラ。`vitest.setup.ts` で配線
  済み —— `fetch` の stub を手書きしない）、モジュール境界は `vi.mock`、設定は `vi.stubEnv`。
- **component には `// @vitest-environment jsdom`** をファイル先頭に置き、ADR 0091 が要求する `axe` の
  検証を入れる。
- **利用者が要素へ辿り着くのと同じ引き方をする**: まず accessible name つきの `getByRole`、次に
  label / placeholder / text。`data-*` は accessible な手がかりを持たないものへの最後の手段。
  `fireEvent` より `user-event`、タイマーより `await waitFor` / `findBy*`。
- **ファイルを通すための skip を決して書かない。** 到達できない分岐があれば手順 5 である。

fixture は局所的で自明なものに保つ。複数のケースが共有するなら、ファイル先頭の fixture component や
builder はよい。共有の fixture モジュールを作るのは本スキルの仕事ではない。

## 手順 5. 書かれたままでは対象を検証できないとき

`vi.mock` / `vi.stubGlobal` では到達できない分岐がある —— モジュール読み込み時の副作用、`process.exit`、
実際のネットワークだけが生む値。**skip せず、対象も編集しない。** 所見として報告する。

- どの分岐か、なぜ `vi.mock` / `vi.stubGlobal` で到達できないかを名指しする。
- 到達可能にする抽出を提案する: 塞いでいる副作用を独自のモジュールへ移し、対象はそれを呼ぶだけにする。
  そうすればテストはその境界を mock し、そこまでの引数と分岐を検証できる。
- 判断は利用者に委ねる。抽出は production コードへの変更であり、本スキルの外にある。

これは ADR 0090 が `it.skip` に課すのと同じ基準である —— skip が許されるのは抽出しても残るものだけで、
「別のテストで覆えている」は理由にならない。

## 手順 6. 検証する

**各群のあとで**次を走らせる。形の誤りが次の群へ写される前に捕まえるためである。

```sh
pnpm fix                                      # 整形と自動修正可能な lint
pnpm exec vitest run <いま書いたファイル>       # 新しいケースが通る
```

手順 0 がその群について控えた runner を使う —— `scripts/` の下の対象は
`--config vitest.scripts.config.ts` が要り、それ以外は既定を使う。

分岐が実際に覆えていることを、その群の対象へ絞って確認する。

```sh
pnpm exec vitest run <いま書いたファイル> \
  --coverage.enabled --coverage.include='<対象のパス>' --coverage.reporter=text
```

対象ごとに 4 つの指標すべてが 100 % を示さなければならない。示さないならケースの集合が分岐を取り
逃している —— 基準を下げるのではなく手順 2 へ戻る。**カバレッジの実行は手にしている対象へ絞る。**
リポジトリ全体の数字はこの変更について何も言わず、並行 worktree を持つ木では他人に属する理由で赤い。

1:1 ゲートは**最後の群のあとに 1 度だけ**走らせる。

```sh
pnpm exec vitest run --config vitest.scripts.config.ts scripts/one-to-one.gate.test.ts
```

`describe` の名前が 1:1 の対応を満たすことを、これが示す。手順 0 で他セッションのものとして外した
対象は、なお報告されると想定する —— **それらを報告で名指しする**。説明の無い赤いゲートは、この実行の
失敗として読まれるからである。それ以外は残らないはずである。この実行が取った対象は、境界を跨ぐ
シンボルも含めて、ここで緑になることが期待される。

## 手順 7. レビューへ渡す

何を書き、何を検証し、何を所見として残したかを率直に述べる。そのうえで新しいファイルに対する
`test-review` を提案する。本スキルは対象の分岐から書くが、`test-review` は書いた側が自分の出力に対して
問えないことを問う —— 検証が意味を持つか、層の責務が実際に行使されているか。

## 制約

- ✅ ADR 0090 / 0091、`test-requirement` frontmatter、兄弟テストを実行時に読む
- ✅ 日本語の `it` 文字列、export 名の `describe`、ADR 0090 が割り当てる軸での区切り
- ✅ 書く前にケース計画の確認を取る（群ごと）
- ✅ 集合をこのブランチのファイルへ絞る。他セッションの対象には手を触れない
- ✅ 1:1 ゲートと対象ごとのカバレッジで検証する
- ❌ 対象を編集・改名・再構成する —— 常に読み取り専用
- ❌ ファイルを通すために `it.skip` / `it.todo` を書く
- ❌ 1:1 ゲートが欠落として報告しない対象にテストを書く
- ❌ MSW が境界を所有するところで `fetch` の stub を手書きする
- ❌ 本ファイルの一覧を規約として扱う —— 出所と食い違えば出所が勝つ
