# Submit PR

このスキルは、現在のブランチを `origin` に push し、対応する GitHub プルリクエストが存在することを保証する。次の 2 ケースを自動で判別して処理する。

- **Create**: 現在のブランチに対する PR が存在しない場合 → `-u` 付き push（upstream 未設定時）と新規 PR 作成を行う。
- **Update**: 既存の open PR が存在する場合 → ユーザーに確認してから push する（PR 上の diff は自動で更新される）。

そのいずれの前にも、ベースブランチを現在のブランチへ取り込む。レビューと push の対象を、実際に着地する状態と一致させるためである。

PR の本文は `.github/pull_request_template.md` をひな型にして埋める。自動 push は行わず、既存 PR のタイトル / 本文を勝手に上書きせず、force push もしない。

## 前提

- `gh` CLI がインストールされ、認証済みであること（`gh auth status` が成功する）。
- 現在のブランチが保護ブランチ（`production` / `develop` / `staging` / `release/*`）ではないこと。
- working tree がクリーンであること。未コミット変更がある場合はスキルを中断し、先に `/commit` を実行するよう促す。

## Step 0. 事前チェック

並列で実行:

```sh
git rev-parse --abbrev-ref HEAD                          # 現在のブランチ
git status --porcelain                                   # working tree の状態
git rev-parse --verify '@{u}' 2>/dev/null                # upstream の有無
git log '@{u}'..HEAD --oneline 2>/dev/null               # 未 push コミット（upstream がある場合）
gh auth status
```

以下のいずれかに該当する場合は中断する。

- ブランチが `^(production|develop|staging|release/.+|hotfix/.+)$` にマッチする → feature ブランチに切り替えるようユーザーに伝える。
- `git status --porcelain` が非空 → 先に `/commit`（または stash）を実行するようユーザーに伝える。
- `gh auth status` が失敗 → `gh auth login` の実行をユーザーに依頼する。

これらを最初に置くのは、後続がこれらに依存するためである。汚れた作業ツリーではマージできず、保護ブランチ上では何も実行してはならない。

Step 1 に進むときの状態は以下の 4 パターン。

| upstream | 未 push コミット | 意味 |
| --- | --- | --- |
| なし | n/a | 初回 push |
| あり | > 0 | 追加 push |
| あり | 0 | push 不要だが PR が未作成の可能性 |
| あり | 0 + PR open | 何もすることが無い（マージで件数が変わりうるため Step 2 の末尾で判定する） |

## Step 1. 既存 PR とベースブランチの検出

```sh
gh pr view --json number,state,baseRefName,headRefName,url,title,body 2>/dev/null
make -s base-branch
```

結果に応じて分岐する。

- **PR が存在し state が `OPEN`** → "update" 経路。ベースブランチは固定（結果の `baseRefName`）。PR の base は既にその PR がマージ先にしているブランチであり、何かが再解決してよいものではない。
- **PR が存在するが state が `MERGED` / `CLOSED`** → `AskUserQuestion` でユーザーに確認:
  - 質問: 「このブランチには `<state>` 状態の PR #N があります。新規 PR を作成しますか？」
  - 選択肢: 「新規 PR を作成する」 / 「キャンセル」
- **PR が存在しない** → "create" 経路。ベースは `make base-branch` が解決するブランチ、すなわち `origin` の実状態から読んだ最新のリリースライン。`gh repo view --json defaultBranchRef` は使わない。GitHub のデフォルトブランチは現行のリリースラインより遅れうるので、そこへ向けて PR を作ると 1 世代前のベースを対象にしてしまう。

`make base-branch` が失敗した場合は、ベースを推測せず報告して止める。間違ったブランチへ PR を作ってしまうと、PR を編集して取り消せる種類の失敗ではない。

"create" 経路では、解決したベースを `AskUserQuestion` で確認する。backport や意図的な hotfix 対象は、解決器が知りようのないケースだからである:

- 質問: 「ベースブランチをこれで作成しますか？」
- 選択肢: 「`<resolved-base>` を使う」 / 「別のブランチを指定する」

ベースブランチをここで確定させるのは、次のステップがそれをマージするためである。

## Step 2. ベースブランチの取り込み

Step 1 で確定した `<base>` を現在のブランチへ取り込む。レビュー・pre-push hook・CI が、実際に着地する状態を見るようにするためである。

```sh
git fetch origin --prune
git merge origin/<base> --no-edit
```

**ベースブランチを checkout も push もしない。** `release/**` をはじめとする保護ブランチは `CLAUDE.md` により push 禁止であり、`origin/<base>` をマージすれば現在のブランチだけが更新されるので、このステップにはそれで足りる。ここでいう「ベースの更新」とは `git fetch` によるリモート追跡参照の更新を指す。

結果ごとの扱い:

- **Already up to date** → その旨を伝えて次へ進む。空コミットは作らない。
- **マージ成功** → 取り込んだコミット数を報告する。生成されたマージコミットは Step 7 の push 対象に含まれるため、未 push コミット数は Step 0 の値を使い回さず、ここで取り直す。
- **コンフリクト** → **ここで停止し、利用者へ渡す。** このスキル自身は解消しない。コンフリクトしたパスを表示し、次を伝える。

  > ベースの取り込みでコンフリクトしました。`/resolve-merge` が機械的に解けるクラス（生成物・lockfile・pin・追記専用のレジストリ）を解決し、残りを返します。確定してから改めて `/submit-pr` を実行してください。

  **作業ツリーは MERGING のまま残し**、`git merge --abort` を勧めない —— その木は `resolve-merge` の
  入力であり、捨てるとこれから行う分類ごと失われる。

マージ後のコミット数に依存する早期終了は、ここで判定する。

- "update" 経路で未 push コミットが 0 件 → push する必要が無い旨を伝えて終了。既存 PR の URL を表示する。
- "create" 経路で未 push コミットが 0 件だがリモートブランチは存在 → 続行する（リモートに既にある内容で PR を作成する）。

## Step 3. push 前のローカルレビュー確認

ベースを取り込んだ状態で、**本文を組み立てる前、push する前**に、ローカルレビューを実行するか確認する。レビューは変更がマシンを離れる前に置くものであり、ここがレビュー 3 スキルを一度に見せる唯一の場所である —— どのスキルも他を提示しないので、1 つしか名指さないステップは、そこを通るたびに残り 2 つが黙って忘れられる場所になる。どれも自動実行はしない。

| スキル | 主題 | 見込み |
| --- | --- | --- |
| `/impl-review` | 変更そのもの —— correctness / security / architecture / cohesion / runtime gap | `src/**` の振る舞いが動いた、リクエスト時 seam やカーネル境界に触れたときは高い |
| `/test-review` | 変更を固定しているテスト | テストを書いた・書き換えたときは高い。差分がテストに触れていなければ低い |
| `/comment-sweep` | 触れたファイルが抱えるコメント在庫 | doc コメントが動いた・増えたときは中程度。機械的な変更では低い |

**3 つを見込み無しで並べず、差分から 1 つずつ値段を付ける。**「三つとも回しますか」は見積もりを付けずにコストをユーザーへ返す問いであり、`AGENTS.md` の Review Phase Protocol が禁じている形である。どれが効くと見ているか、どれが空振りと見ているか、その理由を述べる。

Step 2 の後に置くのは意図的である。取り込み前の状態をレビューすると、CI に到達しないツリーを見ることになる。

`AskUserQuestion`:

- 質問: 「push 前にローカルレビューを実行しますか？（実装者とは別モデルの独立・敵対レビュー。見込みは上表のとおり）」
- 選択肢:
  - 「`/impl-review` を実行する（submit-pr はキャンセル）」
  - 「`/test-review` を実行する（submit-pr はキャンセル）」
  - 「`/comment-sweep` を実行する（submit-pr はキャンセル）」
  - 「実行済み / 不要（このまま進める）」 — Step 4 へ進む
  - 「キャンセル」 — 中止

**レビューを 1 つでも選ばれたら submit-pr をキャンセルして案内する。レビュースキルをインラインで chain せず、この実行を再開しようともしない。** 選ばれたスキルを実行順に並べて次を表示する。

> submit-pr をキャンセルします。<選ばれたスキル> を実行し、指摘を修正してから `/commit` で確定し、改めて `/submit-pr` を実行してください。（clean tree でないと push できないため、レビュー修正の commit を先に済ませる必要があります。次回はこの Step 3 で「実行済み」を選べばそのまま進みます。ベースの取り込みは済んでいるので、次回の Step 2 は「Already up to date」で通ります。）

再開ではなくキャンセルにする理由: ローカルレビューは修正を生むことが多く、その修正は submit-pr が動く前に commit されている必要がある（Step 0 の clean tree 前提と Step 7 の push）。作業ツリーはどのみち変わるので「再開」するものが無い。修正を commit したあとの `/submit-pr` は、素通しで流れる安価な新規実行になる。

**変更種別による深さ** — 差分が触っているものに合わせて推奨を調整する。尺度は Step 10 の「変更種別による深さ」が定めるもので、両方の問いに同じ尺度が効く。

## Step 4. コンテキスト収集とテンプレート読み込み

タイトル・本文を組み立てるための入力を収集する。`<base>` は Step 1 で確定したベースブランチ。

```sh
git log <base>..HEAD --pretty=format:'%h %s'                # コミットタイトル
git log <base>..HEAD --pretty=format:'%h%n%s%n%b%n---'      # コミットタイトル + 本文
git diff <base>...HEAD --shortstat                          # diff サマリ
git diff <base>...HEAD --name-only                          # 変更ファイル
```

`.github/pull_request_template.md` を読み、`#` / `##` ヘッダでセクションを識別する。現行テンプレートは以下のセクションを持つ。

- `# 概要`
- `## 変更内容`
- `## 動作確認方法`

HTML コメントのプレースホルダは除去する。テンプレートが無い場合は同じ 3 セクション構成をインラインで用いる。

## Step 5. タイトルと本文の生成

### タイトル

- もっとも重要な変更から導く。単一コミットの PR → そのコミットのタイトルを使う（先頭の `<Prefix>:` は冗長な場合のみ落とす）。複数コミットの PR → 全体の意図を日本語で要約する。
- 70 文字以内。
- ブランチ名に issue 番号が埋まっている場合（`feature/1234-...`、`bugfix/5678-...`）、タイトルに `#1234` を自然に含める。
- "update" 経路では、利用者が明示的に変更を求めない限り既存 PR のタイトルを変えない。

### 本文

テンプレートの各セクションを日本語で埋める。

- **概要**: PR の意図を 1〜3 文で要約する。コミットメッセージを一次情報にする。
- **変更内容**: 領域ごと（API / DB / 内部ロジック / テスト / ドキュメント など）に箇条書きでまとめる。変更ファイルとコミットタイトルを参照する。意味のある単位でまとめ、生のファイル一覧を貼らない。Step 2 が生成したマージコミットはこの PR の変更ではないので、列挙しない。
- **動作確認方法**: 具体的な確認手順。実際に変わったものに合わせる。UI の変更なら `pnpm dev` と開く画面、production build を壊しうる変更なら `pnpm build`、それ以外は `pnpm lint:ci` / `pnpm typecheck`。

ブランチ名が issue 番号を含む場合、本文末尾に `closes #N` を付ける（自然なら概要へ畳んでもよい）。

## Step 6. ユーザー確認

ローカルレビューの可否は Step 3 で判断済みである。ここで再度訊かない。

確定したタイトル、ベースブランチ、push コマンド、本文全体を表示する。Step 2 で何かを取り込んだ場合はその旨も伝え、push にマージコミットが含まれることが分かるようにする。

### create パス

`AskUserQuestion`:

- 質問: 「以下の内容で PR を作成しますか？」
- 選択肢:
  - 「この内容で作成する」
  - 「draft で作成する」
  - 「title / body を修正したい」
  - 「キャンセル」

「修正したい」が選ばれた場合はフリーテキストで指摘を受け取り、該当セクションを作り直して再確認する。

#### 描画が変わる差分なら `baseline-retake` ラベルを提案する

差分が story の見え方を変えうるかを判断する（`src/components/**` や feature の `ui/` の `.tsx`、design token、Tailwind のクラス、story の新設・改名）。変えうる場合は、同じ確認の回で訊く。

- 質問: 「見た目が変わる変更ですか？（`baseline-retake` ラベルを付けて PR を作成します）」
- 選択肢: 「付ける」 / 「付けない」

`gh pr create --label baseline-retake` で付ける。このラベルは VRT Retake ワークフローの**トリガではなく条件**である。ワークフローは VRT の完了で発火するため、先に付けておけば、実行の完了を待って人がラベルを付け直す必要が無くなる。見送りも越える: 他のチェックが落ちている間は撮らずにラベルを残すので、そのチェックを直せば次の実行で再開する。

**見た目の変更を承認するものとして提示しない。** retake は差分をレビュー可能な画像差分にするだけで、承認の前に置き場の compare ビューを見るのは利用者である。Step 9 の報告でそう添える。

### update パス

未 push のコミット一覧と diff サマリを表示する。そのうえで `CLAUDE.md` が求める文言で確認する。

- 質問: 「変更はローカルにコミット済みです。これらの変更をプルリクエストにプッシュしますか？」
- 選択肢: 「push する」 / 「キャンセル」

## Step 7. push

```sh
# 初回 push（upstream 無し）
git push -u origin <branch>

# 2 回目以降
git push
```

`origin/release/*` から切ったブランチ（`commit` のマージ済み PR からの復帰フロー）は upstream がその**保護**ベースを指しているため、素の `git push` は保護ブランチへ向かってしまう。初回 push は必ず `git push -u origin <branch>` と refspec を明示して upstream を feature ブランチへ張り替える。素の `git push` が安全なのはそのあとである。

利用者が明示的に要求しない限り `--force` / `--force-with-lease` は使わない。

push が失敗した場合（non-fast-forward、権限不足、ネットワークエラー等）は、エラーをそのまま利用者へ報告して停止する。自動復旧を試みない。

### 検証は pre-push hook が担う — 先回りしない

`pre-push` は lefthook 経由で重いゲート（`pnpm typecheck` / `make test-full` / `make secret-scan`）を回す。判定は hook に任せる。

「念のため」に `pnpm lint:ci` / `make test-full` を手で回さない。ウィンドウを複数開いている状況では、CI が同じことをするのを数分ホストを飽和させて再発見するだけであり、その飽和自体が無関係なゲートを落とす（`repo-ops` §7）。**push そのものが検証である。**

**hook がこの変更の外側の理由で落ちた場合** — 別セッションが編集中の未コミットファイル、同じ `coverage/` を奪い合う 2 つの Vitest、`PATH` に無いツール — その失敗は push しようとしている変更の話ではない。`--no-verify` の例外扱いとその条件は `repo-ops` §7 が持つ。どのゲートがなぜこの変更の外側なのかを報告し、判断は利用者に委ねる。黙って例外を使わない。

## Step 8. PR の作成 / 更新

### PR の作成

```sh
gh pr create \
  --base "<base-branch>" \
  --title "<title>" \
  --body "$(cat <<'EOF'
<body>
EOF
)" [--draft] [--label baseline-retake]
```

### PR の更新

Step 7 の push で PR の diff は既に更新されている。既定では PR のタイトル・本文に触れない。

利用者が明示的に更新を求めた場合にのみ実行する。

```sh
gh pr edit <number> [--title "<new-title>"] [--body "$(cat <<'EOF'
<new-body>
EOF
)"]
```

## Step 9. 結果報告

PR の URL と短い要約を日本語で表示する。

create 経路:

```text
PR を作成しました: <url>
ベース: <base-branch>
タイトル: <title>
コミット数: N
```

update 経路:

```text
PR を更新しました: <url>
追加コミット数: N
```

Step 2 でベースを取り込んだ場合は、取り込んだコミット数を 1 行添える。

## Step 10. PR 後レビュー（確認）

PR の URL を報告したあと、**必ずレビューを実行するか確認する**。省略せず、自動実行もしない。`AskUserQuestion` を使う。

- 質問: 「PR を作成/更新しました。コードレビューを実行しますか？」
- 選択肢（該当するものを出す）:
  - 「`/impl-review` を実行」 — ローカル差分を実装者と別モデルで敵対的にレビューする。対象は変更そのもの（モックテストが見落とす auth / IDOR / 境界 / ランタイムのギャップに強い）。既定で残った指摘を PR のインラインコメントとして投稿する（`--no-comment` で抑止）
  - 「`/test-review` を実行」 — 変更を固定しているテスト。独立した主題を持つ別スキル
  - 「`/comment-sweep` を実行」 — 触れたファイルが抱えるコメント在庫
  - 「`/code-review <PR#>` を実行」 — PR ベースのレビュー（`--comment` でインラインコメント投稿可）
  - 「ultrareview を案内」 — クラウドのマルチエージェントレビュー。**利用者が起動するものであり課金対象**なので、スキルからは起動できない。コマンドを提示するに留める
  - 「レビューしない」

### 変更種別による深さ

変わったものに合わせて推奨する深さを調整する（ソース全面レビューを 10 とした場合）。

- **振る舞いを変えるコード**（`src/**` の `.ts` / `.tsx`、Server Action、Route Handler、`adapters`）→ 全面（10）。既定でレビューを勧める
- **ドキュメント / ツール中心の変更**（`docs/**`、`*.md`、`.claude/**`、`AGENTS.md`、CI 設定 — 本番の振る舞いを変えない）→ 浅くてよい（7〜8/10 程度）。それでも訊くが、ROI が低いことを添えて素早く判断できるようにする

差分の主たる性質（変更ファイルのパス / commit prefix）で既定の推奨を決めるが、利用者の選択が常に優先する。

## 制約

- ❌ 保護ブランチ（`production` / `develop` / `staging` / `release/*`）への push
- ❌ ベースを更新するために保護ブランチを checkout すること — 代わりに `origin/<base>` を現在のブランチへマージする
- ❌ ベース取り込みのコンフリクトをここで解消する / MERGING のツリーを捨てる（利用者へ渡して停止する。機械的なクラスは `resolve-merge` が所有する）
- ❌ `git push --force` / `--force-with-lease`（利用者の明示的な指示がある場合のみ）
- ❌ 既存 PR のタイトル・本文の自動更新（明示的な要求がある場合のみ）
- ❌ working tree に未コミット変更がある状態での push
- ❌ ユーザー確認なしの PR 作成
- ❌ `CLAUDE.md` が求める文言で再確認せずに既存 PR ブランチへ push すること
- ✅ レビューと push の前にベースブランチを取り込む
- ✅ `.github/pull_request_template.md` を本文のひな型として使う
- ✅ タイトル・本文は日本語
- ✅ `gh pr create` / `gh pr edit` の本文は HEREDOC で渡す
- ✅ ブランチ名から issue 番号を検出し、タイトル / 本文に反映する
- ✅ 描画が変わりうる差分なら、作成時に `baseline-retake` ラベルの要否を提案する
- ❌ `baseline-retake` ラベルを「見た目の変更の承認」として提示すること（差分をレビュー可能にするだけ）

## チェックリスト

完了を報告する前に、以下を確認する。

- [ ] 現在のブランチが保護ブランチでない
- [ ] push 前に working tree がクリーンだった
- [ ] `gh auth status` が通った
- [ ] Step 2 でベースを取り込んだ（または「Already up to date」を確認した）。保護ブランチは checkout も push もしていない
- [ ] PR テンプレートを読み、本文に反映した
- [ ] タイトル・本文が日本語
- [ ] タイトルが 70 文字以内
- [ ] Step 3 で push 前のローカルレビュー 3 本の実行可否を、見込み付きで確認した（レビューを選んだ場合は submit-pr をキャンセルして案内した）
- [ ] push 前にユーザー確認を得た（update 経路では `CLAUDE.md` により必須）
- [ ] 見た目が変わりうる差分なら `baseline-retake` ラベルの要否を確認した（承認ではないことを添えて）
- [ ] PR の URL を利用者へ報告した
- [ ] （必須）PR 作成/更新後にレビュー実行可否を確認した（深さは変更種別でスケール）
- [ ] `--force` を使っていない
