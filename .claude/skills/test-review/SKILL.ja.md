# Test Review

このリポジトリのテストファイルに対する、敵対的で偏りの少ないレビュー。壊れている・検証が薄い・実質何も確かめていない箇所を洗い出し、確認を 1 回取ったうえで、見つけた意味論の穴をレポートのまま残さず塞ぐ。

同じディレクトリの `SKILL.ja.md` に日本語の参考訳がある（スキルとしては読み込まれない。人間の参照用）。

## 使用する場面

- commit / PR の前に、その変更に含まれるテストファイルへ
- **カバレッジが 100% なのにリグレッションが出るとき。** このリポジトリの 100% カバレッジゲート（`make test-full`）の下ではカバレッジはアサーションについて何も語らない —— Lens 4 Axis B はまさにその盲点のために存在する
- カーネルや component ディレクトリ単位の単独監査として

## このスキルを使わない場面

- **実装コードのレビュー** — `impl-review` の担当
- **テストの実行** — `make test-full` の担当。このスキルはテストを読むだけで、実行しない
- **テストの作成・修正** — ファイルを一切編集しない。適用は利用者が行う

## このスキルが読むもの

規則の出所は ADR と [`docs/testing-conventions.md`](../../../docs/testing-conventions.md) とカーネル README であり、実行時に読む。

| 出所 | 何を決めるか |
| --- | --- |
| [ADR 0090](../../../docs/adr/0090-testing-strategy.md) | フレームワークの分担（Vitest / RTL / MSW / Playwright）、export 名の `describe`、`正常系` / `異常系` のコメント区切り、ケースごとの命名、1 対象 1 テスト、skip / todo の規律、層別責務、integration = HTTP 境界のみ |
| [ADR 0091](../../../docs/adr/0091-test-verification-methods.md) | 非同期 RSC テストの置き場、a11y 自動検査の組込 |
| カーネル `README.md` の frontmatter（`test-requirement: unit \| component \| integration \| route \| feature`） | 対象がどのテスト層に属するか |
| [AGENTS.md](../../../AGENTS.md) | `describe` / `it` の文字列は日本語 |
| 同じディレクトリの sibling テスト | その場所で確立している書き方（fixture の形、helper の signature、MSW の配線） |
| subject のソース | コード起点の 2 レンズが必要とする |

**別の言語の文化に属するテスト規約を持ち込まないこと。** 別のランナーの都合を回避するために在る規則は、ここには当たらない —— Vitest はファイルを既定で並列に走らせ（テストごとの opt-in を要求する相手がいない）、`expect` は 1 つで（致命 / 非致命のアサーションの使い分けが無い）、mock の境界は生成スタブ型ではなく MSW である。

**規則の出所が沈黙している箇所では、規則を発明せず「無い」と報告する。** 意味的品質の基準は `docs/testing-conventions.md` が持つので、Lens 3 は一般原則ではなく**その文書**を当てる。届かない範囲は補遺でギャップとして報告し、リポジトリの方針であるかのように規則を持ち込んではならない（`docs/rules.md`「作業とエージェント」= 導出できない領域に独自の規約を持ち込まない）。

## 書き出すもの

無し。成果物は会話へ描画される日本語レポートだけである。

## Step 0. スコープの解決

何より先に、この実行が越える境界を打刻する: `.agents/closed-loop/marks.sh reviewStartedAt`。 <!-- boilerplate-only:line -->

`AskUserQuestion`:

- 質問: 「test-review の対象スコープを指定してください」
- 選択肢:
  - 「変更ファイル (HEAD-vs-working tree, 推奨)」 — `git diff --name-only` から `*.test.ts` / `*.test.tsx` を抽出。新規追加（`--diff-filter=A`）も含める
  - 「ブランチ base 比較」 — base は `gh pr view --json baseRefName -q .baseRefName`、PR が無ければ `make -s base-branch` で解く（`gh repo view --json defaultBranchRef` は使わない）。その base との `git merge-base` 以降に touch されたテスト
  - 「レビュー指摘への対応分」 — 前回レビューの最終コミット `...HEAD`。反映そのものが未レビューである（`AGENTS.md` の Review Phase Protocol）
  - 「特定パス / ディレクトリ (free-text)」
  - 「キャンセル」

スコープにテストが 1 件も無ければ、レビュー対象が無いので停止する。続行する唯一の場合は、スコープが**ペアテストを持たない production ファイル**のときである —— テストの無い subject こそが Lens 5 の対象であり、Lens 1–3 はそのファイルについて読むものが無い（合格と読める空の結果を返すのではなく、そのファイルについては起動しない）。

対象ごとに **subject のソース**（同じディレクトリの、`.test` を除いた basename）を解決する。Lens 4 / 5 が必要とする。

## Step 1. 層の文脈を読む

対象ごとに:

1. ファイルから遡って最も近いカーネル `README.md` を見つけ、`test-requirement` frontmatter と本文を読む
2. ADR 0090 と ADR 0091 を実行ごとに 1 回読む
3. subject のソースを読む
4. 同じディレクトリの sibling テストを読む

`test-requirement` が ADR 0090 の層別表を引く鍵である。`unit` のカーネルと `component` のカーネルは同じ観点を負わないし、`integration` を宣言するカーネル配下の対象は「HTTP 境界のみ / 内側は mock / 型・形状をアサート」に縛られる。

## Step 2. 敵対的レビュアーを 5 つ並列に立てる

`adversarial-reviewer` の subagent を 5 つ**並列**に起動する。既定は `sonnet` で、Opus の実装者とレビュアーが別モデルになるようにする。全員が Step 1 の同じ文脈を受け取り、レンズだけが異なる。

うち 2 つは**コード起点**で、subject のソースから始める。したがってテストが 1 つも無いコードも視野に入る。これはテストファイルから読み始める方式では構造上見えない盲点である。

### Lens 1: 構造準拠

ADR 0090 への機械的な適合。今回の実行で読み、その時点の記述を適用する。規則は「テストの構成: export ↔ describe の 1:1 対応」節（export 名の `describe`、入れ子の `describe` ではなくコメント区切り、対象が `正常系` / `異常系` で割れるか表示状態で割れるかを決める「軸の選び方」、ケースがどちら側に居るか、ケースごとの命名、skip / todo の規律）、「mock 戦略」（MSW 境界）、「配置・命名」（co-location）、「禁止事項」の一覧が持ち、ケース名が日本語であることは `AGENTS.md` の Language Rules が持つ。このレンズは規則の写しを持たない —— finding は違反した節を引き、ADR が沈黙している範囲は補遺へ回す。

**ゲートが既に落とすものを再報告しない。** `scripts/one-to-one.gate.test.ts` が名前レベルの 4 形（`missing-test-file` / `missing-describe` / `duplicate-describe` / `unknown-describe`。最上位の `正常系` 束ねはここに落ちる）を機械判定する。それらは CI で既に赤なので言及は 1 行に留め、このレンズはゲートが読めないもの — 区切りによる束ね、ケースがどちら側に居るか、ケース名の質、ケースごとの命名、skip / todo の規律、MSW 境界、co-location — に使う。**テストが 1 つも無い subject は Lens 5 の所管**であり、このレンズは既にあるテストの形だけを見る（二重報告しないため）。

出力: `file:line` と違反した規則。

### Lens 2: 観点カバレッジ

層が負うものと、テストが実際に確かめているものを突き合わせる。

- カーネルの `test-requirement` が ADR 0090 の層別表の行を選ぶ。その行の責務（unit = 純粋ロジック、component = 描画・振る舞い、integration = HTTP 境界の型・形状、route / feature は ADR に従う）に照らす
- component のテストでは、ADR 0091 により a11y 自動検査が責務に含まれる。`axe` のアサーションが無い component テストは観点の欠落である
- `components/README.md` が「どの UI がどの状態を所有するか」を定めている。loading / empty / error / success を所有する component はそれらを確かめる必要があり、所有しない component に無意味な state ケースを作ってはならない。component が対象のときは読む

**観点はカーネル README の `test-requirement` frontmatter から取る。** ADR と frontmatter から観点を導けない対象については、黙って何も返さず（合格と読めてしまう）、補遺でドキュメントの欠落として報告する。

**宣言とテストが食い違うときは、次の規則で裁定する。** 都度の判断にしないのは、同じ状況が 2 つのディレクトリで別々に決着するのを避けるためである。どの規則を適用したかを書く。

- **テストが設計として妥当 → 宣言を直す。** テストの取っている方法がアーキテクチャ上正当なら、実態を記述できていないのは宣言の側である。README の修正（通常はそのディレクトリに自前の `test-requirement` を持たせる）を提案し、方法そのものではなく**その方法を選ぶ基準**を提案する。次に同じ状況へ来たディレクトリが、前例の模倣ではなく規則を適用できるようにするため
- **宣言が正しい意図 → テストを直す。** 逸脱に設計上の正当性が無いなら、宣言が「そうあるべき姿」である。テストをそれに合わせる
- **継承した宣言は、前提が成り立つ範囲でだけ支配する。** 最も近い祖先の `test-requirement` が下位ディレクトリに及ぶのは、その前提が実際にそこで成り立つときだけである。HTTP 境界の adapter のために書かれた `integration` の宣言は、純粋な整形ヘルパだけを持つ隣のディレクトリを支配しない。walk で**形式的に**解決できることは、その宣言が適用されることと同じではない。適用できない最近傍の宣言は、欠落しているのと同じに扱い、そのディレクトリに自前の frontmatter を持たせて閉じる
- **カーネルでないディレクトリも自分の観点を持つ。** `scripts/` / `tokens/` / `docs-viewer/` は構造上、上位にカーネル README を持たない。観点はそれぞれの README に属し、無いことは報告すべき欠落である — 何も基準が無いままレビューしてよい、という許可ではない

どちらへ裁定したか、その理由は、変更する PR に書く。README には書かず、このレポートにも規則名の 1 行を越えて書かない。

出力: 層が負っているのにテストが確かめていない観点。

### Lens 3: 意味的品質

アサーションに意味があるか。**基準は `docs/testing-conventions.md`** であり、今回の実行で読んでその現行本文を当てる。弱い / 空振りのアサーションは「アサーションの強さ」、component / hook が対象のときは「component / hook のテスト — Testing Library の原則」（指摘では文書と原則を名前で引く）、過剰な mock は「mock の境界」が持つ。このレンズは規則の写しを持たない。文書が沈黙している範囲は、規則を発明せず補遺でギャップとして報告する。

出力: `file:line` と、なぜ弱いかの一文。

### Lens 4: 分岐 × 意味の網羅（コード起点）

subject のソースを読み、関数ごとに 2 軸の行列を作る。**カバレッジ ≠ 意味**（基準は `docs/testing-conventions.md`「意味網羅 — カバレッジは情報を持たない」。行列はこのレンズによるその適用）であり、100% ゲートを敷いたリポジトリではこの区別だけが情報を持つ。

**Lens 5 との分担**: Lens 4 は既にテストがある symbol の*内側*を見る。「テストが 1 つも無い」は Lens 5 の finding であり、Lens 5 が挙げた symbol の分岐をここで列挙し直さない（それは 1 件のギャップであって N 件ではない）。

**Axis A — 分岐網羅**: すべての論理分岐が少なくとも 1 ケースで到達される。あらゆる条件分岐、投げるエラーの種類、境界の対、nil / 空入力への防御。本体を実行しない harness だけが通る分岐はカバーされていない。

カバーするケースが無い分岐は **分岐未カバー** → severity **追加検討**。subject の `file:line` を引用し、`it` の名前を提案する。**criticality (1-10)** を本番影響で採点して添える（severity が「どの種類のギャップか」を言うのに対し、criticality は「壊れたらどれだけ悪いか」を言う直交軸）。壊れた場合に出荷されるリグレッションを一行で添える: 9-10 データ破壊 / 認証・認可の穴 · 7-8 ユーザ影響のあるロジック誤り · 5-6 軽微な edge · 3-4 網羅性のための nice-to-have · 1-2 任意。追加検討は criticality 降順に並べる。修正必須には criticality を付けない（常に今直す対象だから）。

**Axis B — 意味網羅**: カバー済みの各分岐のケースが、その分岐の*固有の* outcome をアサートしているか。

- エラー分岐は「どのエラーか」をアサートする。投げたことだけでは足りない
- 成功分岐は、他の分岐と区別できる結果の値や DOM 状態をアサートする
- 状態を変えるハンドラは、変更後の状態をアサートする。呼ばれたことだけでは足りない
- 境界のケースは、境界の両側で異なる結果をアサートする

カバーされているが固有の outcome をアサートしていない分岐は **分岐カバー済み・意味未検証** → severity **再考**。対象の分岐と、名目上それをカバーしているケースを結び付ける。

### Lens 5: subject シンボル網羅（コード起点）

subject のソースから、*symbol* の粒度で始める。答えるのは「そもそもテストが存在するか」の一点である。テストファイルから読み始める方式は見つけたテストしか判定できず、テストが 0 の symbol は見えない。

1. ペアになる subject から export シンボルの表を作る（export された関数・component・hook、および分岐ロジックを持つモジュールレベルの非 export 関数）。生成ファイルとテスト専用 helper は対象外
2. 各シンボルをテストに突き合わせる
3. 突き合わないシンボルを **シンボル未カバー** → severity **補完推奨** として挙げる。`symbol @ file:line` を引用し、`describe` 名（シンボル自身の名前）と `// ----- 正常系 -----` / `// ----- 異常系 -----` で区切った `it` の骨子を提案し、Lens 4 と同じ criticality を付す。criticality 降順に並べる

## Step 3. finding ごとに検証する

生き残った finding は、独立した `review-verifier` subagent（`sonnet`）へ渡す。finder を信用せずコードから結論を導き直し、**既定で懐疑的に倒す** — 曖昧さが残るなら PLAUSIBLE か REFUTED を付ける。

検証は finding 間で並列に走らせる。REFUTED はレポートから落とし、件数だけ伝えてノイズの水準を示す。CONFIRMED と PLAUSIBLE は残す。

## Step 4. レポートを合成する

日本語のレポート 1 本。

```text
# Test Review レポート

対象: <スコープ + ファイル一覧>
レンズ: 構造準拠 / 観点カバレッジ / 意味的品質 / 分岐×意味 / シンボル網羅
verifier 通過: CONFIRMED <n> 件 / PLAUSIBLE <m> 件 / REFUTED <k> 件（除外済み）

## サマリ
- 修正必須 / 補完推奨 / 再考 / 追加検討: 各 <件数>

## 構造準拠（修正必須）
## 観点カバレッジ（補完推奨）
## 意味的品質（再考）
## シンボル網羅（補完推奨）  ← criticality 降順
## 分岐網羅（追加検討）      ← criticality 降順
## 意味網羅（再考）

## 補遺
- <ADR / README / testing-conventions.md の補完候補>
```

severity の対応:

- **修正必須** — Lens 1。ADR 0090 の規則違反。CONFIRMED → 修正必須 / PLAUSIBLE → 確認推奨
- **補完推奨** — Lens 2 と Lens 5。層が負う観点が未実施、またはシンボルにテストが 1 つも無い
- **再考** — Lens 3 と Lens 4 Axis B。通るが何も明らかにしない
- **追加検討** — Lens 4 Axis A。subject 起点で見つけた未カバー分岐

## Step 5. 意味論の穴を塞ぐ（既定。ユーザーが断れば飛ばす）

**報告しただけで誰も塞がない穴は、また作られる。** このリポジトリのテストは基本的に AI が書くため、同じ形のコードを次に書いたときに同じアサーション漏れが再生産される。したがって「アサーションが無い・空振りしている」種類の finding について、報告は終着点ではない。

この step の対象:

- **再考** — Lens 3（弱い / 空振りのアサーション）と Lens 4 Axis B（カバー済みだが固有の結果を見ていない）
- **追加検討** — Lens 4 Axis A（カバーするケースが無い分岐）

対象外（報告のみ）:

- **修正必須**（Lens 1）— 構造規則の違反は既存ケースの書き換えであり、どちらへ倒すかが ADR 改訂に依存しうる（Lens 2 の裁定規則）。利用者に委ねる
- **補完推奨**（Lens 2 / Lens 5）— テストが 1 つも無いシンボルは `scaffold-test` の担当で、層の観点の欠落は宣言側の誤りかもしれない

編集の前に 1 回だけ確認する:

- `AskUserQuestion`:「意味網羅の穴 <N> 件にテストを追加しますか？」— 選択肢:「すべて追加」/「1 件ずつ確認」/「追加しない（レポートのみ）」

その後、finding ごとに:

1. subject の既存 `describe` の下に、結果が決める側（ADR 0090）へ、日本語の `it` 名でケースを足す
2. **そのケースが役に立つことを示す。** 対象の分岐を壊し（条件を反転する、ガードを落とす）、新しいケースが落ちることを確かめてから戻す。壊した実装に対しても通るケースは何も検証していないので残さない。何を壊してどう落ちたかを報告する
3. 場所を空けるために既存のケースを弱めない。削除もしない

編集後に検証する: `pnpm fix`、`pnpm lint:ci`、対象自身のテスト実行。**コミットはしない** — 変更は利用者（あるいは後続の `/commit`）へ残す。

利用者が断ったら飛ばし、黙って省かずレポートにそう書く。

## Step 6. 次の一手

Step 5 が塞が**なかった**もの — 修正必須と補完推奨 — について、具体的な提案を 1 つだけ添えて終える。対象ファイルと追加すべきケースを名指しし、テストが 1 つも無いシンボルは `scaffold-test` へ向ける。検証を通過した finding が無ければ、そう言う（「verifier 通過後 0 件です」）。

## 他のレビュースキルとの関係

このスキルは**テスト**を所管し、所管するのはこのスキルだけである。どのレビュースキルもテストのレンズを持たず、このスキルは他のスキルの内側からではなく単体で呼ばれる。`/impl-review`（変更そのもの）と `/comment-sweep`（コメント在庫）は `AGENTS.md` の Review Phase Protocol における対等な相方であり、別々に問われ、別々に決められ、互いに委譲しない。

Lens 5 が「テストが 1 つも無い」を、Lens 4 が分岐 × 意味を所管し、どちらの形にも報告者はちょうど 1 つである。このスキルは他へ chain しない。

## 制約

- ❌ Step 5 の範囲外の編集。報告は read-only で、塞ぐのは意味論の穴だけ、確認の後だけ、テストファイルの中だけ
- ❌ テストの実行（`make test-full` は別の重い gate — `repo-ops` §7）
