# Verify Spec

**約束と実装を読み合わせ**、もう一致していないところを報告する。

canonical はこのディレクトリの `SKILL.md`（英語）。規約の正はそちらで、この訳は参考である。

## 使うとき

- リリース前 —— **全画面をその約束に対して読む唯一の時点**。
- 画面の観測可能な振る舞いが変わった後。
- 仕様書と画面が食い違って見えるとき。

## Contract

| | |
| --- | --- |
| **Owns** | 仕様書の約束と実装の**読み合わせ**、4 種の所見の提示、確かめられなかった約束の申告 |
| **Never** | 存在の突合のやり直し / どちらが動くべきかの決定 / 仕様書と実装のどちらかへの書き込み |
| **Starts when** | リリース前、画面の観測可能な振る舞いが変わった後、あるいは食い違いが疑われたとき |
| **Stops when** | 所見を提示したとき。直すのは user、あるいは `new-feature` |

## このスキルを使わない場面

- **仕様書が在るかの確認。**ゲートが決着させている —— 下記。
- **差分の実装品質のレビュー** —— `impl-review`。
- **仕様書を書くこと** —— `new-feature`。

## 2 つの突合と、これがどちらか

[0143](../../../docs/adr/0143-spec-driven-development.md) は突合を 2 つに割っており、
**割り方は「機械がどこまで届くか」**である。

| | 誰が所有するか |
| --- | --- |
| **存在の突合** —— 全 route が画面要件を持つ / route を失った仕様書が無い | [`scripts/spec-routes.gate.test.ts`](../../../scripts/spec-routes.gate.test.ts)。写像は [`scripts/lib/spec-routes.ts`](../../../scripts/lib/spec-routes.ts) |
| **内容の突合** —— 約束がまだ成り立つか | **このスキル** |

**このスキルは存在の突合をやり直さない。**それは決定的に決着しており、散文でやり直すのは
**同じ検査を劣った道具でやること**である —— しかも**写像の 2 つめの実装**を生み、
それは規約に追随しなくなる日まで追随する。

**写像は実装し直さず、それを使う。**route の仕様書ディレクトリを解決する必要があるときの答えは
`toSpecDir` である。

## Step 0 —— スコープを確認する

`AskUserQuestion` 1 回。引数が既に答えているなら飛ばす。

- 「読み合わせのスコープを選んでください」
  - 「変更で触れた画面のみ」 —— 仕様書か実装が差分に入っている route
  - 「全画面」 —— 全 route。**これがリリース時のパス**
  - 「1 つのルート」 —— route を名指し

## Step 1 —— route とその入力を解決する

ベースは `commit` / `submit-pr` と同じ解き方で解く ——
`gh pr view --json baseRefName -q .baseRefName`、無ければ `make -s base-branch`。
**解けないなら止める** —— 空の route 一覧は何も fan-out せず何も報告せず、
**それは綺麗なパスとまったく同じに読める。**

範囲内の route ごとに、次を揃える。

- そのディレクトリの仕様書 —— 画面要件と、在るなら機能要件
- 写像先の `src/app` の入口と、そこから届くファイル
- **その上位の `layout.*.md`。**layout の約束は配下すべてに効き、各画面はそこからの差分だけを書く ——
  **layout を見られない検証者には、書き直しと元の記述を区別できない。**

## Step 2 —— 検証者を並列に fan-out する

[`spec-validator`](../../agents/spec-validator.md) を **Agent ツール**で、**route ごとに 1 起動**、
すべて 1 メッセージで出して並列に走らせる。`route` / `specs` / `implementation` を渡す。

**1 起動 1 route、そしてその 2 つのファイルを一緒に。**間違った文書に置かれた記述は
**どちらのファイル単独からも見えない** —— それが、単位をファイルではなく route にしている理由そのものである。

> この環境でエージェントを起動できないときは、代わりに `prompts/validate-spec.md` をその場で辿る。

## Step 3 —— 集約して報告する

```text
仕様書と実装の読み合わせ（scope: <X>）

読んだルート: <N> / 対象: <M>
確かめられなかった約束: <K> — <理由。1 行ずつ>

[約束と実装の食い違い] <n>
  - <route> — 仕様書: `<path>` の <節> / 実装: `<path>` の <symbol>
    どちらが動くべきか: <仕様書 | 実装 | 判断が要る> —— <根拠>
[振り分けの誤り] <n>
[上位 layout の書き直し] <n>
[書かないものが書かれている] <n>

本スキルは何も変更していません。直すのは user、あるいは new-feature です。
```

**確かめられなかった約束は、確かめられなかったものとして報告する。**確かめたものだけを並べた
読み合わせは、**全部を確かめた読み合わせと見分けが付かない** ——
そして**リリース時にはその差こそがこのパスの値打ちの全部**である。

**どちらが動くべきかを決めない。**0143 が決めているのは**向き**である —— 約束が変わったのなら
仕様書が動き、変わっていないのなら実装が動く。だが**そのどちらが起きたかは、ここからは見えない。**
**両方の読みを証拠付きで報告し、user に選ばせる。**

## Step 4 —— 引き渡す

このスキルはどちら側にも一切書き込まない。所見ごとに次を名指す。

| 所見 | 次 |
| --- | --- |
| 約束が変わった | 仕様書が動く —— `new-feature` の仕様書の段、あるいは user |
| 実装がずれた | user が画面を直す |
| 間違った文書に置かれている | user が文を移す。どちらのファイルもその人のもの |
| 仕様書に置くものでない内容 | 家が在る —— `docs/spec/README.md` がそれを名指している |

## やる / やらない

- ✅ ベースは `commit` / `submit-pr` と同じ解き方で解く。解けないなら止める。
- ✅ route の仕様書ディレクトリは共有の写像で解決する。2 つめの実装を作らない。
- ✅ route の 2 つの仕様書を 1 つの検証者へ、上位の layout と一緒に渡す。
- ✅ 検証者を 1 メッセージで fan-out する。
- ✅ 確かめられなかった約束を、理由付きで確かめられなかったものとして報告する。
- ✅ 食い違いは両方の読みを報告し、user に選ばせる。
- ✅ 日本語で報告する。
- ❌ 存在の突合をやり直す / route → 仕様書の写像を実装し直す。
- ❌ どちらが動くべきかを決める。
- ❌ 仕様書や実装へ書き込む。
- ❌ 確かめられなかった約束を、守られているものとして報告する。
- ❌ ゲートを回す。

## チェックリスト

- [ ] スコープを確認した。ベースを解決した、あるいは止めた。
- [ ] route → 仕様書ディレクトリを共有の写像で解決した。
- [ ] 2 つの仕様書と上位の layout を各検証者へ渡した。
- [ ] 検証者を 1 メッセージで、route ごとに 1 起動で fan-out した。
- [ ] 4 種の所見を分けて報告した。空の種別は空と述べた。
- [ ] 確かめられなかった約束を理由付きで並べた。守られているとして報告したものは無い。
- [ ] 食い違いごとに両方の読みを出した。どちら側も選んでいない。
- [ ] 何も書いていない。所見ごとに次を名指した。
