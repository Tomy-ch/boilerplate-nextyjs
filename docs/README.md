# ドキュメント

**設計知識をどこへ置くかを決めるための判定**を持つ。各文書が何を持つかはそれぞれの冒頭が述べる
ので、ここには再掲しない —— ここに置き場の目録を書くと、置き場が増えた日に黙って古くなる。

## 置き場より先に、分類を決める

| 分類 | 何か | 行き先 |
| --- | --- | --- |
| **decision** | 選択肢の中から選んだ、結果が残る判断 | [`adr/`](adr/) |
| **exclusion** | **意図してやらない**と決めたこと | [`adr/`](adr/) |
| **rule** | 決定の帰結として日々強制される制約 | [`rules.md`](rules.md)（ADR へリンクする） |
| **inventory** | コードに追随して漂う目録 | 生きた参照。**ADR には入れない** |

**inventory を ADR へ入れない**のが、この 4 分類を持つ理由である。不変の記録と漂う目録を同じ
文書に同居させると、目録の側が「根拠」の顔をしたまま静かに腐る。依存の**選定方針**は decision
だが、依存の**一覧**は inventory であり、両者は同じ場所に住めない。

## 判定 —— 上から順に当て、最初に YES になったところが行き先

1. **これを覆すとしたら、誰かが「別の案を選び直した」と言うことになるか。**
   → [`adr/`](adr/)。却下した案が書けるなら確実にここ。「意図してやらない」も ADR
2. **次に同種のものが来たとき、どちらへ倒すかを答える基準か。複数の層や部品にまたがるか。**
   → [`design/`](design/README.md)
3. **「やったら違反」と機械的に言える形か。**
   → [`rules.md`](rules.md)。根拠の ADR へリンクする
4. **1 つの層・feature の中で完結する責務・禁止・所有する状態の話か。**
   → その層 / feature の `README.md`
5. **業務が何を意味するかの話か。その領域の語彙で書けるか。**
   → [`spec/`](spec/README.md)
6. **コードに追随して漂う目録か。**
   → 生きた参照。ADR へは入れない
7. **どれでもない。**
   → **元の場所（コード）に置いたままにする**

## 2 つのテスト

判定に迷ったときは、この 2 つで決まることが多い。

- **管轄テスト** —— **これを覆すとしたら、誰がどの文書を更新する義務を負うか。** そこが家である。
  「この Why は非自明か」ではない。非自明さは量の議論にしかならない
- **前提の所在テスト** —— **この宣言を編集せずに、この記述を偽にできるか。** できないなら、それは
  気づかれずに腐ることがないのでコードに残る。できるなら（上流の振る舞い・運用方針・業務規則）、
  誰もそれを検証できず、偽になっても何も鳴らない

## 既定は「動かさない」

**行き先が決まらないものに、仮の置き場を作らない。** どの行き先にも当てはまらないなら、それは
コードが正しい置き場だった証拠である。

間違った移動は、移動しなかったことより**取り消しが難しい**。移した先の文書は書き換わり、元の
場所には残余しか残らないので、後から「本当はここで良かった」と戻すには両方を直すことになる。

## `adr` / `design` / `rules.md` は 3 つのノード

同じ主題について、3 つが別々の問いに答える。

| ノード | 問い | 時間的性質 |
| --- | --- | --- |
| [`adr/`](adr/) | **何を決め、何を却下したか** | 記録。v1.0.0 未満は living document として本文を上書きする（[0140](adr/0140-documentation-operations.md)） |
| [`design/`](design/README.md) | **目の前の case をどう裁くか** | **育つ。** 基準が鋭くなるたび書き足す |
| [`rules.md`](rules.md) | **何をしたら違反か** | 強制可能な禁止だけ。判断の根拠は持たず、上の 2 つへリンクする |

**`design/` が生えるのは、1 つの README では収まらない判定手続きがあるときだけ。** 「この取得は
どこに置くか」を毎回裁く必要がある主題には基準が要るが、「必ずこの口を通す」で終わる主題には
裁く余地がなく、書くことがない。後者は決定（ADR）と、それを実装する層の README で足りる。

## `spec/` と層・feature の `README.md`

| | [`spec/`](spec/README.md) | 層 / feature の `README.md` |
| --- | --- | --- |
| **何の語彙で書くか** | **業務・ドメインの語彙** | **実装構造の語彙** |
| 何を答えるか | この業務ルールは何を意味するか。どの値がどの範囲か。どの遷移が許されるか | 何を所有し、何を禁じ、どの状態を持ち、どうテストするか |

**入場条件はその語彙で書けるかであって、粒度ではない。** 業務の語彙で書けないものは、どれだけ
詳細でも spec には入らない。逆に、業務の語が README の中で育ち始めたら、それは家を出た語であり、
同じ語が別の場所で再定義される。

## 行き先にならない場所

**設計知識をここへ移設しない。** それぞれ別の理由で、受け取っても保たない。

**ただし「行き先にならない」と「読まなくてよい」は別である。** ここに挙げた場所にも決定は書かれて
いて、行き先が無いまま置かれているからこそ**引き上げる対象**になる。とくに `plan/` と
`get-started/` は、**まだ ADR になっていない決定の在り処**である。移設先として選ばないことと、
探しに行かないことを取り違えない。

| 置き場 | 受け取らない理由 |
| --- | --- |
| [`playbook.md`](playbook.md) | 逆引きの索引。行き先が増えたら索引を更新するだけ |
| [`traceability.md`](traceability.md) | 集計。自分でそう宣言している |
| [`portal/`](portal/) | 生成ビュー。生成器が書き直す |
| `plan/` | 過程の成果物。テンプレートから作った側へ配るものではない |
| `get-started/` | 手順。テンプレートから作る前提が死ぬと消える |
| [`screens.md`](spec/screens.md) | 輸入したサンプルの画面表。残す側の文書ではない <!-- sample:line --> |

**対訳（`*.ja.md`）は正典の写しであって、別の置き場ではない。** 知識を探すのも、判定を当てるのも、
書き換えるのも正典に対して行い、対訳はそれに追従する（[0140](adr/0140-documentation-operations.md)）。
両方を読むと同じものを 2 回読むことになり、両方を書くと片方が遅れる。

**開発の経緯・移行の履歴・「なぜ X から切り替えたか」は `.github/release/` が受け取る。**
恒久文書に経緯を書かない。恒久文書が答えるのは「いま何が真か」であって、「どうしてそうなったか」
ではない。

## 捨てられる文書に一般形を書かない

前提がいずれ失効する記述は、**その場でマークせず、失効と同時に捨てられる 1 つの文書へ集める。**
散文の途中を切り取ると、切り口の両側を繕う必要が残り、その近くを編集するたびに壊す機会が増える。

**一般形は残る側の文書に置き、そこから 1 行の自己完結したリンクだけを張る。** 行ごと消せる形で
なければ、捨てるときに残る側を壊す。
