# テスト検証手段方針(async RSC テストの寄せ先・a11y 自動テストの組込・visual regression・E2E の実行条件)

[0090](0090-testing-strategy.md) が本 ADR へ委ねた **async Server Components(RSC)テストの寄せ先**と、[0100](0100-accessibility-target.md) が手動チェックに委ねていた **a11y 自動テストの組込**、および **visual regression** と **E2E の実行条件** を確定する。いずれも [0090](0090-testing-strategy.md) のテストピラミッド(unit / component / integration / e2e)tooling 上に載る **検証手段** であり、1 ドメインとして本 ADR に束ねる。

UI カタログ(Storybook)の採否は機能 seam でない開発ツール選択という別主題であり、[0054](0054-ui-catalog-storybook.md) が持つ。

## Status

Accepted

## 背景

[0090](0090-testing-strategy.md) は層別責務(unit / component / integration / e2e)を確定するが、**Server Components のテスト方針 / RSC・route handler・E2E の線引き**を本 ADR へ委ねる。これが決まらないと最初のテスト PR で毎回この議論が再燃し、カバレッジゲート(0090)の充足手段も定まらない。

[0100](0100-accessibility-target.md) は a11y 検証を「biome 静的検査 + 手動チェック」で構成するが、**実行時 DOM に対する自動検査**(ARIA 整合・コントラスト実測)は biome(静的)では検出できず、AA 目標(0100)の検証が手動レビュー頼みになる。

本 ADR は [0010](0010-standards-and-non-lockin.md) の 2 原則(標準準拠 / 非ロックイン判定)に基づいて確定する。

## 決定

### 1. RSC テストの寄せ先

- **async RSC 自体は unit(Vitest + RTL)で検証する**。async Server Component は **JSX を返す async 関数**であり、`render(await Component(props))` の形で描画できる。React Testing Library が扱えないのは `render(<Component />)`(要素として渡す形)であって、関数として await してから渡す形はこの制約に当たらない
- **取得は module 境界で差し替える**。`adapters` を `vi.mock` で置き換えると、`server-only` を含む import 鎖がそもそも読み込まれないため、サーバランタイムを模した描画 mock を積む必要がない([0090](0090-testing-strategy.md) の mock 戦略「モジュール境界の差し替えは `vi.mock`」に一致)
- **unit が負うのは、取得結果をどう組み立てて渡すか**である。取得した値の写し方、`notFound()` などフレームワーク境界への振り分け、失敗分類の再 throw は、いずれも取得の実体を持たずに決まるため unit の対象とする
- **E2E / integration が負うのは、通しでしか確かめられないもの**に限る。実 API 応答の形と契約適合は integration(MSW)、ブラウザ経路・streaming と HTTP ステータスの対応・hydration・cache の再検証は E2E(Playwright)である。unit で mock した取得を「取得を検証した」と数えない
- **route segment(`src/app/**/page.tsx`)は別に判定する**。`params` / `searchParams` が Promise である App Router の規約と生成型に依存するため、unit の対象に含めるかは route 側の検証手段として個別に決める(E2E 側に置く)
- **正当性材料(vendor-independent / [0010](0010-standards-and-non-lockin.md) §2)**: この線引きは「フレームワークが提供する描画経路をどこまで再現するか」ではなく、**検証対象が取得の実体を必要とするか**で決まる。したがって React / Next.js の実装詳細が変わっても線は動かず、Vitest / Playwright のどちらを使うかにも依存しない
- 本 ADR が確定するのは**寄せ先(placement)**である。**MSW モックの具体パイプライン(契約 → MSW の契約駆動モック)は [0071](0071-bff-api-integration.md) の責務**であり、本 ADR では二重に決めない([0090](0090-testing-strategy.md) の mock 戦略 = MSW / `vi.mock` と接続)

### 2. a11y 自動テストの組込

- **axe-core を実行時 a11y 自動検査として組み込む**。バインディングは 0090 が採用した各フレームワークに乗せる = **component 層に `vitest-axe`(Vitest + RTL)/ story・e2e 層に `@axe-core/playwright`**
- **story 全数を実ブラウザで検査する**。visual regression と同じ digest 固定コンテナ・同じ story 列挙に相乗りし、追加のランナーは入れない(§3)。**実ブラウザであることが本質** — jsdom には描画も色計算も無く `color-contrast` を検査できないため、component 層では同ルールを無効にしている
- **検査するのは撮影と同じ 1 テーマだけ**。全 story を 2 テーマぶん検査すると実行が倍になり、private ランナー(2 コア)で課金される。撮らない側のテーマ(dark)は、配色が面へ効いていることだけを見る(`vrt/theme-tokens.spec.ts`)。**片テーマでだけ出るコントラスト違反は届かない** — 配色値の正しさは token の SSOT と生成物の突き合わせ(`tokens-drift`)が持ち、ここが持つのは実描画での検出である
- **spec と job は visual regression と分ける**。a11y の失敗が撮り直しの報告へ混ざると、撮り直しの経路がそれを撮り直そうとする。撮り直しても a11y は直らず、基準画像だけが承認済みになる
- **責務境界は「story の有無」ではなく「その層に何が見えるか」で引く**。`axe()` は **story を持つかどうかに関わらず、描画を返す対象のテストすべてに書く**。両層は同じ観点を二重に保守しているのではなく、**見えるものが違う**:
  - **component 層(jsdom)**が見るのは、その部品が単独で満たすべき **ARIA 整合・アクセシブルな名前・関係**である。部品の契約として固定するので、契約が壊れた瞬間に unit の実行で落ちる。色は見えない(`color-contrast` は無効化する)。**`region` も無効化する** —— 「ページの内容がすべて landmark に含まれるか」を見る page 単位の best-practice 規則であり、landmark を持たない component 単体の render と、Portal で `body` 直下へ出る内容の両方に構造上適合しない。component の意味論を見る規則ではないため、無効化しても検査範囲は狭まらない
  - **story 層(実ブラウザ)**が見るのは、**実描画でしか出ないもの** — コントラストの実測と、合成した状態での崩れである。全数を 1 テーマで回す(上記)
  - ARIA 系のルールは両層で鳴り得るが、**落ちる時機と単位が違う**ため重複ではない。片方を落とすと、部品の契約が壊れたことを PR の unit では検知できなくなるか(component 側を落とした場合)、実際の配色で読めないことを検知できなくなる(story 側を落とした場合)
  - したがって **story を持たない対象(feature の合成 / page)にも `axe()` は要る**。story 層が到達しないので、そこだけが唯一の検査地点になる
- **検査するルールの範囲は適合目標そのもので決める**。axe は既定で目標の外側(`best-practice` 等)まで回すため、範囲を宣言しないと掲げていない水準を全 story ぶん評価することになる。宣言は目標([0100](0100-accessibility-target.md) §1 = WCAG 2.x AA)を axe のタグへ写したものであり、目標を動かすときは 0100 を先に変える
- **無効化するルールは理由と撤去条件を添えて 1 箇所へ宣言する**。全 story から外してよいのは、story が部品を単独で描画していることの副作用として鳴るものだけで、「いまは直せない」は理由にならない
- **story を名指しする無効化は、上流の実装が原因で到達不能なものに限る**。使う側の実装では取り除けず、かつ利用者が実際には到達できないことが条件で、宣言は対象 story を列挙する。他の story では同じルールが生きたまま残る
- **正当性材料(vendor-independent / [0010](0010-standards-and-non-lockin.md) §2)**: AA 目標(0100)は、biome(静的)が表現できない**実行時 DOM の ARIA 整合・コントラスト**を機械検証する層を必要とする。この必要性は特定ベンダーに依存しない — axe-core は Lighthouse / Deque / 各種 `*-axe` ラッパが共有する事実上の a11y エンジンであり、「axe を正当化から抜いても、実行時 a11y を自動アサートする層を test に敷く」というパターンは AA 準拠それ自体から正当化される(数ある選択肢〈手動のみ / 他エンジン〉から、独立した根拠で axe を 1 要因として選んだ)。`vitest-axe` / `@axe-core/playwright` は 0090 で既決のフレームワークへの標準バインディングゆえに一意
- 依存追加は exact pin + `pnpm audit`([0004](0004-library-management.md))。CI 組込は [0153](0153-ci-configuration.md) へ

### 3. visual regression = Playwright のスクリーンショット比較を採用

- **visual regression を採用**し、実行基盤は **[0090](0090-testing-strategy.md) が既に採る Playwright のスクリーンショット比較**(`toHaveScreenshot()`)とする。追加のサービス・別ランナーは導入しない
- **正当性材料(vendor-independent / [0010](0010-standards-and-non-lockin.md) §2)**: 検出したいのは「意図しない見た目の変化」であり、これは DOM アサートでは表現できない。Playwright は E2E ですでに動いており、スクリーンショット比較はその**組込機能**であるため、専用 SaaS を正当化から抜いても「基準画像との差分を CI で比較する」というパターンは成立する
- **対象は Storybook の story を第一とする**([0054](0054-ui-catalog-storybook.md))。story がコンポーネント在庫リストであり、feature 画面より安定した比較単位になるため。画面単位の比較は主要ジャーニーに限る
- **基準画像は専用のリポジトリへ置き、サブモジュールとして参照する**。PNG は圧縮済みで delta も zlib も効かないため、同じ repo に置くと更新 1 回ぶんがほぼ丸ごと永久に積まれ、design token を触るたびに全数が動く。置き場は workflow もルールセットも持たず、更新・掃除はすべて本体側から流し込む
- **置き場の公開範囲は既定で `private`**。基準画像は画面の見た目そのものなので、公開側へ倒れる既定は取らない。代償は、**外部(fork)からの PR で比較が落ちる**こと —— fork の PR には secrets が渡らず、基準画像を読むトークンを取れない。外部の PR を受けるリポジトリは `public` にする
- **撮り直しは一式まるごとを 1 コミットにし、親は常に置き場の根とする**。撮り直しどうしを繋げると古い一式が新しい一式の祖先になり、掃除でどれも落とせなくなる。根を共有させるのは、compare が無関係な履歴どうしを比較できないため
- **保持するのは本体の生きた ref が指す一式だけ**とし、条件は理由と撤去条件を添えて 1 箇所へ宣言する。過去のコミットへ遡ると基準画像が揃わないのは前提であり、**掃除の実行は人が起こす**(取り消せず、保持の計算を誤ると生きたポインタを殺す)
- **ポインタは、そのブランチが変更を受け取る経路で入る**。直接 push できるブランチへは push し、ruleset が PR を要求するブランチ(`release/**` / `hotfix/**` と各環境のブランチ)へは、gitlink だけを載せた PR を開く。**その PR は対象ごとに 1 本で、撮り直すたびに開き直さず更新する** —— 撮り直しは繰り返し起きるので、1 回ごとに 1 本増やすと、マージしなかった提案が溜まっていく側へ倒れる。**保護を緩めて bot に直接 push させる形は採らない** —— 迂回できる保護は保護ではなく、緩める先は ref 単位に絞れないので `production` まで一緒に開くことになる。経路の判定は ruleset そのものに問い合わせ、パターンの写しを持たない
- **壊れた木からは撮らない**。撮り直しは人が見ていない時刻に走るので、その瞬間の絵がそのまま正になり、絵を決める入力が壊れたまま撮ると壊れが基準画像へ焼き付く。判定に使うのは**絵を動かしうる検査を名指しした一覧**で、落ちているもの全部ではない —— 全部を数えると、撮るまで存在しない画像の承認を待つ検査が入り、承認は撮り直しを、撮り直しは承認を待つ。**見るのは各検査の最新の結果**であり、試行を合算しない —— 合算すると、一度揺らいだ検査はその commit が生きているあいだ落ちたままになり、再実行して緑にしても撮り直せない
- **revert では、ラベル無しで撮り直す**。掃除により復帰先の一式が消えていることがあるため。revert は定義上「以前に承認された状態へ戻す」操作なので、自動化しても承認の意味は壊れない
- **承認は画像差分のレビューで行い、その単位は PR のレビューではなくラベル(`baseline-approve`)に取る**。基準画像を撮り直す操作(`baseline-retake` ラベル / 手元での実行)は「画素を見られる形にする」までであり、それ自体は承認ではない。基準画像が動いている PR では承認ラベルを必須にする。単位をラベルに取るのは、判断の対象が PR 全体ではなく基準画像だからで、1 人のリポジトリでも成立するという性質はその帰結にすぎない。差分は撮り直しのコメントが動いた画像 1 枚ずつに並べる前後のリンクで見る — 画像そのものを PR コメントへ貼らないのは、置き場が非公開のとき GitHub の画像プロキシが匿名でアクセスして 404 になるため(見る人の権限は関係ない)。置き場の compare ビューは使えない: 撮り直しは一式まるごとを置き場の根の上に積むので、共通の祖先が根になり、動いた数枚ではなく一式まるごとが「追加」として並ぶ
- **撮り直せる範囲は、直前の実行が報告した差分に限る**。報告した集合と撮り直す集合を同じ出所(実行結果のレポート)から取ることで、表に出ていない差分が基準画像へ入る経路を塞ぐ
- **1 つのラベルが複数の系統を覆うとき、全系統が覆われるまでラベルを消費しない**。系統ごとに報告の出所が違えば、報告の出る時刻も違う。先に報告した系統だけを撮り直してラベルを外すと、遅れて報告した系統はそのブランチで二度と撮り直されない —— **撮り直しは起きたのに、覆われていない**という、緑にも赤にもならない状態になる。判定は「報告が無い」ではなく「報告がまだ出ていない / 出たが差分が無い」を分けて行う。前者は待ちであって、撮る対象が無いことではない
- **判定する木と撮る木を一致させる**。比較は base へマージした結果に対して行うため、base に遅れたブランチでは撮り直させない。マージ時点で最新であることを要求することで、判定済みの木がそのままマージされる
- **保護ブランチ着地後も比較する**。前提(判定済みの木がマージされる)が崩れた場合にだけ鳴る。ここで基準画像を撮り直すことはしない — 誰も画素を見ていない状態を正にすることになる
- **除外は理由と撤去条件を添えて 1 箇所へ宣言する**。撮っても意味を持たない story(見た目が時刻の関数になるもの等)に限り、「いまは直せない」は除外の理由にしない
- **OS / ブラウザ差は、実行環境を digest 固定したコンテナへ閉じることで吸収する**。フォントのラスタライズは OS でも CPU アーキテクチャでも変わるため、基準画像が一意なのは「どのイメージで撮ったか」による。ホスト直実行は比較の前に落とし、撮った人の環境が基準になる状態を作らない
- **差分許容度は置かない**(`maxDiffPixels: 0`)。同一イメージで撮る前提が成り立つ以上、閾値はその幅に収まる退行(1px のずれ・わずかな色の変化)を通すだけになる
- **揺らぎは撮影条件の固定で消す**(animation の停止 / `prefers-reduced-motion` / フォント読み込みの待機 / カーソル非表示 / timezone・locale の固定)。時間で変化する story は「収まるまで待つ」ことで扱い、許容差分で吸収しない

機構の手順(撮り直し・承認・掃除の流れ)は [`docs/design/vrt.md`](../design/vrt.md) が持つ。

### 4. E2E の実行条件

- **E2E は MSW モードで実行し、バックエンド非依存にする**。CI でバックエンドを立てない。前提はモックが**同じ要求へ同じ応答を返す**ことで、契約から生成した応答は素のままでは呼ぶたび中身が変わるため、画面の基準画像も中身の検証も成立しない
- **画面単位の比較は story の比較と同じ digest 固定コンテナへ相乗りし、基準画像の置き場も共有する**(§3)
- **アプリはホストで起動し、コンテナで動かすのはブラウザだけ**にする。`node_modules` は入れた OS と CPU 向けに解決されるため、コンテナ内で `next start` を起動できない
- **同じ Playwright の土台に乗る 3 件を E2E の射程に含め、独立させない**:
  - **ブラウザエラー** — hydration の不一致 / 描画中の例外 / 通信の失敗を検出する。**hydration の不一致は build も型検査も通り、実機でしか出ない**
  - **レスポンシブ** — [0051](0051-styling-system.md) §2 の 3 段で見る。境界の値は design token が持ち、テストへ数値を書かない
  - **クロスブラウザ** — [0102](0102-browser-support.md) が追認するモダンブラウザを 3 つの描画エンジン(Chromium / Firefox / WebKit)へ畳んだものだけを見る。**銘柄も版も見ていない**ことを job に書く

## 禁止事項

- ❌ サーバランタイムを模した描画 mock を積んで async RSC を回すこと(取得は `adapters` を `vi.mock` で差し替える。それで足りない検証は E2E / integration の担当)
- ❌ unit で mock した取得を「取得を検証した」と数えること(実 API 応答の形は integration、ブラウザ経路とステータスは E2E)
- ❌ 検証できない前提で feature の `page-content.tsx` をカバレッジ・1:1 ゲートの母数から外すこと(除外は「通しでしか確かめられない」ものに限る)
- ❌ MSW モックパイプライン機構を本 ADR で確定すること([0071](0071-bff-api-integration.md) が所有。二重決定しない)
- ❌ axe(`vitest-axe` / `@axe-core/playwright`)を理由なく無効化すること、a11y 自動検査を feature 実装から切り離して「後付け」にすること([0100](0100-accessibility-target.md) 実装 PR 時担保と接続)
- ❌ a11y 関連依存を exact pin / `pnpm audit` なしに追加すること([0004](0004-library-management.md))
- ❌ visual regression の差分許容度を上げて揺らぎを吸収すること(揺らぎは撮影条件の固定で消す。閾値はその幅の退行を通す)
- ❌ 報告されていない差分を撮り直しの対象に含めること、基準画像の撮り直しそのものを承認と見なすこと
- ❌ 保護ブランチで基準画像を自動的に撮り直すこと(前提が崩れた合図を消すことになる)
- ❌ 落ちている検査の全部を撮り直しの条件に数えること、試行を合算して判定すること(§3。承認と撮り直しが互いを待つ)
- ❌ 基準画像の置き場の保護を緩めて bot に直接 push させること(§3。gitlink は PR で運ぶ)
- ❌ 除外を story 側の宣言だけで済ませること、揺らぎを理由に除外すること(揺らぎは撮影条件で消す)
- ❌ 比較対象を story 側の申告制にすること(申告制では新しく足した story が黙って対象外になる)
- ❌ 基準画像の置き場にルールセットを掛けること(撮り直しの push を自分で塞ぐ)、置き場側に workflow を持たせること(正が 2 箇所に分かれる)
- ❌ 基準画像の掃除を自動実行すること(取り消せない操作を、報告を読んだ人の判断なしに走らせない)
- ❌ E2E をバックエンドに依存させること / アプリをコンテナ内で起動すること(§4)

## 補足
