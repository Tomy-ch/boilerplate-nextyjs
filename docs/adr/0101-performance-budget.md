# パフォーマンス予算

パフォーマンスの **計測指標(Core Web Vitals)/ 予算の仕組み(Lighthouse・bundle size)/ 具体閾値の所在** を定める。本リポジトリは**仕組みと、用途に依らない閾値**を持ち、**用途で動く閾値だけ**をここでは定めない。

## Status

Accepted

## 背景

**予算値のうち用途(コンテンツ量・対象デバイス・SLA)に依存するのは bundle size であり、Core Web Vitals の閾値は依存しない。** 後者は Web の標準が "good" として定める境界そのもので、どのアプリでも同じ値を指す。両者を「予算値」として一括で用途依存にすると、**どこも計測はするが誰も落ちない**状態になり、仕組みだけが残る。

## 決定

### 1. 計測指標 = Core Web Vitals

- パフォーマンスの一次指標は **Core Web Vitals(LCP / INP / CLS)** とする(業界標準)。lab 計測(CI Lighthouse)に対する **field 値(RUM)の収集経路は [0082](0082-client-observability.md) が定める**(INP 等は実ユーザ操作を要するため field 側で補完)

### 2. 予算の仕組み(計測 + ハードゲート)

- **Lighthouse / bundle size 予算を CI で計測し、超過で落とす**。組込みは **[0153](0153-ci-configuration.md)** の枠(job 分割 / PR コメント upsert 基盤)に従う。計測 job は 2 つで、`lighthouse` が画面ごとの Core Web Vitals を、`bundle-budget` が route ごとの client JavaScript を持つ
- **2 つは判定の時点が違う。** `bundle-budget` は PR ごとの required check、`lighthouse` は保護ブランチへの push と日次で回し、落ちたら issue を立てる。**PR でも待たずに測る場合が 2 つあり、どちらも構造で決まる** —— 画面の宣言(`e2e/lib/screens.ts`)が動いたとき(**一度も測られていない画面**が生まれた可能性があり、比べる先の数値が存在しない)と、layout が動いたとき(全画面がそこを通る)。数値を要さずに理由を言えるものだけを置く。**ラベルを促す判定はここが持たない** —— 先送りにした 3 つの検査(`a11y` / `e2e` / `lighthouse`)を 1 度に読む側が持ち、そこは上の 2 つで既に測ると決まった PR では計測を勧めない([0153](0153-ci-configuration.md) §2)。同じ趣旨の判定を 2 箇所に持つと、同じ PR に同じ趣旨のコメントが 2 件残る。**Lighthouse の計測は直列でしか成立しない** —— 同時に測ると並列度そのものが数値へ混ざるため、費用が `画面数 × 試行回数` に張り付く(実測で 23 画面 × 3 試行 ≒ 16 分)。試行を削れば runner のぶれを吸う中央値を失い、画面を削れば宣言から全数を引く意味を失うので、**削るのは網羅ではなく頻度**とする。代償は、退行の検知が 1 マージぶん遅れること
- **base ブランチも同じ計測で build し、増分は base との差で判定する。** 上限だけでは、変更が余裕を数 KB ずつ食い潰し、線を越えた最後の PR を触った人が赤くなる —— 重さを足した人ではなく。base 比較は上限を宣言していない route(同梱サンプルが所有する全 route)も覆うので、宣言の無い route の増分も黙って通らない
- **増分の上限は変更 1 つぶんのラチェットであり、昇格の PR では判定に使わない。** 上限が総量の天井を持ち、増分は「余裕を小刻みに食い潰して最後の PR だけが赤くなる」を防ぐ。この役割は base が**その変更の着地先**であることに乗っており、昇格(`release/*` → `production` / `staging`)では base が配信中のブランチになる。そこへの差は個別に増分を通った変更の総和なので、変更 1 つぶんの幅を当てれば**リリースの度に必ず割れる** —— 緑にする唯一の手が「増分の幅を広げる」になり、feature PR 側のラチェットまで一緒に壊れる。昇格では差を報告に留め、落とすのは宣言した上限だけとする。**したがって昇格でリリース全体の総量を見張るのは routes の宣言の側**であり、宣言を持たない route は昇格では何にも当たらない
- **閾値は本 ADR ではなく [`performance-budget.yaml`](../../performance-budget.yaml) が持つ**。値を変えるたびに ADR を書き換える形にすると、閾値を動かした事実が決定の履歴に紛れる。宣言には**根拠を必須**にし、空なら読み込みの時点で落とす
- Lighthouse が判定するのは **LCP / CLS / TBT の 3 つだけで、performance スコアは見ない**。スコアは 5 指標の加重平均であり、下がったときにどれが下がったかを答えられない。INP は実ユーザの操作を要して lab では測れないため、その代替として TBT を見る(field 値の収集経路は [0082](0082-client-observability.md))
- **効果の A/B は、先にノイズの床を出してから比べる。** 2 つの成果物のどちらが速いかを言うとき、その差が実在するかを決めるのは**同じ成果物を 2 度測った差**である。実測では、CPU を絞って操作を反復する計測で同一 build の 2 回が +12〜+63% 動き、施策側の差(−9〜−11%)はその中に埋もれた。床を出さずに 1 回ずつ比べると、施策の有無ではなく実行の順番を測ることになる。**床を超えない差は効果として報告しない。**
- **CI runner の数値はぶれるため、画面ごとに複数回測って中央値を採る**。試行回数も同じ宣言が持つ。ぶれを理由に閾値を緩め続けると gate として機能しなくなる。**緩めることを禁じてはいないが、落ちたときの第一選択肢にはしない**（手順は §3）
- **機械の速さを読む「床の画面」を宣言し、割った台すべてで測る**。TBT は runner の速さがそのまま乗数として効くため、その画面が遅いのか機械が遅いのかは**同じ実行の床と見比べて**判別する(§3 の TBT)。割ると床は担当の台にしか居らず、落ちた画面と床が別の機械で測られては見比べられない。担当でない台の測定は**判定せず報告にだけ出す** —— 同じ画面を台数ぶん判定すると、1 台でも遅い実行があるだけで落ちる
- **開く画面の一覧は計測側で持たない**。[`e2e/lib/screens.ts`](../../e2e/lib/screens.ts) の宣言(build の出力と突き合わされる)をそのまま使う。一覧を 2 箇所に持つと、片方だけへ足された画面が黙って測られないまま緑で通る
- **client JavaScript は成果物から引く**。`next build` の出力に First Load JS の列が無いため、route ごとの `__RSC_MANIFEST` と `build-manifest.json` から chunk を集めて gzip する。数えるのは **公開 route の単位**であり、成果物の entry の単位ではない —— 並行ルート(`@slot`)を持つ route は entry を複数持ち、開いたときの HTML はその全ての script を読むので、和集合で数える。entry ごとに数えると同じ route が複数行に割れ、上限も増分もそのうちの 1 つしか見ない
- **数えるのは初期 JS だけではない。** 初期 / 遅延 / 合計 の 3 つと CSS を、route ごとに並べる。初期だけを見る予算は、重いものを `next/dynamic` の先へ移した変更を「減った」として歓迎する —— 開いた人が最終的に払う量は変わっていないのにである。§4 の `next/dynamic` の規則を検査できる形にするには、移した先の量が見えていなければならない。遅延の側は、初期の chunk が読み込み器へ渡す chunk を推移的に辿って引く
- **CSS も予算に載せる。** 描画をブロックするため LCP に直接効き、他にその量を見る job が無い。JS と同じ数字へ混ぜないのは、片方の悪化がもう片方の改善で消えるためである
- **polyfill は数えない**。Next.js が `<script nomodule>` で出すため、[0102](0102-browser-support.md) が対応対象とするブラウザは一度も取得しない。数えると、誰も読まない量が全 route へ一律に乗り、予算が見ているはずの「開いた人が払う量」から離れる

### 3. 具体閾値の所在

**用途で動くかどうかで所在が分かれる。**

| 閾値 | 所在 | 理由 |
| --- | --- | --- |
| Core Web Vitals の CLS | **本書が値を持ち、そのまま引き継ぐ** | "good" の境界は Web の標準が定める固定値であり、アプリの用途では動かない |
| LCP | **本書が値を持ち、そのまま引き継ぐ。ただし値は lab から導く** | **"good" の境界(2.5 秒)は field の定義であり、lab の推定値へそのまま置けない。**模擬回線(150 ms RTT)と模擬 CPU にはリクエストの連鎖ぶんの固定費があり、器も client 島もほぼ持たない画面で 2.16 秒を要する。2.5 秒はこの床の 0.34 秒上にあたり、アプリの側で動かせる幅より計測の振れのほうが大きい。したがって lab の上限は**床 + 実行をまたぐ振れ + アプリへ割り当てる分**で置く。field の LCP は RUM([0082](0082-client-observability.md))が持ち、この上限とは別物である |
| TBT | **本リポジトリが持つ。ただし値は lab から導く** | **これは Core Web Vitals ではなく、Lighthouse が INP の lab 代替として置く指標である。**したがって根拠も上とは別で、"標準が定めた値だから"ではなく"INP を lab で測る手段が他に無いから"そのまま採る。INP そのものの "good" 境界(200 ms)と数値が一致するのは Lighthouse のスコアリング規約の側の都合であり、[0010](0010-standards-and-non-lockin.md) §2 の非ロックイン判定に照らせば、Lighthouse を外した瞬間にこの値の根拠は失われる。**計測手段を変えるときは、この行だけ置き直すこと**。**LCP と同じく、200 ms を lab の推定値へそのまま置けない** —— TBT は main thread を塞いだ時間なので、runner の速さがそのまま乗数として効く。同梱サンプルの 10 実行で、器しか持たない`not-found` が 11〜50 ms、重い画面が 60〜179 ms と、**どの画面も同じ実行で揃って 3〜4.5 倍に動いた**。3 回の中央値は 1 回だけ遅い試行を消すが、実行そのものが遅いときは消せない。したがって一律の上限も LCP と同じ導き方で **床 + 実行をまたぐ振れ + アプリへ割り当てる分** で置き、それを超える重さを設計として引き受けた画面だけ `screens` へ実測を根拠として宣言する。**一律の上限を INP の境界(200 ms)のまま置くと、超える画面が実行ごとに入れ替わる** —— 同梱サンプルの 4 release で 3 つの画面が順に超えたが、いずれも別の実行では半分以下で、超えた回に重くなった理由がどれにも無い。それは画面の重さではなく機械の速さを判定している |
| bundle size の route ごとの上限(初期 JS) | **測り直して置き換える** | 実測に由来する値で、別のアプリでは意味を持たない |
| bundle size の増分の上限(初期 JS / 合計 JS / CSS) | 本リポジトリが持つ | 依存更新や chunk の切り直しで動く幅であり、用途に依らない。3 つを別々に置くのは、動く幅が桁で違ううえ、1 つの数字に畳むと片方の悪化がもう片方の改善で消えるためである |

画面ごとの上限は `performance-budget.yaml` の `lighthouse.screens` へ根拠付きで宣言する。**締める側も同じ場所で書く** —— 器と CSS しか持たない軽い画面を既定より締めておくと、器の退行が、重い画面の振れに紛れる前に鳴る。重い画面ほど実行をまたいで振れるため、一律の上限だけでは床の悪化を捕まえられない。**ただし締めるのは LCP の側だけにする** —— TBT は乗数が支配的で、器しか持たない画面ほど機械の速さを素直に写すので、そこへ細い線を引くと遅い実行のたびに床が鳴り、床を見て判別するという役目を失う。

#### 上限を緩めるときの手順

**緩めること自体は禁じない。禁じるのは、落ちたときの第一選択肢にすることである。** 閾値は超えた事実を消すために動かすものではなく、その画面に必要な重さが判明したときに置き直すものである。順序を踏まずに動かすと、gate は「落ちたら広げる線」になり、何も守らなくなる。

1. **まず軽くする。** §4 の書き方を当てて、削れるものを削り切る。削った量と、削った後の実測を残す
2. **削り切れない理由を、機構の言葉で言う。** 「ぶれるから」は理由にならない —— ぶれは中央値と、実行をまたぐ振れを織り込んだ上限が引き受ける。理由になるのは「その画面が開いた人に必ず見せるものが重い」「取得を計測の窓の外へ出すと、体験のほうが壊れる」のように、**代わりに何を諦めることになるかを言えている**ときである
3. **見えるものを変える案があるなら、それも並べる。** 部品を操作で開く形にする、別の描き方へ替える、といった選択肢は、緩める案と同じ土俵に並べて示す。どれを採るかは実装者が決めない
4. **テックリード / アーキテクトの確認を取る。** 1〜3 を揃えて示し、承認を得てから `screens` へ書く。**この確認は省略できない** —— 緩める判断は、その画面の重さを設計として引き受ける判断そのものだからである
5. **宣言には、下げられる条件を書く。** 何が変われば元へ戻せるのかを書いておかないと、恒久の緩和として残る

**締める側にこの手順は要らない。** 軽い画面を既定より締めるのは、守る線を増やす向きの変更である。

### 4. 重さを持ち込まない書き方

**予算は超えてから直すより、超える書き方を避けるほうが安い。** 同梱サンプルの計測で繰り返し現れた形を、規約として置く。

- **値を 1 つ取るために、検証やスキーマの一式を引き込まない。** 定数・項目名・上限値は、それを使う側が検証を必要としないなら、検証を持たない module へ置く。JavaScript の import は module 単位なので、`const` を 1 つ取る import が zod のスキーマ一式を bundle へ載せる。入力欄の `name` は `form-names.ts`、件数の上限は `page-size.ts` のように、**綴りと数だけを持つ module** を分けるのが既定
- **初期表示に要らない重い部品は `next/dynamic` で最初に読む一式から外す。** 判断の材料は「その画面を開いた人が必ず見るか」であり、見ない可能性があるもの(閉じている脇の領域、折り返しの下にある編集面や作図)を外す。**枠は出来上がりと同じ寸法で置く** —— 置かないと、届いた瞬間に下の要素がまとめて動く
- **`next/dynamic` は「見るまで取りに行かない」ではない。** 取得が始まるのは**要素がマウントした時点**で、`hidden` で隠れていても、折り返しの下にあっても始まる。したがって効くのは**最初に読む一式(`bundle-budget` が数える範囲)から外れること**までで、同じページを開いた人はそのバイトを結局払う。取得そのものを遅らせたいなら、描かない条件を持つのは呼び出し側であり、`dynamic` ではない
- **待機表示を、外枠が既に持っているデータへ置かない**([0040](0040-routing-rendering-strategy.md) の「境界は待つものの単位で置く」)。外枠と画面が同じ取得を共有する場合、画面側の `<Suspense>` は既に手元にある値を待つだけで、**画面を二度継ぎ足して読み始めた位置を動かす**
- **和文の Web フォントを本文へ置かない**([0051](0051-styling-system.md) §5)。`@font-face` の宣言が描画をブロックする CSS として載るため、client JavaScript より先に効く
- `NEXT_PUBLIC_` の表面積最小化([0030](0030-environment-variable-management.md))・`"use client"` 境界の葉押し下げ([0040](0040-routing-rendering-strategy.md))が、これらの土台

## 禁止事項

- ❌ 計測の仕組み自体を持たないこと
- ❌ 根拠を書かずに閾値を置くこと(読み込みの時点で落とす)
- ❌ 落ちたことを、閾値を緩める第一の理由にすること(§3 の手順を踏まずに動かすと、gate は「落ちたら広げる線」になり何も守らなくなる)
- ❌ テックリード / アーキテクトの確認を取らずに `screens` の上限を緩めること
- ❌ 計測する画面の一覧を `e2e/lib/screens.ts` の外に持つこと
- ❌ 定数を取るためだけに、検証・スキーマを持つ module から import すること
