# 仕様書駆動

本プロジェクトでは、画面が**何を約束しているか**を仕様書として持ち、実装をそこから導く。仕様書は `docs/spec/route/**` に置き、画面ごとに機能要件と画面要件の 2 層へ分ける。置き場と書き方の細目は [`docs/spec/README.md`](../spec/README.md) が持ち、本 ADR はその採用と、仕様書から実装の骨格を機械生成する経路を**持たない**決定を定める。

[0140](0140-documentation-operations.md) が文書の運用を、[0141](0141-portal-operations.md) が portal を持つのに対し、本 ADR が持つのは仕様書という文書種の採否と役割である。

## Status

Accepted

## 採用理由 / 目的

- **約束の置き場を決める。** 画面の約束（描画の時点とその理由、待ちの境界の掛け方、断り書きを置く位置、節の並び）は、文書にもコードにも doc コメントにも散らばりやすい。仕様書を持つ値打ちは生成の速さではなく、確定した約束が住む場所が 1 つに決まることにある
- **仕様書だけを読んで同じ画面を組み直せる状態を目標にする。** 実装から約束を推定させると、読む側ごとに違う約束が復元される
- **契約から決まることとデザインの判断を分けて差し替えられるようにする。** 混ざっていると片方だけを差し替えられない

## 仕様書を持つ

**仕様書を持つのは画面（`src/app` の route）である。** カーネルと部品は README と Storybook が語彙を持ち、仕様書の対象にしない。

- **置き場は `docs/spec/route/**`** で、`src/app` の階層をそのまま写す。route group は括弧を外し、動的セグメントは角括弧のまま置く。layout の仕様はその配下すべてに効き、画面をまたぐ約束は上位の `layout.*.md` に 1 回だけ書く
- **画面ごとに機能要件（`*.function.md`）と画面要件（`*.screen.md`）の 2 層へ分ける。** 振り分けの問いは 1 つ —— バックエンドの契約と利用者の目的が同じまま、その記述だけが違う画面があり得るか。あり得るなら画面要件、あり得ないなら機能要件
- **機能要件を持たない画面には `page.function.md` を置かない。** 空のファイルは「まだ書いていない」と「無い」の区別を消す
- サンプル画面の仕様書はサンプルの一部であり、サンプルの破棄と一緒に消える。残るのは `docs/spec/README.md` と、コアとして残る画面の分だけである

## 指すだけで写さない

仕様書は次を**指すだけ**で、内容を写さない。写した時点で、直すときに 2 か所へ反映することになる。

| 指す先 | そこが持つもの |
| --- | --- |
| 契約（OpenAPI） | 型・エラー・上限値 |
| token | 値（段の幅など） |
| [`rules.md`](../rules.md) | 日常的に強制される規約 |
| 部品の README + Storybook | 部品の語彙 |
| ADR | 機構の選択と、その理由 |

したがって仕様書には、部品の名前・単位つきの数値・層をまたぐ規約・実装の手順・画面に固有でない運用を書かない。書くのは観測可能な約束と、**やらない理由**である。「状態で絞り込む口は置かない」のような 1 文は、契約に口があっても置かないという判断そのものであり、仕様書の価値の中心はここにある。

## 実装は仕様書から導く

- **仕様書は確定した約束を書く。** したがって書ける時点は見た目が確定した後であり、画面実装の順序（[`docs/playbook.md`](../playbook.md)）では story のレビューを通り、層への割り付けを終えたあとに置く。**仕様書を先に固めることは強制しない** —— 先に固めると、見た目が動くたびに書き直すことになる
- **仕様書を書き終えるまで画面をレビューへ出さない。** 約束が書かれていない画面を出すと、読む側が実装から約束を推定することになる
- **feature の README は route ごとに仕様書の対を指す**（[feature README テンプレート](../templates/feature-readme.md)）。指す先が実在するかは `readme-review` が突き合わせる
- **仕様書は読み込み入力である。** 散文から実装を導けるのは scaffold ではなく、読んで判断する側（人と `new-feature` スキル —— [0155](0155-claude-skills-development.md)）である
- **約束を変える変更は、仕様書を同じ変更で直す。** 仕様書と実装が食い違ったとき、約束を変えたのなら仕様書を直し、変えていないのなら実装の不具合として扱う

## 生成 scaffold を持たない

仕様書から実装の骨格を機械生成する経路は設けない。

1. **仕様書は機械可読な構造を持たず、持たせるべきでもない。** 中身は判断の散文で、価値の中心は「やらない理由」にある。生成器の入力にするには構造化データへ寄せることになり、その部分が落ちる
2. **仕様書が書くのは観測可能な契約であって機構ではない。** 「既定と同じ値は URL に載せない」から、既定を空文字で表す実装は導けない。導けるのは仕様書と契約の両方を読む側だけである
3. **生成の入力は 1 本に保つ。** `pnpm gen` の入力は `architecture.ts` と層 README であり（[0021](0021-frontend-responsibility.md) / [0027](0027-directory-structure.md)）、仕様書を第 2 の入力に足すと構造の正が二重化する

生成器は、仕様書を持つ値打ち（約束の置き場が決まること）を 1 つも運ばない。速さのために置くものは、置いた時点で仕様書の側を生成器の都合へ寄せ始める。

## v1.0.0 到達前に構築を完了する

本 ADR の決定のうち、次の 2 つは機構がまだ揃っていない。**v1.0.0 到達前に構築を完了する。** Status は `Accepted` のままとし、完了をもって本節を削除する。

- **存在の突合。** `src/app` の route と `docs/spec/route/**` の対応（機能要件を持たない画面は画面要件だけ）を機械で突き合わせる検査。いまは feature README が指す link の実在を `readme-review` が見るだけで、仕様書を持たない route を挙げる口が無い
- **内容の突合。** 仕様書と実装を読み合わせ、食い違いを挙げる経路。生成とは独立に成立するため、生成 scaffold を持たない決定の影響を受けない。v1.0.0 を切る時点で全画面を一度読み合わせ、以後は約束を変える変更ごとに行う

## 不採用

| 対象 | 理由 |
| --- | --- |
| **仕様書から骨格を生成する scaffold** | 上記のとおり。仕様書の価値の中心（やらない理由）が生成のために落ちる |
| **仕様書を構造化データ（frontmatter / スキーマ）へ寄せる** | 機械可読にした部分だけが生成器へ渡り、散文の判断が二級の記述になる |
| **仕様書を `pnpm gen` の第 2 の入力にする** | 構造の正が `architecture.ts` と仕様書の 2 か所になる |
| **仕様書先行の強制（先に書いてから実装する）** | 見た目が確定する前の約束は確定していない。動くたびに書き直す |
| **画面の約束を feature README に同居させる** | README が持つのは slice の役割論と置き場である。約束と混ぜると、route をまたぐ layout の約束に置き場が無くなる |

## 禁止事項

- ❌ 仕様書から実装の骨格を機械生成する経路を置くこと
- ❌ `docs/spec/**` を `pnpm gen` の生成入力に足すこと
- ❌ 仕様書に部品の名前・単位つきの数値・層をまたぐ規約・実装の手順を書くこと（指す先が持つ）
- ❌ 空の `page.function.md` を置くこと
- ❌ 仕様書を書かずに画面をレビューへ出すこと
- ❌ 見た目が確定する前に仕様書を固めること
